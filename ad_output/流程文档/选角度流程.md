# 选角度流程（大赛 / 产品通用）

> **管什么**：为一个桶或产品做读者证据卡、生成 8～10 个角度句、选出 3 个主角度、冻结属性，并完成最后的角度复核。
> **不管什么**：术语定义 → `术语真源.md`；正式文案、文案自审、投放数据验证 → `../文案风格/README.md`、`../文案风格/文案自审.md`、`想法池与1000曝光复盘流程.md`；产品 / 活动事实 → 各活动的 `物料/活动细则.md`。
> **谁什么时候读**：建想法池、补货、换角度，以及向用户提交角度候选前。

## 1. 做读者证据卡

每个桶或产品先整理：

- 5～10 个真实关键词；
- 2～3 个典型用户任务；
- 用户现在用什么方法解决；
- 当前做法最麻烦、最不放心的地方；
- 产品能够提供的官方事实和出处；
- 已有数据中最好和最差的文案信号。

产品事实只在证据卡里维护一次，后续不再重复建立事实清单。

## 2. 先生成 8～10 个角度句

统一写成：

> 【某类人】在【具体时刻或场景】做【具体任务】时，真正想确认的是【一个决定他是否行动的具体问题】；因为答案关系到【收益或损失】。

例如：

> 会用 VS Code 的开发者参加比赛时，真正想确认的是“还要不要再学一套工具”；因为这决定他是否愿意报名。

> 做登录核验的开发者面对百万级人脸库时，真正想确认的是“检索还能不能保持足够快”；因为这决定当前方案能不能用。

这里只生成“读者真正关心的问题”，先不写卖点清单，也不决定标题用哪种风格。

## 3. 只选 3 个主角度

只对完整的读者问题排序，不再另设一轮淘汰清单：

1. 是否有真实关键词或历史数据支持；
2. 答案是否真的影响用户行动；
3. 场景是否具体；
4. 对应事实能否直接回答问题；
5. 与已有角度是否真正不同。

本轮只确定 **3 个主角度**。

其余完整的读者问题进入备选池，不固定备选数量；池子总库存上限仍沿用原来的规则，不为凑数放弱角度。

## 4. 冻结完整的角度句属性

角度一旦确认，就把角度句里的全部属性一起冻结。

```text
角度 ID：
目标人群：
触发时刻 / 场景：
具体任务：
核心矛盾：
用户真正想确认的问题：
为什么值得在意：
可承诺的收益方向：
支撑事实与出处：
与已有角度的区别：
失败风险：
```

例如：

```text
目标人群：会用 VS Code 的开发者
触发场景：想报名但看到比赛指定 Kiro
具体任务：用 Kiro 完成参赛作品
核心矛盾：担心为了参赛重新学一套编辑器
真正想确认：原有 VS Code 工作流能不能直接继续用
收益方向：不增加工具学习成本就能开始做作品
支撑事实：Kiro 支持 VS Code 用户无缝迁移
```

冻结的是角度属性，不是标题、摘要或文案风格。

## 5. 最后复核选出的角度有没有问题

这是在选完角度后、交给写文案前做的最后检查，不是市场验证，也不看点击数据。

把 3 个主角度放在一起检查：

1. **三个问题是否真正不同**：用一句话分别概括三个角度。如果三个都能概括成同一个核心问题，说明只是换了说法，不算三个角度。

2. **每个问题是否真的影响行动**：“答案会影响他是否报名、采用、更换或继续现有方案”必须具体。如果只是让人多知道一条信息，角度不成立。

3. **每个问题是否能由证据卡直接回答**：对应事实必须已经在读者证据卡里。需要临时补充事实、猜测用户想法才能成立的角度，退回备选或重新生成。

4. **是否又把卖点或活动规则当成了角度**：把产品名称和功能词暂时拿掉，角度仍然应该剩下一个明确的读者问题。如果拿掉以后只剩“这个功能很强”或“这个活动有某项规则”，说明角度选错了。

5. **三个角度并排是否没有明显缺口**：检查是否三个都在问同一种问题，或者有一个明显与目标人群、任务不匹配。这里只修正明显问题，不重新套阶段配额。

## 6. 复核结果怎么处理

- 3 个角度全部通过：选角度结束，交给后续写文案流程；
- 某个角度未通过：从备选池取下一个合格角度补位；
- 备选池没有合格角度：回到第 2 步重新生成，不用弱角度凑满 3 个；
- 替换角度后：重新冻结完整角度卡，并对新的 3 个角度执行一次最后复核。

最终交给后续流程的产物只有：

```text
3 个已冻结并通过复核的主角度
若干合格备选角度
每个角度对应的读者问题、事实和差异说明
```
