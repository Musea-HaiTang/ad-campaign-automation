# 小改流程

> **管什么**：已经决定小改后，如何基于原句重写摘要。
> **不管什么**：什么时候触发小改、判定门槛、点击数据、角度选择、文案风格定义和最终自审。
> **谁什么时候读**：复盘已经确定要做小改，开始重写摘要时读。

## 1. 小改定义

小改是在**同一角度**内调整现有文案，不换角度、不换卖点、不换风格、不新增证据。

小改默认只改摘要，标题原文不动。摘要可以整句重写，不需要保留原来的句子结构。

一次小改只产出一条默认新摘要，不再生成四条候选交用户选择。

## 2. 固定项

小改开始前先锁定：

- 标题原文；
- 角度 ID；
- 点击理由；
- 文案风格；
- 使用的事实和证据；
- 原摘要的事实含义。

除用户当次明确要求外，不修改标题。

## 3. 读取哪些信息

只读取文案自身的信息：

- 原标题；
- 原摘要；
- `hookKey`；
- `hookNote`；
- 点击理由；
- 角度 ID；
- 原有事实和出处。

不再读取点击数和 CTR 去决定怎么改。小改一旦确定，点击数据就不再参与改稿。

## 4. 摘要现状分析

先判断标题已经完成了什么，再确定摘要需要补什么：

| 标题已经完成 | 摘要需要完成 |
|---|---|
| 用对仗、化用、诗词、悬念或冲突吸引注意 | 说清读者具体得到什么、要做什么 |
| 已经写出收益 | 补充实现方式或可核证据，不重复标题 |
| 提出问题 | 第一句直接回答，后文补充依据 |
| 写出痛点或场景 | 写清事情改变后的结果，以及产品怎么做到 |

摘要只负责一个主要点击理由，不增加第二个卖点。

## 5. 拆出事实卡

不要直接在原摘要上逐词修改。先把原摘要拆成四项：

```text
标题留下的信息缺口：
本轮点击理由：
读者要做的动作：
可以使用的原有事实 / 证据：
```

例如：

```text
标题：不写代码也能搭，数据还能不出域
点击理由：不用开发，数据也能留在自己环境
读者动作：在产品里完成配置
原有事实：配置项搭建、企业版私有化 / 数据不出域
```

## 6. 重写摘要

摘要至少要完成两个语义任务：

1. **落地**：读者点进去到底能得到什么，或者要做什么；
2. **支撑**：产品凭什么能做到，使用哪个已有事实。

这两个任务不要求拆成固定两句，也不需要套固定句式。摘要可以根据表达需要自然组织。

重写时优先使用“收益 / 动作在前，机制 / 证据在后”的关系：

```text
原摘要：
腾讯云智能体开发平台内置多种开发模式，运营和产品同事可以按配置项搭建，企业版支持私有化部署。

新摘要：
不写代码也能搭，数据还能不出域；运营照着配置项就能配置智能体。
```

重写不是逐词润色，可以调整：

- 起句；
- 信息顺序；
- 句间关系；
- 表达对象；
- 产品语言和读者语言；

不得改变：

- 点击理由；
- 角度；
- 风格；
- 事实；
- 证据来源。

## 7. 必须产生实质变化

进入小改后必须输出一版新摘要，不能原样返回，也不能只改标点、时间词或公文式措辞。

新摘要至少改变一个实质维度：

- 换起句；
- 换信息顺序；
- 换句间关系；
- 换信息落点；
- 整句重新组织。

多处可以同时改，只要它们共同服务于同一个点击理由。

## 8. 最终输出

小改只交付一张结果卡：

```text
原标题：（不动）
原摘要：
新摘要：
本轮点击理由：
重写方式：换起句 / 换信息顺序 / 换句间关系 / 换信息落点 / 整句重写
使用证据：
未改变：角度、风格、事实、来源
字数：新摘要 N 字
```

生成完成后，交给现有 `文案自审.md` 做最终检查。

文案自审是最后一道闸门，不在小改过程中重复执行。

## 9. 边界

- 小改不换角度；
- 小改不换卖点；
- 小改不换风格；
- 小改不新增证据；
- 小改默认不改标题；
- 小改只输出一条默认摘要；
- 小改不再做四选一；
- 小改不以点击条件重新判断是否要改。
