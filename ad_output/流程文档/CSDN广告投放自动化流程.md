## 2. 步骤 1 · 摸清活动产品

拿到活动链接后第一件事——不是写词，是摸清产品底细。必查：

| 核查项      | 说明                       | 必填原因                          |
| -------- | ------------------------ | ----------------------------- |
| 产品是什么    | 一句话讲清                    | 后续所有口径都基于此                    |
| **产品形态** | **桌面程序 / 插件 / 网页 / App** | 文案用词必须与形态一致（**形态错 = 0 点击根因**） |
| 目标用户动作   | 活动要用户做什么                 | 决定转化口径                        |
| 核心卖点     | 吸引点                      | 文案角度之一                        |
| 活动钩子     | 奖励/福利                    | 文案角度之一                        |
| 竞品       | 用于拦截词                    | 挂进对应人群桶做拦截（§5.2 第 3 条）        |
| 一句话定位    | 让用户一秒听懂                  | 卷首标题                          |

> 产品形态（上表加粗那行）决定全部动作词：程序写「下载 / 开通」、网页写「打开 / 在线用」、权重写「下载 / 部署」。

## 3. 步骤 2 · 建活动细则文件

- 位置：`activities/{活动名}/物料/活动细则.md`（每个活动一个文件夹，文件夹名 = 活动名）

## 4. 步骤 3 · 分人群桶

**拆桶方法**：从产品价值倒推目标读者 → 按"会搜什么 / 会读什么"拆桶。

> ⛔ **不套用别的活动的分桶表**：桶必须从**本活动**的产品价值倒推，一个活动一套分桶。原「7 类基准」表已删除——照抄别的活动的分桶，会导致为了凑够桶数去写没有钩子的文案。

**判断标准（拆桶）**：**两个条件都满足才建桶**——
1. 两类人「会搜的词 / 会读的文章」差异大（差异小就合并）；
2. 这个人群**能凑出 2 个不重复的强钩子**（见 §4.1）——凑不出就不建桶。

**桶数**：由通过钩子闸门的人群数决定，**不预设 4-7 类**（4-7 只是经验区间）。物料模板已按此改造：模板里只有一个桶块，`gen_material.py` 按桶数复制 N 份 → 任意桶数都能直接出物料。

### 4.1 钩子闸门（决定桶数，夹在「分人群」和「写文案」之间）

**钩子 = 能让这个人群点进来的那句话**。只有参数、文档、排名、许可这类**事实不算钩子**——它们是"素材"，可以垫在描述里，不能当标题。

每个候选人群列 **2 个钩子**，两条必须回答**不同的读者问题**。判据只有一句：**这个人群凭什么点？**（说不出具体的人、说不出他能拿到什么 = 不是钩子）

- 凑不出 2 个 → **砍这个人群**，不硬凑文案。
- **钩子不得跨桶复制，素材可以复用**：同一条产品事实对不同人群可以是两个不同的钩子（"与 GLM-5.2 同基座、全靠后训练"→ 对 AI 编程人群是"能力涨了 50%"，对后训练人群是"重训底座太贵，这条路不用重训"）。

**核心公式**（复盘要用）：`曝光 = 圈选人数 × 展现率`，`点击 = 曝光 × CTR`。底部位置 CTR 极低、统计意义弱，曝光和展现率才是主要抓手。

## 5. 步骤 4 · 写关键词（每类一行，英文逗号分隔）

> ⚠ **什么时候圈：A 路径固定下午**（用户 2026-09-21 跟后台技术人员确认）。那边数据集**每天上午还在写入、一般中午才写完**，
> 同一套词**早上圈出来的数偏小**（实测同款 58 词：10:2x = 7,816 → 11:0x = 67,207，差 8.6 倍）。
> **A 路径的圈选与看数一律安排在下午**（**B 路径不受此约束**，见 §5.1 两路径表下）；判断**只看「日均曝光(预估)」**，
> 能圈多少博文只作参考。详见 §5.1、§9.4。

### 5.1 关键词怎么圈到博文（后台能力）

圈选任务 = **关键词博客ID圈选任务**：圈的实体是**博文**，不是人。关键词拿去跟博文的**四个字段**比对，**命中任一即可**：

| 匹配字段 | 说明 |
| --- | --- |
| 博客 landing 词 | 站外点进这篇博文时带的词 |
| 博客描述 | 博文摘要 |
| 博客标题 | 博文标题 |
| 博客标签 | 博文标签 |

命中哪批博文就圈哪批博文，**人是从博文倒推的**（作者 + 读这些博文的人）。所以判断一个写法行不行，**唯一标准是：这个词能不能匹配到博文**。

- 「idf分析与总数预估」读出的**预估圈选总数** = 这行词能匹配到多少篇博文；同一页面给出的 **idf 值**（如 `python: 2.78`）**我们不解读、不参与判断**。
- **「预估圈选总数」不等于曝光**：它数的是**博文ID的个数**，不区分这篇博文有没有流量。「曝光阈值」才是那个筛子——`曝光≥1` 只收「历史上被展示过」的活博文，`曝光=0` 会把零展示的僵尸博文也算进来充数（池子大 2.2~24 倍，日均曝光反而低 2.8~11 倍）。**所以阈值永远用 1，量不够靠加词**，见 §8。
- **什么时候圈：A 路径固定下午**（用户 2026-09-21 跟后台技术人员确认）：那边的数据集**每天上午还在写入，一般中午才写完**，所以同一套词**早上的数偏小、下午才稳定**（实测同款 58 词：10:2x = 7,816 → 11:0x = 67,207，差 8.6 倍；且数据集**时刻都有写入，只是上午写入多**）。**A 路径的圈选与看数一律安排在下午**，别拿早上的数做判断（B 路径不受此约束，见下）。
- **长尾场景句进不了词表**（如"如何用 Cursor 配置 Python 环境"）——这种句子不会出现在博文的 landing 词 / 描述 / 标题 / 标签里，等于空跑。
- 后台另有一套**圈人**口径（搜索词 / Landing 词 / 相似任务），**本流程不走**（我们圈的是博文）——原文存档在 `memory/暂缓经验.md`。

**两条并列的圈选路径（2026-09-21 起）—— 用哪条先问用户，AI 不自行选**

| | **A · 后台圈选用户**（旧，9/14 起） | **B · 数据平台圈选博文**（新，2026-09-21 跑通） |
| --- | --- | --- |
| 入口 | 广告后台 `3.圈选用户 → 博文圈选任务` | `data.csdn.net`（Data BI）对话式取数 |
| 脚本 | `run_audience.py`（建客群）+ `run_distribution.py`（一键建名单） | `run_selection.py`（导出 CSV）→ `run_distribution_ids.py`（用 id 建名单）——**两条命令分开，中间人工看数量** |
| 关键词来源 | 活动 YAML 的 `keywordGroup.keywords` | 同一份词表 → 拼进「口径提示词」发给对话 |
| 过滤口径 | 后台阈值（曝光锁死 1 + 点击≥X，见 §8） | 提示词里写死：`status=1` + `last_30_days_pv>1` + 六个字段 `multiMatchAny` |
| 达标读数 | 后台「博文圈选任务」列表的**日均曝光(预估)**（§9.4 的唯一判据） | CSV 只给**博文数 / 总点击数 / 平均点击数**，**没有曝光**；要测曝光得先建名单→建工单→跑起来看 |
| 名单类型 | 关键词博客ID名单 | 普通名单（名单列表类型 = 博客ID） |
| 产物落哪 | 后台对象 + `日志/` | CSV 落 `activities/{活动名}/数据/圈选/`，台账 `圈选记录.md`（每次导出一行） |
| 现状 | 在用 | 跑通待评估：**用户要先测它的曝光高不高**，测完再定这条到底留不留 |

- **这次走哪条：先问用户**（两条并列保留，AI 不自行挑）。问法就一句："这次圈选走 A（后台）还是 B（数据平台）？"
- **时点只约束 A 路径**（§0「圈选时点」）：A 要等下午；**B 路径（数据平台导 CSV）随时可导、不用等下午**（用户 2026-09-29 定，取代原「B 的 CSV 也一样」的推断）。
- B 的坑（都已在脚本里处理）：平台「全局记忆」不可靠 → **每次必须整段发口径提示词**；导出的文件没扩展名、是无 BOM 的 UTF-8 → 落盘补 `.csv` 并转 UTF-8 带 BOM；平台返回的 filename 主题词由模型现起，本地文件名脚本自己拼。
- 文档：`automation/docs/run_selection.md`（圈选导出）、`automation/docs/run_distribution_ids.md`（用 id 建名单）。

### 5.2 写作三条铁律

1. **原子化**：复合短语拆成**原子词**，每个原子词单独成词。关键词是拿去匹配**博文**的（圈选任务 = 「关键词博客ID圈选任务」），短语越长命中的文章越少——拆开才会命中更多博文。例：`RAG 检索增强` → `RAG`、`检索增强`；`AI 代码生成` → `AI代码`、`代码生成`。
   - **止拆线**：拆出来的原子词必须**单独就能指向目标人群**；拆到泛词就停（`检索`、`增强`、`AI`、`编程` 单独拎出来会圈进大片无关博文，不保留）。**伞词**（`AI大模型`、`大模型`、`开源大模型` 这种什么都沾一点的）同样不进词表——它对哪一类人都不精准，只会把博文池稀释掉；真要拿它拉量，也**只能挂一个桶**。
   - **拆完要验收**：池子变大 = 人群变泛 + 展现率被稀释。所以拆完**跑一次圈选看人数**，越界按 §8「圈选越界处置」处理；远超上限就回退（收回原子词，或换回更精确的词）。
2. **同义多写法全保留、同时投**：同一概念的另一种叫法要全列——缩写 / 全称（`RAG` / `检索增强` / `检索增强生成`）、中 / 英、大小写（VS Code / vscode / Visual Studio Code、智能体 / agent / Agent、Codex / codex）。
3. **竞品词挂进已有桶，不单独建桶**（§12）
   - **判据**：换位成搜这个词的人——他是在找本产品这类东西，还是在找它能替代的东西？是后者才拦。
   - **归属**：追加到**对应人群桶**的关键词行里，作为拦截子集；**默认一词只挂一个桶**——关键词的单位是**博文**，同一个词 = 同一批博文被两个工单争同一个 T0 位，桶间数据也会互相污染。
   - **优先合桶**：如果一个词在两个桶里都是主角，先问「这两个桶是不是同一批博文」——是，就合成一个桶（两套钩子放进同一个桶的对照 / 实验组），而不是把词挂两遍。
   - **跨桶是例外，发生了才记一句**：确有必要同词多桶时，在活动细则里**一句话**注明「X 词同时挂 A、D 桶，复盘不比这两桶 CTR」；**没发生就不写**。同理，词不重复也会有博文同时命中两个桶（一篇"部署 + 微调"的文章），这类重叠消不掉，只能记录 + 合并观察。
   - 品类词库示例（攒词用，不绑活动）：AI 编程类 = Cursor / GitHub Copilot / 通义灵码 / Claude Code / Codex；可下载自部署类 = DeepSeek / Qwen / Kimi / Llama；闭源旗舰类 = Claude / GPT-5 / Gemini。

### 5.3 输出格式

每类一行英文逗号分隔的关键词（直接整行贴后台）：

```
{A 类}: {关键词1}, {关键词2}, {关键词3}, ...
{B 类}: {关键词1}, {关键词2}, ...
```

每类下方附一行"写法数 · 关键说明"（如「25 个写法 · 竞品拦截 6 个」）。

### 5.4 4 个核心实体（后台对象）

- **任务组** = 顶层容器，1 个（命名 `品牌+负责人-`）
- **资源** = 文案素材（每条 = 标题 + 描述 2 行）

**结构约束**：1 人群 = 1 任务工单 = 1 客群 × 3 资源（对照 34 / 实验1 33 / 实验2 33，**流量均分 1/3**）。**每个桶必须交满 3 条文案**——3 条打的是同一批人，是**并列的三个角度**、没有对照组（见 §6.1；资源名里的「对照 / 实验1」只是后台槽位的固定叫法，不是文案口径）。

## 6. 步骤 5 · 写文案（每桶固定 3 条）

### 6.1 动笔前想清楚角度（不再"选风格"）

**「文案风格」这个概念已取消**（2026-09-28 用户定）：不再有"写文案前先选一种风格"这一步，也没有「默认风格」了。
`文案风格/用户痛点版.md` 只作**参考**——里面那套句式规则（「想让 X，就 Y」「承接词」…）是 AI 从实验里提炼的，
**不是用户定的规范**，想借鉴就借鉴、不想用就不用，**别当模板套**。

**两种风格共同的结构**（后台 `abGroups` 三组，权重 34/33/33 均分）：

- 三条 = **同一个人群的三个角度（= 三种钩子）**，**一条文案对应一个**（2026-09-22 用户定）：
  **就找三种不同的角度，每种写一条**——不绑 §4.1 闸门那两个钩子，也不硬凑；
  角度之间**痛点不同**，不是同一件事换词说三遍。
- **没有对照组**（2026-09-22 用户定）：不再有一条"基准"或"陪跑"，**三条都得有钩子**。
- **横读**：三条摆一起要看得出是**三种不同的说法**。
- **还要定"类型"**（2026-09-24 用户定）：① 伪装成推荐博文 / ② 纯营销类，规则见 `文案风格/两种文案类型.md`；
  **同一批里两种都要有**（存量文案基本是②型，新一轮补齐①型），这样同批 / 同人群 / 同位置，数据直接可比。
  类型是叠在角度上的第二个维度，不替代角度。

### 6.2 写作底线

- **只正向陈述自家卖点**，不拉踩、不影射同行；对比只引官方同表数据，不写结论式贬低。
- 动作词必须与真实产品形态一致（形态错 = 0 点击，见 §2）。
- **纪律只有两层、不要扩写**——全局红线 + 活动特例（内容见 §0，活动特例写 `活动细则.md`）；不要写"AI 自己提炼的纪律"。

### 6.3 交付前自审（必过 · 规则见 `文案风格/文案自审.md`）

**每条文案定稿前都要走一遍**（2026-09-24 用户定：「以后每次你都这样做」）——**四条判据**、回炉循环、
交付时要展示的「初稿 → 卡在哪 → 改写 → 定稿」全过程，规则全在 `文案风格/文案自审.md`，本节只留核心三问。

把自己当成**那个刚读完文章、只剩几秒的人**——你只有很少的时间抓住他。

1. **他会停下来看吗？**（**2026-09-30 用户定的第一关**：站在**目标人群**视角看这条对他有没有吸引力——
   扫读位上是**曝光 → 停下来看 → 点击**，**停不下来就没有点击**；说不出"他扫到哪个词会停" = 没过）
2. **谁会点这条？**（说不出具体的人 = 这条没钩子）
3. **扫一眼看得懂吗？**（读着累、要停下来换算、或者记不住 → 重写）

**桶级回退**：某个桶凑不出**三种角度（三种钩子）** → 回 §4.1 砍掉这个人群，**不要用换词凑数**。

**分工（2026-09-24 用户定）**：写文案阶段 AI 按自审定稿即可，**用户不再逐条判断文案**——
他只在这条**特别中意 / 特别不认可**时才提出来，其余一律以点击数据为准。

### 圈选越界处置（默认策略）

`run_audience.py` 圈选时某桶预估总数超出默认区间 `[10000, 200000]`（越界，脚本 mark `warn`）：

- **曝光阈值锁死 1**（用户 2026-09-21 定：「日常就设置曝光1，然后博文数量越多越好，这样曝光就会大」）。搜索旋钮只剩**点击需≥X**：超上限时升点击收缩；**低于下限时不动阈值**——那是词不够，去改词加词。
  - 为什么不再碰曝光：**曝光=0 是虚池**——池子大 2.2~24 倍，日均曝光反而低 2.8~11 倍（9/14 五桶对照 + 9/21 后台实测两条：12,370 篇→7,757 曝光，300,000 篇→5,130 曝光）。详见 §5.1。
- **默认**：直接用 `--tune` 处理（脚本超上限时升点击、重跑分析、读新总数，取第一个 ≤上限且 ≥下限的组合，写 `thresholds.yaml`，不创建）。
- **低于下限**：标记 `needs_keywords` 并**通知用户改词**，不硬选（规则见 §12）。
- **不逐次询问**：此为用户既定偏好，不必每次向用户确认；跑完把结果**通知用户**即可（哪桶越界、调优后的点击阈值、最终圈选总数、是否仍 `needs_keywords`）。
- 若 `--tune` 后仍无法落入区间（整数阈值跳变、掉到 <下限），脚本会标记 `needs_keywords` 建议改词——这种才需要同步用户。
- 默认阈值：点击需≥`0`、曝光需≥`1`（固定）；**圈选总数下限默认 `25000`**（≈ 保底 1 万日均曝光，2026-09-21 由 1 万抬高）、上限 `200000`；区间可由 `--min-count/--max-count` 调整。

> 空库则从投放开始日全量回填）。补历史 / 修后台改过的数：加 `--from/--to`，幂等、随便重拉。

**判定表（一个结论对一个动作）**：

| 工单累计曝光 | 点击 | 结论 | 动作 |
| -- | -- | -- | -- |
| < 本桶门槛 | — | 未到门槛 | 继续观察，什么都不做 |
| ≥ 门槛 | **实际点击率 ≥ 千三**（点击 ÷ 曝光 ≥ 0.3%） | **达标** | 该桶**停测试**：只留点击集中的那一条作长期单 |
| ≥ 门槛 | 有点击但 < 千三 | 未达标 | 有击的留下（3 资源桶最多留 2 条、2 资源桶留 1 条，按点击多的优先），零点击的下线；**幸存 + 新文案**凑满下一轮 |
| ≥ 门槛 | 0 | 全不合格 | 整批换新文案（条数 = 该桶资源数） |

**门槛**（用户 2026-09-24 定，A 于 2026-09-29 调高）：**A 3,000**（3 资源）｜ B·C·E 1,500（3 资源）｜ **D 1,000（2 资源，50/50）**；
换算成"每条文案"≈ 500 曝光（B·C·E / D）~ **1,000（A，2026-09-29 由 2,250 调上来，对齐这条标尺）**。
> ⚠ **达标线算的是实际点击率**（用户 2026-09-30 定）：门槛只管"**什么时候开始判**"；
> 达标击数 = **当次实际曝光 × 千三（向上取整）**，**不是"门槛 × 千三"那个固定击数**——
> 曝光跑过门槛之后两者会脱钩：KIRO 一批 E 桶 **9,039 曝光 / 9 击 = 0.10%**，按固定击数（3,000 × 千三 = 9）
> 会被判「达标」，按实际点击率是**未达标**（9,039 曝光要 28 击才到千三）。
> 参照值（曝光**正好压在门槛**时的击数）：A 9 ｜ B·C·E 5 ｜ D 3。

**两条纪律**：

1. 后台**只能整单下线**（单个资源下不了）→ 实际动作是"幸存资源 + 新文案建新工单（批次号 +1）→ **新批上线后**再把老工单下掉"（先下会断流）。
2. **批次号每轮 +1**（当前 -6，下一轮 -7），一眼看出第几批。

**每次判定都要留痕**：`数据/判定/` 的清单 + `activities/{活动名}/README.md` 记一笔「哪天、判了哪桶、留了什么、补了几条」。

**每次复盘另留一份报告**（用户 2026-09-29 要求"复盘要有记录、要看的时候能输出"）：`activities/{活动名}/物料/复盘-{日期}-{对象}.md`
（先例 `activities/火山引擎MediaKit/物料/复盘-2026-09-29-A桶.md`）——一次复盘一节、**不覆盖历史**，
写清：**动作顺序 → 判定 → 全史数据 → 结论 → 存疑账（含"怎么算验证通过"）→ 本轮动作 → 复查入口**。
**同时把「本轮动作」写进 `activities/{活动名}/配置/复盘动作.yaml`**（留谁 / 下谁 / 补几条 + 一句说明）——
看板「文案 / 动作」列靠它把"这批这桶**已经调整过**"和"还没动"分开（用户 2026-09-30 定）；
只在报告里写、不写这份文件，页面上就只剩规则建议，看不出这桶已经定过了。
用户说「**输出 {活动} {桶} 复盘**」时 = 读这份报告 + `数据台账.md` 对应批次 + `数据经验.md` 对应条目，按最新数据补进度。

**定下一轮文案的口径**（**2026-10-08 用户定**，取代 2026-09-29 那版"每轮留 1 条锚"）：
每个槽位按**上批读数**三选一——

| 上批情况 | 动作 |
|---|---|
| **0 击** | **重写**：换角度（不是换词） |
| **有点击、没达标** | **小改**：同角度优化表达 / 文风，或加上飘红试一次；**不整条换掉** |
| 小改后**点击或 CTR 涨了** | 先观察，可以继续小改 |
| 小改后**没涨 / 还是没达标** | **重写**（换角度） |
| 用户点名的 | **原样保留**（一个字不改）——这是例外，不是常规动作 |

- ⛔ **没有"锚"这个概念了**（2026-10-08 用户定）：旧的"每轮留 1 条完全不动当内部对照"跟上面这条规则冲突，已删。
  同批对照改成靠**同一条文案的小改前 / 小改后**——所以台账必须记 `lineage`（`实验1-2 → 实验1-9（小改：…）`）。
- **三条都可以小改**（用户 2026-10-08：数据证明这个方向能吸引人，只做小优化没问题）——不强制留槽位写新角度。
- **小改在后台 = 新建资源**：后台不能改已上线资源的文案（用户 2026-10-08 确认），所以小改 = 新建资源 + 新工单、老工单下线；
  和"重写"在执行上一样，区别只在**文案改了多少**，靠 lineage 认祖先。
- **"涨没涨"的样本下限 = 该桶工作日一天的曝光量**（周末和节假日不算——用户 2026-10-08），没攒够就继续观察。
  实测参考（工单级一天）：火山 A ≈3,018 ｜ B ≈598 ｜ C ≈857 ｜ D ≈297 ｜ E ≈706；KIRO A ≈4,279 ｜ B ≈808 ｜ C ≈1,789 ｜ D ≈1,852 ｜ E ≈6,466。
- **每条新文案必须挂一个明确的存疑项**（挂不上就不写）；同一个判断**连续 2~3 轮成立**才从"存疑"升级成结论
  （存疑账在 `memory/暂缓经验.md`；**转正进 `数据经验.md` 前必须先问用户**——用户 2026-10-08 定）。

### 9.4 圈选达标口径 + 基线（2026-09-24 回填）

**达标口径（博客页 T0）**：**「日均曝光(预估)」目标 ≥ 20,000、底线 ≥ 10,000**（用户 2026-09-21 定，取代 9/14 的 5,000；**越多越好**）。

> **判断只看「日均曝光(预估)」**（用户 2026-09-21 明确）：`实际圈选博客ID数`（能圈多少博文）**只是参考**，两者不成比例
> （同一列表里比值 0.2~5.7 都有）。所以**不要用"圈了多少博文"当达标依据**——建完读曝光，才是判据。

**这个数在哪读、什么时候读得到**（2026-09-21 探针确认）：

- **位置**：后台「圈选用户 → **博文圈选任务**」列表的四列 —— `实际圈选博客ID数` / `日均点击(预估)` / `日均曝光(预估)` / `日均pv(预估)`（筛选框 = `请输入圈选任务名称`）。
- **时机**：**创建弹窗里没有这几项**（弹窗只给「预估圈选总数」+ idf 分词表），要**建完、等后台「圈选用户中…」跑完**才刷得出来（实测 10~26 秒）。所以达标判断天然在**创建之后**，而且**要下午做**（见上「圈选时点」）。
- **一条命令读它**：`check_campaign.py --only audience`（名字在位 + 达标一并打出来，见 `automation/docs/check_campaign.md`）。不达标 → **改词重投**（客群名由命名规则算死、重名建不了，重投要带后缀，先例见 `activities/火山引擎MediaKit/调整/`）。
- **出数要等 1~5 分钟**（2026-09-21 实测五桶：快的 80 秒、慢的 4~5 分钟）——别建完立刻判，`--verify` 会自己每 10 秒点一次查询等它。

**试圈流程（2026-09-21 起）**：下午先 `run_audience.py --submit --name-suffix=-试圈 --min-count 1000` 建一版
（**不动正式客群名、不占正式账本**）→ 看「日均曝光(预估)」→ 达标就删掉试圈的、用正式名建；不达标就改词重来。
命令见 `automation/docs/run_audience.md`。
> **建前预估 = 建后实际**（2026-09-21 五桶逐桶验证：弹窗里的「预估圈选总数」与列表里的「实际圈选博客ID数」**完全一致**）——
> 所以下午也可以先在弹窗里点一下「idf分析与总数预估」预检，不建就知道大概能圈多少。

**经验比例**（曝光≥1，只看本活动）：`日均曝光(预估) ≈ 实际圈选博客ID数 × 0.33~0.63`
（9/14 五桶 + 9/21 两条 + 9/21 下午五桶复测 0.37~0.52）。
> ⚠ **这不是通用换算**：2026-09-21 在同一个列表里看到别人家的老任务 `86,685 篇 → 494,922 曝光`（×5.7）、
> `74,342 篇 → 426,266 曝光`（×5.7）——比值从 0.2 到 5.7 都有，**别拿比例反推圈选数**，以实际读数为准。
> 本活动 9/21 两条：`12,370 篇 → 7,757 曝光`（0.63）；`300,000 篇 → 5,130 曝光`（0.017，曝光=0 虚池，已废弃不用）。
> **下限 25,000 是按上面那个比例推的（要 2 万曝光约需 5 万篇）——2026-09-21 待复核**：
> 早上量到的数会偏小（后台上午还在写数据），所以这个下限也得等几个**下午**的实测再定。

> 其他广告位类型（非博客页 T0）用户还没做过，**不要套用这个数字**；每期口径以用户当期给的为准。
> ⚠ **开工前先跟用户确认本期达标口径（哪个指标 + 数值）**——本轮就因为口径从"日均点击 ≥100"改成"日均曝光 ≥5,000"，让前期一轮加词白做。

**基线（2026-09-24 用 -4 / -5 批回填）**：五桶合计 **21,154 曝光 / 13 点击 ≈ 0.061%**，离千三差约 5 倍；
单条文案攒到 4,700+ 曝光也只有 0~3 击。**别拿单条一两击的差异当结论**——单轮每条只有 ~333 曝光时，
一条真 CTR 0.3% 的文案也有 **37% 概率一个点击都没有**（算法见 `数据台账.md` 的说明）。
曝光量级（独占估算）：A ≈7,700/天 ｜ C ≈2,170 ｜ E ≈1,760 ｜ B ≈1,450 ｜ D ≈720。

> **桶间比较前先看博文池**：博文池有交集的桶**不做横向 CTR 对比**（见 §5.2 第 3 条）。

### 9.5 数据落在哪（三层：取数 → 台账库 → 看板）

**三件事分开**，看板只读库（`activities/_db/投放数据.db`，SQLite，标准库零依赖）：

| 层 | 位置 | 谁写 / 谁读 | 关键性质 |
|---|---|---|---|
| **台账库（唯一真相）** | `activities/_db/投放数据.db` | `fetch_perf.py` 写 / 看板数据装配读 | 按天事实按 **(工单, 日期)** upsert；资源读数**每次取数追加一条** |
| 取数流水（原始存档） | `activities/{活动名}/数据/{时刻}[_标签]/` | `fetch_perf.py` 写，**没人读** | 可 diff 的"我们向后台要过什么"的凭据；一天取几次都行 |
| 看板 | `web/`（服务版，**一个服务管多个活动**）/ `数据/看板/*.html`（单文件版） | 都只读台账库 | 两边同一个聚合实现，数字必然一致 |

**看板多活动（2026-09-28 起）**：

- 一个 `web/app.py` **管所有活动**——活动登记表在启动时由 `campaign.discover()` 扫
  `activities/*/配置/*.yaml` 建好（**能过 YAML 契约才收**：`活动定义.yaml` / `*.thresholds.yaml` /
  `判定门槛.yaml` / `调整/` 下的批次 YAML 都不收；**同任务组名撞车直接报错**，不静默挑一个）。
  页头那个**下拉**就是切换器，选过之后记在浏览器里。
- 接口一律带 `?activity=<任务组名>`（`/api/perf`、`/api/snapshots`、`/api/fetch/status`、`POST /api/fetch`），
  不给就是**默认活动**（优先挑"库里有数据的那个"，免得新活动空库时一打开是空白页）；
  `/api/activities` 给活动清单。
- **取数跨活动串行**（浏览器只有一只），但**"今天已取"的配额按活动各算一份**——给 B 取数不吃 A 的额度；
  取数流水也按活动各一份（`activities/{活动名}/数据/`）。
- 页面**只陈列数据**：分桶表原来那列「判定」（全局 0.10% 参考线）已摘掉——它跟活动的**判定门槛**
  （`配置/判定门槛.yaml` 的 `passCtr` 千三）不是一回事，两个活动同屏时容易看混；
  判定清单仍由 `judge_batch.py` 出（§9.3）。
- 方案与取舍见 `web/多活动改造方案.md`；接口与页面控件细节见 `web/README.md`。

**两个动作分工**（页面两个按钮就是这两件事）：

- **取数** = 把**昨天**的数固定下来（默认区间 = "库里最近有数据那天 ~ 昨天"，空库则从投放开始日全量回填）。
  起点取"最近有数据那天"是为了自动补洞——那天取时它还是个半截的今天，隔天重取才是终值。**一天只点一次**（昨天不会再变），页面今天取过就禁用。
- **刷新** = 刷**今天**的实时数（`--from 今天 --to 今天`，3~10 秒），**随时可点**；刷新后页面**原地保留当前选中的时间段与口径**。

两条路写同一张 `daily` 表（今天那行是**覆盖写**），先刷新后取数不会互相覆盖；**看板区间 = 库里全部日期**，不由"最新一份"决定。

**看板口径表**：

| 口径 | 定义 | 为什么这么定 |
| --- | --- | --- |
| 桶级默认「**仅在投**」 | 只算状态＝进行中的工单，可一键切「**全部**」（含已下线工单的历史） | 同一桶常有多条工单（重投 / 测试各一条），混着相加会把两个实验搅在一起 |
| 桶级「**当前批次**」（2026-10-08 改为**每桶独立**） | **该桶最后一次建批**那一批的工单（规则在 `campaign.bucket_current()`；只写了 audience、没挂资源的批次不算），**不看工单状态** | 各桶复盘节奏不一样：曝光大的桶早就跑到很后面的批次、曝光小的桶还停在前几批——"当前批次"不是全局概念（用户 2026-10-08 定）；另外新建工单在后台生成任务前 `workStatus` 是 `0`，只看「进行中」会把当前这一批**整体漏掉**（2026-09-28 发现） |
| 桶级「**文案 / 动作**」列 | 这批这桶**已经调整过**（`activities/{活动}/配置/复盘动作.yaml` 里有记录）→ 显示**调整动作**（人定的 `留谁 ｜ 下谁`）+ 一个**「调整思路」小图标**，点开弹窗看那次的说明；**没调整过** → 显示 `judging.py` 算的**建议动作**（没到门槛 = `继续观察`） | 用户 2026-09-30：「没调整的时候那就是建议动作，调整过了就写调整动作，这样方便我们后续看」——只看规则建议分不出来"这桶已经定过"还是"还没到门槛"。**长篇说明不进表格**（用户同日：「一大坨不美观」）——补几条也不进，要细节点图标 |
| **日均曝光** | 曝光 ÷ 该桶实际投放的天数；分母只数**当天有量的日子**（多工单并行时同一天算一天，**今天也算一天**） | 工单确实在跑，分子分母口径一致 |

工单明细里另有各工单自己的「日均」。页面其它控件口径（今天 / 单按钮日历 / 刷新图标 / 工单口径）见 `web/README.md`「页面控件」。

**内容写在哪（三问定）**：

1. **每次做新活动都用得上？** → 是：**规则**写本文件；**怎么让广告更有吸引力**（用户定的标准、真实踩过的坑）写 `memory/MEMORY.md`。
2. **只有这一单用得上？** → `activities/{活动名}/`（细则或活动定义）。
3. **改它的时候要不要连带改别的活动？** → 要 = 说明它放错层了，该提到通用层。

- **同一条内容只维护一份**：通用规则只放本文件，活动专属只放 `activities/{活动名}/物料/活动细则.md`；经验库只放词库与数据，**不复写规则**。
- **活动目录只记这一单**：`activities/{活动名}/`（含活动细则）只记**后台对象 / 文案 / 名单 / 日期 / 数据判断**；**工具、界面、数据层的工程变更不进活动目录**——脚本与工具写 `web/README.md`、`automation/docs/`，通用规则写本文件。
- **三个经验文档各写什么**（2026-09-24 起拆开，**别互相串**）：
  - `memory/MEMORY.md`：**怎么让广告更有吸引力**（写文案前用的规则）。没有经过用户允许、没有经过验证的内容**一律不许写**（AI 自己发明的分类 / 框架 / 数字都算）；拿不准的先放 `memory/暂缓经验.md`。
  - `memory/数据台账.md`：**只记数据**——逐条文案 ↔ 曝光 / 点击 / CTR / 结论，**好坏都记**（每次判定后回填）。
  - `memory/数据经验.md`：**只写已经验过的结论**（+ 读数据的方法）。⛔ **转正必须先问用户**（用户 2026-10-08 定），AI 不得自行把暂缓里的东西写进去；样本小的、只验过一两轮的一律放 `memory/暂缓经验.md`。
- **产出侧生成器（物料 / YAML）归 `ad_output/工具/`**；活动内容写「活动定义 YAML」，生成器不含任何活动内容（数据 / 代码分离）。
