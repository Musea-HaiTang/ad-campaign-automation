## 1. 流程总览（7 步 + 1 个持续监控）

| 步骤 | 输入        | 动作                           | 输出                   | 文档章节 |
| -- | --------- | ---------------------------- | -------------------- | ---- |
| 1  | 活动链接 + 要求 | 抓活动页、产品核查                    | 产品事实表（口述即可）          | §2   |
| 2  | 活动名       | 在 `activities/{活动名}/物料/` 建/更新 活动细则.md | 活动细则文件               | §3   |
| 3  | 目标读者      | 按搜索意图拆人群 → **过钩子闸门（每人群 2 个钩子）** | 过闸门的人群 = 最终桶          | §4   |
| 4  | 每个桶       | 写关键词（三铁律 + 竞品）               | 每桶一行关键词              | §5   |
| 5  | 桶 + 2 个钩子  | **先定类型**（①伪装博文 / ②纯营销）→ **再选风格**→ 写 3 条文案（三个角度，无对照组）→ **交付前自审（回炉循环）** | 每桶 3 条 / 回炉（含砍桶）      | §6   |
| 6  | 所有文案+关键词  | 套 HTML 模板出成品                 | `activities/{活动名}/物料/...html` | §7   |
| 7  | 你确认 OK      | 生成整活动 YAML                  | `activities/{活动名}/配置/...yaml` | §8   |
| ·  | 后台导出数据    | 监控 + 复盘                      | 复盘报告 + 下一期调整         | §9   |

**默认不读**：`automation/`、`web/`、别的活动目录（下表写明的除外）。**一次只读当前活动**，不翻别的期次当参考。

### 1.2 活动类型（先判类型再走流程 · 2026-10-12 用户定）

**桶（= 一个任务工单）从哪来，决定这个活动按哪套走。** 判类型在**步骤 1 摸产品之前**做，
判完写进 `活动细则.md` 的**第 0 项**（`_活动细则模板.md` 已带这一项）。

| 维度 | **单页活动**（旧） | **多产品活动** |
| -- | -- | -- |
| 桶从哪来 | 按人群搜索意图拆桶（§4） | **按产品拆**：一个产品 = 一个工单 |
| 每桶内容 | 人群 + 钩子 → 3 条文案 | 产品 + **3 个吸引点** → 3 条文案（一点一条；**不设**"凑不出 2 个钩子就砍桶"那道闸门） |
| 关键词跨桶 | 默认**一词只挂一个桶**（§5.2 第 3 条） | **允许同词挂多个产品工单**，只要词够精确（用户：抢词没关系，本来就有竞争） |
| 判定门槛 | 用活动自己的门槛数（§9.3） | **按该产品工单的曝光速度定**：跑得慢取约一天的量，跑得快取半天的量（半天 3,000 → 门槛 3,000） |

> **其余全部共用**：摸产品 / 活动细则 / 关键词三铁律 / 三角度文案 / 文案自审 / 物料 HTML / 整活动 YAML / 判定闭环
> ——**不另起一套流程**，正文各处只在本表这四处标注差异。
> 多产品活动的目标是**把所有产品都做一遍**（用户 2026-10-12），不设上量闸门，靠数据淘汰。

### 1.3 新增一个产品（六步 · 2026-10-12 定）

**每加一个产品都走这六步，一步不跳；产物全落在 `activities/{活动名}/` 里。**

> **开新对话加产品时，只读这三份就够**：本文件 **§1.2 + §1.3** ｜ `activities/{活动名}/物料/活动细则.md`（活动口径、命名、已建对象）｜
> `activities/{活动名}/物料/产品清单.md`（顺序、下一个上谁、每个产品的拆分结论）。
> ⚠ 执行层所有脚本的 `--config` 一律指**整活动 YAML**（`配置/{前缀}.yaml`）——**不是** `配置/活动定义.yaml`
> （后者是生成器的输入，喂给脚本会被契约校验当场拒绝，2026-10-12 踩过）。

| # | 做什么 | 产物落在哪 | 闸门 |
| -- | -- | -- | -- |
| 1 **摸产品** | 抓产品页 / 官方文档（§2 的工具与要求），核 7 列：是什么 / 形态 / 目标用户 / 卖点 / 钩子 / 竞品 / 一句话定位，含**上线或内测状态** | 追加进 `物料/活动细则.md` §2 的事实表 | — |
| 2 **关键词** | 该产品一行词：产品词 + 品类场景词 + 竞品词（§5.2 三铁律；原子化、同义多写法全留） | `配置/活动定义.yaml` 的 `buckets[]` | **停下给用户看词表** |
| 3 **圈选 + 名单** | B 路径导 CSV → 落 `数据/圈选/` + 登记 `圈选记录.md` → 建分发名单 | CSV + 后台名单 | 看数量 |
| 4 **想法池** | 攒 6~10 条候选吸引点（一句话假设 / 针对谁 / 为什么可能吸引 / 状态 / 证据） | `物料/待验证想法/{产品名}.md`（**一个产品一个文件**） | **停下给用户看想法池** |
| 5 **文案** | 从池子里挑 **3 条未验的** → 一条一个吸引点 → 走自审（§6.3） | `活动定义.yaml` 的 `copies` + `物料/文案自审/文案自审记录-{日期}.md` | 自审归 AI，用户不逐条判 |
| 6 **建批** | 物料 HTML（**只在活动首投出**）→ 生成整活动 YAML → `check_batch_plan` 离线自检 → 任务组 / 资源 / 名单 / 工单 → `check_campaign` 体检 | `物料/投放物料/`、`配置/{前缀}.yaml`、后台对象 | **YAML 停下给用户确认** |

**加新产品时的两个额外动作**（跑完第 6 步立刻做，别等到出数据）：

> **分发名单建在哪一步（2026-10-12 定）**：**第 3 步当场建**，不拖到第 6 步。
> 理由三条：① 名单名只由「前缀 + 产品名」决定、名单内容只由**词表**决定——这两样在**停下点 1** 就冻结了；
> ② 数量核对（后台计数 ↔ CSV 行数）当场能做完，不对还能赶在写文案前重圈；
> ③ 建批那天只留「生成 YAML → 自检 → 任务组 / 资源 / 工单」，不把十几万条 id 的灌入与**可能很慢的核对**
> （大名单核对会被残留浏览器拖到 ~3~6 分钟，见 `automation/docs/执行层实测耗时.md`）混进同一天。
> ⛔ 前提是**词表已过停下点、数量已点头**：没冻结就先建，词表一改名单当场作废（第一批 207061 就是这么废掉的）。
> 反过来，**建批时不用再纠结这条名单**——`run_taskorder.py` 只认名字，名字对得上就行。

1. **给新桶补 `配置/判定门槛.yaml`**：`{桶id}: {threshold: 3000, resources: 3}`（起手值，跑 1~2 天后按该工单的
   日均曝光校准，见 §9.3）。不补的话 `judge_batch` **当场报错**（2026-10-12 加的检查）——在那之前是**静默不判**：
   该桶既不进判定清单、也不会触发自动复盘。
2. **执行层只跑新桶**：`--only <产品名>`（老桶有断点账本会 SKIP，但显式指定更稳，也不会误碰已上线的老工单）。

**两个节奏**（用户 2026-10-12 定）：

- **顺序照抄腾讯云官网「产品」菜单的分类顺序**，一个个来、不跳类——这样不容易漏；清单记在
  `activities/{活动名}/物料/产品清单.md`（做完一个更新一格）。
- **一次上 2~3 个产品**：判定一轮要 2~3 天，铺太多会同时涌进一堆判定，产品间抢词的影响也看不清。
- **下一批上哪几个，AI 自己按顺序定，不回头问用户**（用户 2026-10-12：「我其实不太想去看下一批产品具体是什么」）：
  照清单顺序**从前往后取 2~3 个**（同组内先取前面的），**定完在第一个停下点（词表）里写一句"这批为什么是这几个"**——
  用户在那一步一票否决即可，不用先被问一遍。

> 第 2、4、6 步是**三个停下点**；第 1、3、5 步可以连着做完再一起给你看。

**「一个产品」的粒度（2026-10-12 定）**：官网导航里**顶格**的是产品，**带「－」缩进**的是它的**子项**
（例：`WorkBuddy Enterprise` 是产品，`WorkBuddy / CodeBuddy / WorkBuddy Managed Agents` 是子项）。

- **一个工单 = 一个顶格产品**；**子项默认不单独开单**——它是父产品工单里的一个**吸引点 / 文案角度**
  （首期就是这么干的：三个子项合成一个工单，3 条文案一条打一个子端，一轮就看得出哪个子端吃香）。
- ⛔ **判据只有一个：搜它的人和搜父产品的人，是不是同一批？**（我们的人群就是**关键词从博文里圈出来的**，
  所以落到可操作的形式 = **两边的词表重不重叠**）。**不看**名字像不像、**也不看**官网描述像不像——
  父产品的描述常是几个子能力的拼盘，子项的文本相似度反而更高（2026-10-12 实测：`教育智能批改` 对父产品
  的相似度是三个子项里最高的 0.371，但它跟文档解析的人群完全不是一批）。做法：各写 5~10 个最典型的词比一比。
- **看不清就先合**：拿不准的时候按子项留在父产品里当一个吸引点（成本低、不丢信息），跑一轮看**那一条的 CTR**——
  它自己跑赢，下一轮就**升格成独立工单**（先合、数据说话再拆）。
- 子项**升格**要满足：① 有自己的产品页；② 词表跟父产品**重叠不大**（人群明显不同）；③ 能凑出 **3 个**吸引点。
  **别为了细而细**——拆了就是两个工单抢同一批博文。
- **跨类重复陈列**的（同一个产品出现在多个类目）：**做一次**，按它第一次出现的类目算。

## 2. 步骤 1 · 摸清活动产品

拿到活动链接后第一件事——不是写词，是摸清产品底细。必查：

| 核查项      | 说明                       | 必填原因                          |
| -------- | ------------------------ | ----------------------------- |
| 产品是什么    | 一句话讲清                    | 后续所有口径都基于此                    |
| **产品形态** | **桌面程序 / 插件 / 网页 / App** | 文案用词必须与形态一致（**形态错 = 0 点击根因**） |
| 目标用户动作   | 活动要用户做什么                 | 决定转化口径                        |
| 核心卖点     | 吸引点                      | 文案角度之一                        |
| 活动钩子     | 奖励/福利                    | 文案角度之一                        |
| 竞品       | 用于拦截词                    | 挂进对应人群桶做拦截（§5.2 第 3 条）        |
| 一句话定位    | 让用户一秒听懂                  | 卷首标题                          |

> 产品形态（上表加粗那行）决定全部动作词：程序写「下载 / 开通」、网页写「打开 / 在线用」、权重写「下载 / 部署」。

> ⛔ **写文案前必须把产品 / 活动的具体细节查清**（2026-10-12 用户定）：形态、能力、目标用户、交付方式、
> **上线或内测状态**、版本与价格口径——**查不清不许动笔**，也不能拿"页面没写"当默认。
> **抓取工具**：`ad_output/工具/fetch_page_text.py <url>`（已支持 gzip 响应，腾讯云文档站可以直接抓）。
> **页面是前端渲染的**（只回标题 / 骨架）→ 换浏览器取正文：本机装了 Playwright，浏览器在 `D:\playwright-browsers`；
> ⚠ 沙箱里跑 Playwright 会被拒（创建子进程管道报 Permission denied），要提权执行。
> 活动页、产品页、官方文档都算一手来源；**一次抓不到不是"查不到"的理由**，先换工具再下结论。

## 3. 步骤 2 · 建活动细则文件

- 模板：`activities/_活动细则模板.md`（空白版，直接复制）
- **通用规则不写进细则**（拆桶/钩子闸门/三铁律/复盘标准都在本文件），避免重复维护

## 4. 步骤 3 · 分人群桶

**拆桶方法**：从产品价值倒推目标读者 → 按"会搜什么 / 会读什么"拆桶。

> ⛔ **不套用别的活动的分桶表**：桶必须从**本活动**的产品价值倒推，一个活动一套分桶。原「7 类基准」表已删除——照抄别的活动的分桶，会导致为了凑够桶数去写没有钩子的文案。

**判断标准（拆桶）**：**两个条件都满足才建桶**——
1. 两类人「会搜的词 / 会读的文章」差异大（差异小就合并）；
2. 这个人群**能凑出 2 个不重复的强钩子**（见 §4.1）——凑不出就不建桶。

**桶数**：由通过钩子闸门的人群数决定，**不预设 4-7 类**（4-7 只是经验区间）。物料模板已按此改造：模板里只有一个桶块，`gen_material.py` 按桶数复制 N 份 → 任意桶数都能直接出物料。

> ⚠ **多产品活动不走本节**：桶 = 产品，一个产品一个工单，**没有钩子闸门**——每个产品在想法池里凑 **3 个吸引点**
> （一点一条文案），凑不出就换下一条未验的想法（见 §1.2、§6.1）。

### 4.1 钩子闸门（决定桶数，夹在「分人群」和「写文案」之间）

**钩子 = 能让这个人群点进来的那句话**。只有参数、文档、排名、许可这类**事实不算钩子**——它们是"素材"，可以垫在描述里，不能当标题。

每个候选人群列 **2 个钩子**，两条必须回答**不同的读者问题**。判据只有一句：**这个人群凭什么点？**（说不出具体的人、说不出他能拿到什么 = 不是钩子）

- 凑不出 2 个 → **砍这个人群**，不硬凑文案。
- **钩子不得跨桶复制，素材可以复用**：同一条产品事实对不同人群可以是两个不同的钩子（"与 GLM-5.2 同基座、全靠后训练"→ 对 AI 编程人群是"能力涨了 50%"，对后训练人群是"重训底座太贵，这条路不用重训"）。

**核心公式**（复盘要用）：`曝光 = 圈选人数 × 展现率`，`点击 = 曝光 × CTR`。底部位置 CTR 极低、统计意义弱，曝光和展现率才是主要抓手。

## 5. 步骤 4 · 写关键词（每类一行，英文逗号分隔）

> ⚠ **什么时候圈：A 路径固定下午**（用户 2026-09-21 跟后台技术人员确认）。那边数据集**每天上午还在写入、一般中午才写完**，
> 同一套词**早上圈出来的数偏小**（实测同款 58 词：10:2x = 7,816 → 11:0x = 67,207，差 8.6 倍）。
> **A 路径的圈选与看数一律安排在下午**（**B 路径不受此约束**，见 §5.1 两路径表下）；判断**只看「日均曝光(预估)」**，
> 能圈多少博文只作参考。详见 §5.1、§9.4。

### 5.1 关键词怎么圈到博文（后台能力）

圈选任务 = **关键词博客ID圈选任务**：圈的实体是**博文**，不是人。关键词拿去跟博文的**四个字段**比对，**命中任一即可**：

| 匹配字段 | 说明 |
| --- | --- |
| 博客 landing 词 | 站外点进这篇博文时带的词 |
| 博客描述 | 博文摘要 |
| 博客标题 | 博文标题 |
| 博客标签 | 博文标签 |

命中哪批博文就圈哪批博文，**人是从博文倒推的**（作者 + 读这些博文的人）。所以判断一个写法行不行，**唯一标准是：这个词能不能匹配到博文**。

- 「idf分析与总数预估」读出的**预估圈选总数** = 这行词能匹配到多少篇博文；同一页面给出的 **idf 值**（如 `python: 2.78`）**我们不解读、不参与判断**。
- **「预估圈选总数」不等于曝光**：它数的是**博文ID的个数**，不区分这篇博文有没有流量。「曝光阈值」才是那个筛子——`曝光≥1` 只收「历史上被展示过」的活博文，`曝光=0` 会把零展示的僵尸博文也算进来充数（池子大 2.2~24 倍，日均曝光反而低 2.8~11 倍）。**所以阈值永远用 1，量不够靠加词**，见 §8。
- **什么时候圈：A 路径固定下午**（用户 2026-09-21 跟后台技术人员确认）：那边的数据集**每天上午还在写入，一般中午才写完**，所以同一套词**早上的数偏小、下午才稳定**（实测同款 58 词：10:2x = 7,816 → 11:0x = 67,207，差 8.6 倍；且数据集**时刻都有写入，只是上午写入多**）。**A 路径的圈选与看数一律安排在下午**，别拿早上的数做判断（B 路径不受此约束，见下）。
- **长尾场景句进不了词表**（如"如何用 Cursor 配置 Python 环境"）——这种句子不会出现在博文的 landing 词 / 描述 / 标题 / 标签里，等于空跑。
- 后台另有一套**圈人**口径（搜索词 / Landing 词 / 相似任务），**本流程不走**（我们圈的是博文）——存档在 `../../automation/docs/run_audience.md` 末尾。

**两条并列的圈选路径（2026-09-21 起）—— 用哪条先问用户，AI 不自行选**

| | **A · 后台圈选用户**（旧，9/14 起） | **B · 数据平台圈选博文**（新，2026-09-21 跑通） |
| --- | --- | --- |
| 入口 | 广告后台 `3.圈选用户 → 博文圈选任务` | `data.csdn.net`（Data BI）对话式取数 |
| 脚本 | `run_audience.py`（建客群）+ `run_distribution.py`（一键建名单） | `run_selection.py`（导出 CSV）→ `run_distribution_ids.py`（用 id 建名单）——**两条命令分开，中间人工看数量** |
| 关键词来源 | 活动 YAML 的 `keywordGroup.keywords` | 同一份词表 → 拼进「口径提示词」发给对话 |
| 过滤口径 | 后台阈值（曝光锁死 1 + 点击≥X，见 §8） | 提示词里写死：`status=1` + `last_30_days_pv>1` + 六个字段 `multiMatchAny` |
| 达标读数 | 后台「博文圈选任务」列表的**日均曝光(预估)**（§9.4 的唯一判据） | CSV 只给**博文数 / 总点击数 / 平均点击数**，**没有曝光**；要测曝光得先建名单→建工单→跑起来看 |

| 现状 | 在用 | 跑通待评估：**用户要先测它的曝光高不高**，测完再定这条到底留不留 |

- **这次走哪条：先问用户**（两条并列保留，AI 不自行挑）。问法就一句："这次圈选走 A（后台）还是 B（数据平台）？"
- **时点只约束 A 路径**（§0「圈选时点」）：A 要等下午；**B 路径（数据平台导 CSV）随时可导、不用等下午**（用户 2026-09-29 定，取代原「B 的 CSV 也一样」的推断）。
- B 的坑（都已在脚本里处理）：平台「全局记忆」不可靠 → **每次必须整段发口径提示词**；导出的文件没扩展名、是无 BOM 的 UTF-8 → 落盘补 `.csv` 并转 UTF-8 带 BOM；平台返回的 filename 主题词由模型现起，本地文件名脚本自己拼。
- 文档：`automation/docs/run_selection.md`（圈选导出）、`automation/docs/run_distribution_ids.md`（用 id 建名单）。

### 5.2 写作三条铁律

1. **原子化**：复合短语拆成**原子词**，每个原子词单独成词。关键词是拿去匹配**博文**的（圈选任务 = 「关键词博客ID圈选任务」），短语越长命中的文章越少——拆开才会命中更多博文。例：`RAG 检索增强` → `RAG`、`检索增强`；`AI 代码生成` → `AI代码`、`代码生成`。
   - **止拆线**：拆出来的原子词必须**单独就能指向目标人群**；拆到泛词就停（`检索`、`增强`、`AI`、`编程` 单独拎出来会圈进大片无关博文，不保留）。**伞词**（`AI大模型`、`大模型`、`开源大模型` 这种什么都沾一点的）同样不进词表——它对哪一类人都不精准，只会把博文池稀释掉；真要拿它拉量，也**只能挂一个桶**。
   - **拆完要验收**：池子变大 = 人群变泛 + 展现率被稀释。所以拆完**跑一次圈选看人数**，越界按 §8「圈选越界处置」处理；远超上限就回退（收回原子词，或换回更精确的词）。
2. **同义多写法全保留、同时投**：同一概念的另一种叫法要全列——缩写 / 全称（`RAG` / `检索增强` / `检索增强生成`）、中 / 英、大小写（VS Code / vscode / Visual Studio Code、智能体 / agent / Agent、Codex / codex）。
3. **竞品词挂进已有桶，不单独建桶**（见 [`决策台账.md`](决策台账.md)）
   - **判据**：换位成搜这个词的人——他是在找本产品这类东西，还是在找它能替代的东西？是后者才拦。
   - **归属**：追加到**对应人群桶**的关键词行里，作为拦截子集；**默认一词只挂一个桶**——关键词的单位是**博文**，同一个词 = 同一批博文被两个工单争同一个 T0 位，桶间数据也会互相污染。**多产品活动例外**（2026-10-12 用户定）：按产品拆的工单**允许同词重复**，只要词够精确（用户原话「有词相同是没关系的，只要精确就可以」）——见 §1.2。
   - **优先合桶**：如果一个词在两个桶里都是主角，先问「这两个桶是不是同一批博文」——是，就合成一个桶（两套钩子放进同一个桶的对照 / 实验组），而不是把词挂两遍。
   - **跨桶是例外，发生了才记一句**：确有必要同词多桶时，在活动细则里**一句话**注明「X 词同时挂 A、D 桶，复盘不比这两桶 CTR」；**没发生就不写**。同理，词不重复也会有博文同时命中两个桶（一篇"部署 + 微调"的文章），这类重叠消不掉，只能记录 + 合并观察。
   - 品类词库示例（攒词用，不绑活动）：AI 编程类 = Cursor / GitHub Copilot / 通义灵码 / Claude Code / Codex；可下载自部署类 = DeepSeek / Qwen / Kimi / Llama；闭源旗舰类 = Claude / GPT-5 / Gemini。

### 5.3 输出格式

每类一行英文逗号分隔的关键词（直接整行贴后台）：

```
{A 类}: {关键词1}, {关键词2}, {关键词3}, ...
{B 类}: {关键词1}, {关键词2}, ...
```

每类下方附一行"写法数 · 关键说明"（如「25 个写法 · 竞品拦截 6 个」）。

### 5.4 4 个核心实体（后台对象）

- **任务组** = 顶层容器，1 个（命名 `品牌+负责人-`）
- **资源** = 文案素材（每条 = 标题 + 描述 2 行）
- **客群** = 关键词圈选的一组用户（每类 1 个）
- **任务工单** = 资源 + 客群绑定（每类 1 个工单，工单内挂 3 资源）

**结构约束**：1 人群 = 1 任务工单 = 1 客群 × 3 资源（对照 34 / 实验1 33 / 实验2 33，**流量均分 1/3**）。**每个桶必须交满 3 条文案**——3 条打的是同一批人，是**并列的三个角度**、没有对照组（见 §6.1；资源名里的「对照 / 实验1」只是后台槽位的固定叫法，不是文案口径）。
> 命名（桶 / 资源 / 客群 / 工单 / 物料）见 §7.3；名字的唯一实现是 `../automation/scripts/naming.py`。

## 6. 步骤 5 · 写文案（每桶固定 3 条）

### 6.1 动笔前想清楚角度（不再"选风格"）

**「文案风格」这个概念已取消**（2026-09-28 用户定）：不再有"写文案前先选一种风格"这一步，也没有「默认风格」了。
`文案风格/用户痛点版.md` 只作**参考**——里面那套句式规则（「想让 X，就 Y」「承接词」…）是 AI 从实验里提炼的，
**不是用户定的规范**，想借鉴就借鉴、不想用就不用，**别当模板套**。

**动笔前先有「待验证想法池」，文案从池子里挑，不现攒**（**2026-10-12 用户定 · 所有活动通用**）：

- **一个产品 / 一个活动一个文件**：多产品活动 = `activities/{活动名}/物料/待验证想法/{产品名}.md`（**一个产品一个文件**）；
  单页活动 = `activities/{活动名}/物料/待验证想法.md`（一个活动一个文件，内部按桶分节）。
- **一条想法 = 一个吸引点假设**，四个字段：**一句话假设 / 针对谁 / 为什么可能吸引 / 状态**；
  状态只有三种：`未验` / `已验有效` / `已验无效`，验证后**回填证据**（批次号 + 曝光 / 点击 / CTR）。
- **写文案时**：从该产品（或该活动）的想法池里挑 **3 条未验的**，**一条写一条文案**——正好对上"一个工单三条资源"。
  池子里没有的角度 → **先记进池子**再上，不临时加塞。
- **复盘时**：把结论**写回想法池**（哪条有效、哪条无效、证据），**旧结论不删**。
  为什么这样更快：一个工单里三条资源打的是**同一批人**，CTR 高下**直接对应三个吸引点**，不用再推断；
  验过的无效点也不会重复踩。
- 想法池是**候选**；连续 2~3 轮成立才升级成结论（升级规则见 §9.3、§11.2）。

**两种风格共同的结构**（后台 `abGroups` 三组，权重 34/33/33 均分）：

- 三条 = **同一个人群的三个角度（= 三种钩子）**，**一条文案对应一个**（2026-09-22 用户定）：
  **就找三种不同的角度，每种写一条**——不绑 §4.1 闸门那两个钩子，也不硬凑；
  角度之间**痛点不同**，不是同一件事换词说三遍。
- **没有对照组**（2026-09-22 用户定）：不再有一条"基准"或"陪跑"，**三条都得有钩子**。
- **横读**：三条摆一起要看得出是**三种不同的说法**。
- **还要定"类型"**（2026-09-24 用户定）：① 伪装成推荐博文 / ② 纯营销类，规则见 `文案风格/两种文案类型.md`；
  **不再要求"同一批里两种都要有"**（**2026-10-09 用户定**：大赛 / 活动宣传这类，**②型更直接、效果可能更好**，
  后续复盘不用为凑类型补写 ①型）。类型是叠在角度上的第二个维度，不替代角度；要验类型本身，
  **整批都用同一种**，别一条一条混着试。
- **写之前先看暂缓经验的"验证队列"**（**2026-10-09 用户定**：「我们之后的复盘也是这样，逐步测试验证我们的猜测，
  这个记录下来，我们以后复盘就这样做」）：**每一轮的文案 = `memory/暂缓经验-{产品类|大赛类}.md` 里排队的那几条候选**，
  不是现攒新角度。三条规矩：
  1. **一个槽位挂一个变量**：每条文案在复盘报告里写明「它测的是暂缓经验的哪一条」；
     想写一个池子里没有的角度 → **先把它记进暂缓经验**（连同"怎么算验证通过"），下一轮再上。
  2. **一轮只干净地验一个变量**：同一个角度不占两个槽位（见 `memory/数据经验.md` §1.2）；
     幸存条继续跑 = 当**锚**用，不算新变量。
  3. **按队列顺序排**：队列见那两份文件的"验证队列"一节；本轮没轮到的桶不许插队（到门槛的桶优先拿池内条目）。
  复盘时按每条的「怎么算验证通过」回填结果——累计够了才转正，**转正必须先问用户**（§11.2）。

### 6.2 写作底线

- **只正向陈述自家卖点**，不拉踩、不影射同行；对比只引官方同表数据，不写结论式贬低。
- 动作词必须与真实产品形态一致（形态错 = 0 点击，见 §2）。
- **纪律只有两层、不要扩写**——全局红线 + 活动特例（内容见 §0，活动特例写 `活动细则.md`）；不要写"AI 自己提炼的纪律"。

### 6.3 交付前自审（必过 · 规则见 `文案风格/文案自审.md`）

**每条文案定稿前都要走一遍**（2026-09-24 用户定：「以后每次你都这样做」）——判据清单（含 2026-10-12 加的「凭什么是你」差异关）、回炉循环、
交付时要展示的「初稿 → 卡在哪 → 改写 → 定稿」全过程，规则全在 `文案风格/文案自审.md`，本节只留核心三问。

> **落盘位置**（用户 2026-10-09 定）：回炉过程写进 `activities/{活动名}/物料/文案自审/文案自审记录-{日期}.md`
> （独立文件，按老先例）；**复盘报告只列定稿**（标题 / 摘要 / 飘红 / 动作），两处不重复。

把自己当成**那个刚读完文章、只剩几秒的人**——你只有很少的时间抓住他。

1. **他会停下来看吗？**（**2026-09-30 用户定的第一关**：站在**目标人群**视角看这条对他有没有吸引力——
   扫读位上是**曝光 → 停下来看 → 点击**，**停不下来就没有点击**；说不出"他扫到哪个词会停" = 没过）
2. **谁会点这条？**（说不出具体的人 = 这条没钩子）
3. **扫一眼看得懂吗？**（读着累、要停下来换算、或者记不住 → 重写）

**桶级回退**：某个桶凑不出**三种角度（三种钩子）** → 回 §4.1 砍掉这个人群，**不要用换词凑数**。
（**多产品活动**：不砍产品，换成想法池里**下一条未验的吸引点**——见 §1.2、§6.1。）

**分工（2026-09-24 用户定）**：写文案阶段 AI 按自审定稿即可，**用户不再逐条判断文案**——
他只在这条**特别中意 / 特别不认可**时才提出来，其余一律以点击数据为准。

## 7. 步骤 6 · 产出投放物料 HTML（**只在活动首投出** · 2026-10-09 用户定）

### 7.1 模板与文件位置

### 圈选越界处置（默认策略）

`run_audience.py` 圈选时某桶预估总数超出默认区间 `[10000, 200000]`（越界，脚本 mark `warn`）：

- **曝光阈值锁死 1**（用户 2026-09-21 定：「日常就设置曝光1，然后博文数量越多越好，这样曝光就会大」）。搜索旋钮只剩**点击需≥X**：超上限时升点击收缩；**低于下限时不动阈值**——那是词不够，去改词加词。
  - 为什么不再碰曝光：**曝光=0 是虚池**——池子大 2.2~24 倍，日均曝光反而低 2.8~11 倍（9/14 五桶对照 + 9/21 后台实测两条：12,370 篇→7,757 曝光，300,000 篇→5,130 曝光）。详见 §5.1。
- **默认**：直接用 `--tune` 处理（脚本超上限时升点击、重跑分析、读新总数，取第一个 ≤上限且 ≥下限的组合，写 `thresholds.yaml`，不创建）。
- **低于下限**：标记 `needs_keywords` 并**通知用户改词**，不硬选（规则见 [`决策台账.md`](决策台账.md)）。
- **不逐次询问**：此为用户既定偏好，不必每次向用户确认；跑完把结果**通知用户**即可（哪桶越界、调优后的点击阈值、最终圈选总数、是否仍 `needs_keywords`）。
- 若 `--tune` 后仍无法落入区间（整数阈值跳变、掉到 <下限），脚本会标记 `needs_keywords` 建议改词——这种才需要同步用户。
- 默认阈值：点击需≥`0`、曝光需≥`1`（固定）；**圈选总数下限默认 `25000`**（≈ 保底 1 万日均曝光，2026-09-21 由 1 万抬高）、上限 `200000`；区间可由 `--min-count/--max-count` 调整。

### 9.1 监控频率

> **运维配置明细（心跳 rrule、触发条件、去重、落点对话、回复格式、排查史）已归
> [`../../automation/docs/巡检与自动复盘.md`](../../automation/docs/巡检与自动复盘.md)**（2026-10-09 整理）。
> 本节只留**监控节奏本身**：

- **自动巡检**：Codex 定时任务每小时整点（时段 10:00–18:00）**只读台账库**出判定清单与建议
  （`judge_batch.py --write --todo`）；**它不自己取数**，取数归看板服务。没到门槛就继续等，够了就出可判结论（§9.3）。
- **活动收尾后不再跟**（2026-10-12 新增，同日补了补数窗口与"整批跳过"）：投放结束的活动在**活动根下放一份 `已结束.md`**（收尾标记，首例 `activities/火山引擎MediaKit/已结束.md`），标记正文里**必须有一行 `收尾日：YYYY-MM-DD`**——看板读它算补数窗口。见到这份标记：**自动巡检**整个跳过它（不跑判定、不刷待办、不触发复盘，状态行也不占行）；**看板**在「收尾日 + 2 天」内仍自动补数（后台数据回传有延迟，收尾那天先取到的是半截值），过了窗口才彻底停，并且**整批「刷新 / 取数」一律跳过它**（免得它一失败把整批拖成"0 成功 N 失败"、看不出到底是谁出问题）——要看 / 要补就切到它单独点「取数」。门槛配置与历史复盘原样留着；想恢复判定，删掉这份文件即可。
- **到门槛自动起复盘对话**：**触发条件只有一个 = 某桶累计曝光 ≥ 门槛**（不看点击）；
  同一活动 + 同一桶**当天最多起一次**；**一轮一条对话**装下本轮所有到门槛的桶，用户就在那条对话里接着走下一步。
- **通知每次都发**，格式只留三块（要你动手 / 提醒 / 状态）。
- **看板服务自动刷新数据新鲜度**：每 30 分钟刷「今天」，每天第一次先「取数」把昨天的终值固定下来；
  不配开机自启。
- ⚠ **浏览器只能被一个进程用**：巡检不取数、命令行脚本要用浏览器时**先把看板服务停掉**，跑完再起回来。
- **判定按曝光触发，不看天数**：工单**累计曝光**攒到本桶门槛才判——曝光快的桶几小时一轮，慢的 1~2 天一轮。
- ⛔ 旧的"投放期 7-14 天、避免冷启动期下线"已作废（属于旧机制）。

### 9.3 判定闭环（2026-09-24 起）

> **这套机制是通用规则：所有活动都按「曝光门槛触发判定」走**（用户 2026-09-28 明确）；
> 门槛**数值**按各活动自己的曝光数据确定（下表那组是火山引擎MediaKit 实测出来的，别的活动不照抄）。

**巡检（每 2 小时自动跑）**：取今天实时数 → 出判定清单。

```powershell
.venv\Scripts\python.exe -u automation/scripts/fetch_perf.py  --config activities/{活动名}/调整/{批次}.yaml --from 今天 --to 今天
.venv\Scripts\python.exe -u automation/scripts/judge_batch.py --config activities/{活动名}/调整/{批次}.yaml --write
.venv\Scripts\python.exe -u automation/scripts/visualize_perf.py --config activities/{活动名}/配置/{品牌}{负责人}.yaml
```

> 判定清单落 `activities/{活动名}/数据/判定/{日期}_{批次}.md`（追加）和 `待办.md`（覆盖，一眼扫）。
> 也可以在 `web/` 看板页上点「取数」——等价于跑上面第一条（增量）。
> 取数**默认只补增量**：从"库里最近有数据那天"取到今天（正常 2 天；中间断过会自动补洞；
> 空库则从投放开始日全量回填）。补历史 / 修后台改过的数：加 `--from/--to`，幂等、随便重拉。

**判定表（一个结论对一个动作）**：

| 工单累计曝光 | 点击 | 结论 | 动作 |
| -- | -- | -- | -- |
| < 本桶门槛 | — | 未到门槛 | 继续观察，什么都不做 |
| ≥ 门槛 | **实际点击率 ≥ 千三**（点击 ÷ 曝光 ≥ 0.3%） | **达标** | 该桶**停测试**：只留点击集中的那一条作长期单 → 做法见下方「**达标 → 转长期单**」 |
| ≥ 门槛 | 有点击但 < 千三 | 未达标 | 有击的留下（3 资源桶最多留 2 条、2 资源桶留 1 条，**按点击多的优先；点击并列时比点击率**，见下），零点击的下线；**幸存 + 新文案**凑满下一轮 |
| ≥ 门槛 | 0 | 全不合格 | 整批换新文案（条数 = 该桶资源数） |

**门槛**（用户 2026-09-24 定，A 于 2026-09-29 调高）：**A 3,000**（3 资源）｜ B·C·E 1,500（3 资源）｜ **D 1,000（2 资源，50/50）**；
换算成"每条文案"≈ 500 曝光（B·C·E / D）~ **1,000（A，2026-09-29 由 2,250 调上来，对齐这条标尺）**。
> **多产品活动**：门槛**按该产品工单自己的曝光速度定**（用户 2026-10-12 定：「如果曝光比较少，那就是一天的量左右，
> 如果曝光很多，那就按照半天，比如说半天有 3000 的话，那就按 3000 来」）。三步，缺一步都会卡住：
> ① **先建文件**——`activities/{活动名}/配置/判定门槛.yaml` **必须存在**：`judge_batch.py` 找不到它直接
> `SystemExit`，判定与自动巡检对整个活动**失效**（不是跳过，是报错退出；2026-10-12 首投当天踩到）。
> ② **起手值**用通用标尺：3 条资源 → `threshold: 3000`（= 每条约 1,000 曝光，与火山/KIRO 同一把尺），先让链路跑起来。
> ③ **用实测校准**：投放 1~2 天后算该工单的**日均曝光 D**——`D/2 ≥ 3,000` → 门槛取**半天量**（就近取整）；
> 否则取**一天量 D**（一天都不到标尺说明池子太小，门槛照一天量写，同时去考虑加词）。
> ⚠ **达标线算的是实际点击率**（用户 2026-09-30 定）：门槛只管"**什么时候开始判**"；
> 达标击数 = **当次实际曝光 × 千三（向上取整）**，**不是"门槛 × 千三"那个固定击数**——
> 曝光跑过门槛之后两者会脱钩：KIRO 一批 E 桶 **9,039 曝光 / 9 击 = 0.10%**，按固定击数（3,000 × 千三 = 9）
> 会被判「达标」，按实际点击率是**未达标**（9,039 曝光要 28 击才到千三）。
> 参照值（曝光**正好压在门槛**时的击数）：A 9 ｜ B·C·E 5 ｜ D 3。
> ⚠ **点击并列时按点击率**（用户 2026-10-09 定）：以前并列时保持读数原始顺序，等于让后台列表顺序替人做决定——
> 真事：火山 A 桶九批 **对照 1,350 曝光 / 1 击 = 0.07%** 与 **实验1 1,306 曝光 / 1 击 = 0.08%** 点击打平，
> 结果留了点击率更低的对照。现在并列时比**点击率**（再并列比曝光），最高那条留下。规则本体仍是 `judging.py` 一处。

**两条纪律**：

1. 后台**只能整单下线**（单个资源下不了）→ 实际动作是"幸存资源 + 新文案建新工单（批次号 +1）→ **新批上线后**再把老工单下掉"（先下会断流）。
2. **批次号每轮 +1**（当前 -6，下一轮 -7），一眼看出第几批。

**达标 → 转长期单（2026-10-12 定 · 首例 KIRO D 桶）**：某桶**单条资源级 CTR ≥ 千三**时，该桶**停测试**，
把那条转成**长期单**——不再跑 AB、不再补文案、**退出测试轮换**（判定脚本会显示"达标"）。五步，一步都别跳：

1. **写配置**：新建 `activities/{活动名}/调整/{日期}-{桶}长期单.yaml`（复用整活动 YAML 契约，但**它不是一次批次实验**）：
   `taskOrder.abTest: **false**`（缺省 `true` = 老的三组 AB 路）｜ `audiences[].resources: []`（**不重建资源**，复用后台那条现成的）｜
   `audiences[].abGroups` **只写 1 条**（`label: 对照组` + 那条 `resource`）｜ `nameSuffix: '-长投'`（工单名 `…{topic}-长投`；**桶名本体不带后缀**）｜
   `distributionList` 复用本桶现成名单；`price` / `deliveryDate` / `exposureCaps` 按当期问用户。
2. **离线自检**：`check_batch_plan.py --config <这份 YAML>`——单资源模式**不校验权重 / 位次 / 角色段**，只卡"正好 1 条 + 写了资源名"。
3. **彩排**：`run_taskorder.py --config <这份 YAML>`（**要用浏览器 → AI 先停看板服务**）。看三样：
   `AB测试: 否（单资源）` ｜ `[资源] … ✓`（回读一致）｜ 步骤结果里 **`资源=ok`**。
4. **提交 + 体检**：加 `--submit` → 回读命中完整工单名；再 `check_campaign.py --config <这份 YAML> --only order`
   （⚠ **别查 ads**：复用的是老资源，资源页默认创建时间窗会假报缺失）。
5. **收尾**：新单审核通过、跑起来之后**再下线该桶老工单**（先上后下，别断流）；该桶**从此不进批次 YAML**。

> 后台形态（2026-10-12 真机勘察，脚本 `automation/_tmp/_probe_no_ab.py`）：那个开关**默认就是「否」**；

> 字段契约见 `automation/campaigns/README.md`，执行细节与踩过的坑见 `automation/docs/run_taskorder.md`。

**定下一轮文案的口径**（**2026-10-08 用户定**，取代 2026-09-29 那版"每轮留 1 条锚"；**2026-10-12 收紧小改预算**）：
每个槽位按**上批读数 + 这个槽位小改过没有**挑一个动作——

| 上批情况 | 动作 |
|---|---|
| **单个资源级 CTR ≥ 千三** | **别动，原样保留**（它就是长期单候选）——**优先级最高**，不管它小改过没有 |
| **0 击** | **重写**：换角度（不是换词） |
| **有点击、没达标**，且这个槽位**还没小改过** | **小改**：同角度优化表达 / 文风，或加上飘红试一次；**不整条换掉** |
| 小改过、**点击率涨了** | **可以继续小改**（说明这个方向还在往上走） |
| 小改过、**点击率没涨 / 还是没达标** | **重写（换角度）** |
| 用户点名的 | **原样保留**（一个字不改）——这是例外，不是常规动作 |

- ⛔ **没有"锚"这个概念了**（2026-10-08 用户定）：旧的"每轮留 1 条完全不动当内部对照"跟上面这条规则冲突，已删。
  同批对照改成靠**同一条文案的小改前 / 小改后**——所以台账必须记 `lineage`（`实验1-2 → 实验1-9（小改：…）`）。
- ⛔ **小改的预算按"点击率涨没涨"算**（**用户 2026-10-12 定**，同日两次口述合并成这一条）：
  ① 第一次"有击没达标" → **留下、小改一轮**；② 小改后 **CTR 涨了 → 可以继续小改**；③ 小改后 **CTR 没涨（或还是没达标）→ 换角度**。
  ④ **例外（优先级最高）：单条资源级 CTR 已经 ≥ 千三 → 一个字别动**——它是长期单候选，不参与"该不该换"的讨论。
  被这条取代的旧口径："三条都可以小改、不强制留槽位写新角度"（2026-10-08，已作废）。
  起因（真事）：KIRO E 桶对照线连着 3 轮小改（四批 0.147% → 五批 0.123% → 六批 0.069%），**CTR 一路往下**——
  它该在第 2 轮就换；反过来，涨的那几轮（就像 A 桶对照 0.092% → 0.122%）才值得再给一次。
- ⛔ **小改要动钩子层，不是只顺句子**（用户 2026-10-12：「我感觉你的小改很粗糙」）：做法见
  [`文案风格/文案自审.md`](../../ad_output/文案风格/文案自审.md) 的「小改怎么做」——只改标点 / 补时间 / 去公文词的属于**顺句微调**，
  **不消耗小改预算、也不算验过一轮**；一次真正的小改必须动"他会停下来的那个词"。
- **小改在后台 = 新建资源**：后台不能改已上线资源的文案（用户 2026-10-08 确认），所以小改 = 新建资源 + 新工单、老工单下线；
  和"重写"在执行上一样，区别只在**文案改了多少**，靠 lineage 认祖先。
- **"涨没涨"的样本下限 = 该桶工作日一天的曝光量**（周末和节假日不算——用户 2026-10-08），没攒够就继续观察。
  实测参考（工单级一天）：火山 A ≈3,018 ｜ B ≈598 ｜ C ≈857 ｜ D ≈297 ｜ E ≈706；KIRO A ≈4,279 ｜ B ≈808 ｜ C ≈1,789 ｜ D ≈1,852 ｜ E ≈6,466。
- **每条新文案必须挂一个明确的存疑项**（挂不上就不写）；同一个判断**连续 2~3 轮成立**才从"存疑"升级成结论
  （存疑账在 `memory/暂缓经验-产品类.md` / `memory/暂缓经验-大赛类.md`——**按广告类型分家**；
  **转正进 `数据经验.md` 前必须先问用户**——用户 2026-10-08 定）。

### 9.4 圈选达标口径 + 基线（2026-09-24 回填）

**达标口径（博客页 T0）**：**「日均曝光(预估)」目标 ≥ 20,000、底线 ≥ 10,000**（用户 2026-09-21 定，取代 9/14 的 5,000；**越多越好**）。

> （同一列表里比值 0.2~5.7 都有）。所以**不要用"圈了多少博文"当达标依据**——建完读曝光，才是判据。

**这个数在哪读、什么时候读得到**（2026-09-21 探针确认）：

- **位置**：后台「圈选用户 → **博文圈选任务**」列表的四列 —— `实际圈选博客ID数` / `日均点击(预估)` / `日均曝光(预估)` / `日均pv(预估)`（筛选框 = `请输入圈选任务名称`）。

**试圈流程（2026-09-21 起）**：下午先 `run_audience.py --submit --name-suffix=-试圈 --min-count 1000` 建一版
（**不动正式客群名、不占正式账本**）→ 看「日均曝光(预估)」→ 达标就删掉试圈的、用正式名建；不达标就改词重来。
命令见 `automation/docs/run_audience.md`。
> **建前预估 = 建后实际**（2026-09-21 五桶逐桶验证：弹窗里的「预估圈选总数」与列表里的「实际圈选博客ID数」**完全一致**）——

**经验比例**（曝光≥1，只看本活动）：`日均曝光(预估) ≈ 实际圈选博客ID数 × 0.33~0.63`

> `74,342 篇 → 426,266 曝光`（×5.7）——比值从 0.2 到 5.7 都有，**别拿比例反推圈选数**，以实际读数为准。

### 9.5 数据落在哪（三层：取数 → 台账库 → 看板）

**三件事分开**，看板只读库（`activities/_db/投放数据.db`，SQLite，标准库零依赖）：

| 层 | 位置 | 谁写 / 谁读 | 关键性质 |
|---|---|---|---|
| **台账库（唯一真相）** | `activities/_db/投放数据.db` | `fetch_perf.py` 写 / 看板数据装配读 | 按天事实按 **(工单, 日期)** upsert；资源读数**每次取数追加一条** |
| 取数流水（原始存档） | `activities/{活动名}/数据/{时刻}[_标签]/` | `fetch_perf.py` 写，**没人读** | 可 diff 的"我们向后台要过什么"的凭据；一天取几次都行 |
| 看板 | `web/`（服务版，**一个服务管多个活动**）/ `数据/看板/*.html`（单文件版） | 都只读台账库 | 两边同一个聚合实现，数字必然一致 |

**看板多活动（2026-09-28 起）**：一个 `web/app.py` **管所有活动**，页头下拉切换；活动登记、接口参数
（一律带 `?activity=`）、取数串行与"今天已取"的配额、页面只陈列数据（判定那列已摘掉，判定清单仍由
`judge_batch.py` 出）——**细节见 [`web/README.md`](../../web/README.md) 的「多活动」「接口」两节**；
方案与取舍见 `web/多活动改造方案.md`。

**两个动作分工**（页面两个按钮就是这两件事；**2026-10-09 用户定：两个都改成一次跑全部登记的活动**——
浏览器只有一只、取数本来就串行，分开点不会更快，而「待复盘」角标是跨活动的，只刷一个活动它必然半新半旧；
顺序 = 当前看的活动先跑）：

- **取数** = 把**昨天**的数固定下来（默认区间 = "库里最近有数据那天 ~ 昨天"，空库则从投放开始日全量回填）。
  起点取"最近有数据那天"是为了自动补洞——那天取时它还是个半截的今天，隔天重取才是终值。**一天只点一次**（昨天不会再变；配额**按活动各算**），
  页面**所有活动都取过**才禁用；只取过一部分时仍可点，会把还没取的活动补上。
- **刷新** = 刷**今天**的实时数（`--from 今天 --to 今天`，3~10 秒），**随时可点**；刷新后页面**原地保留当前选中的时间段与口径**。

两条路写同一张 `daily` 表（今天那行是**覆盖写**），先刷新后取数不会互相覆盖；**看板区间 = 库里全部日期**，不由"最新一份"决定。

**看板口径表**：

| 口径 | 定义 | 为什么这么定 |
| --- | --- | --- |

### 11.1 按寿命分三类（2026-10-09 用户定）

> 起因：文档越攒越多、同一事实好几份、正文里历史和新规混着。回头看犯过的那些错
> （文件级清单副本失真、`待办.md` 停摆、圈人机制长进写文案的经验池里）——**全是同一类错：内容放错了层**。
> 所以先按**寿命**分类，不按主题分类；每条内容只归一类。

| 类别 | 寿命 | 只准写什么 | 本项目的文件 |
| --- | --- | --- | --- |
| **规范 / 契约** | 少变，改要慎重 | **现在该怎么做**；⛔ 禁止写历史过程 | 本文件、`automation/campaigns/README.md`、`automation/docs/*.md` 的说明书部分 |
| **存档** | 只增不改 | **什么时候、为什么这么定**；⛔ 禁止写"现在该怎么做" | `流程文档/决策台账.md`（本文件 §12 已搬出去）、`memory/数据台账.md`、`activities/{活动名}/物料/复盘/`、`automation/docs/执行层实测耗时.md` |
| **候选 / 进行中** | 会变会删 | 还没验的、待办的 | `memory/暂缓经验-产品类.md` / `暂缓经验-大赛类.md`、`数据/判定/待办.md` |

### 11.2 五条硬规则（每条都对应一个真犯过的错）

1. **一条事实只有一个家。** 这条在代码上早就做对了（命名唯一出处 `scripts/naming.py`、装载唯一入口 `campaign.load`），
   文档照搬就行。反例：目录清单曾经同时活在 `ad_output/AGENTS.md`、本文件 §11、各层 README 里。
2. **规范正文只能重写，不能只追加。** 一遍遍追加是这份文件胖起来的根因；被推翻的结论要从正文**删掉**、
   进决策台账。反例：决策台账里 09-22「文案风格定两种」和 09-28「取消风格」并排躺着，读者分不清哪条算数。
3. **每份文件头部三行**：管什么 / 不管什么（指向谁）/ 谁在什么时候读。
   （`run_distribution_ids.md` 曾让人读不懂"这文件是干嘛的"，就是缺这一段。）
4. **新建文件前先答三个问题**：它是新事实还是新副本？寿命属于 §11.1 的哪一类？谁会读？
5. **地图只有一个入口**：每层只列自己那一层的细目，不复制别层的清单——`automation/README.md` 曾漏列 `seed_demo.md`，
   就是"清单副本"的典型代价。

**内容写在哪：**

1. **每次做新活动都用得上？** → 是：**规则**写本文件；**怎么让广告更有吸引力**（用户定的标准、真实踩过的坑）写 `memory/MEMORY.md`。
2. **只有这一单用得上？** → `activities/{活动名}/`（细则或活动定义）。
3. **改它的时候要不要连带改别的活动？** → 要 = 说明它放错层了，该提到通用层。

- **同一条内容只维护一份**：通用规则只放本文件，活动专属只放 `activities/{活动名}/物料/活动细则.md`；经验库只放词库与数据，**不复写规则**。
- **活动目录只记这一单**：`activities/{活动名}/`（含活动细则）只记**后台对象 / 文案 / 名单 / 日期 / 数据判断**；**工具、界面、数据层的工程变更不进活动目录**——脚本与工具写 `web/README.md`、`automation/docs/`，通用规则写本文件。
- **经验文档各写什么**（2026-09-24 起拆开、2026-10-09 按广告类型再拆一层，**别互相串**）：
  - `memory/MEMORY.md`：**怎么让广告更有吸引力**（写文案前用的规则）。没有经过用户允许、没有经过验证的内容**一律不许写**（AI 自己发明的分类 / 框架 / 数字都算）；拿不准的先放暂缓经验（见下一条）。
  - `memory/数据台账.md`：**只记数据**——逐条文案 ↔ 曝光 / 点击 / CTR / 结论，**好坏都记**（每次判定后回填）。
  - `memory/数据经验.md`：**只写已经验过的结论**（+ 读数据的方法）。⛔ **转正必须先问用户**（用户 2026-10-08 定），AI 不得自行把暂缓里的东西写进去。
  - `memory/暂缓经验-产品类.md` / `暂缓经验-大赛类.md`：**还没验够的候选**，**按广告类型分家**——
    用户 2026-10-09 定「写经验的时候要写清楚是对于什么类型的广告，是产品类还是大赛类，不分清这个就会出错误」；
    跨类嫌疑标「疑通用，待另一类复验」，**不设"通用"筐**。样本小的、只验过一两轮的一律放这两份里；大赛类那份同时是**下一批文案的测试清单**。
    ⚠ 每份头部都有一张 **验证进度表**：**每轮复盘后回填一行**（哪一轮、哪个桶哪个槽位在跑、结果、下一步）——
    这是"逐步验证猜测"的过程记录；**数字本身仍只写在 `数据台账.md`**（一条事实只有一个家）。
- **产出侧生成器（物料 / YAML）归 `ad_output/工具/`**；活动内容写「活动定义 YAML」，生成器不含任何活动内容（数据 / 代码分离）。
