# 用户痛点版（参考写法，不是规范）

> ⚠ **这是参考、不是必选**（用户 2026-09-28 定）：不再有"写文案前先选一种风格"这一步，也没有「默认风格」了。
> 它留在这里，只是因为这套写法你认可过、可以拿来借鉴——想借鉴就借鉴，不想用就不用。
> **里面的句式规则（「想让 X，就 Y」「承接词」「检 1~4」）是 AI 从实验里提炼的，不是你定的规范**，别当模板套。
> 一句话：**写的时候看第一部分，写完之后看第二部分；第二部分只检不改。**
> 来历：2026-09-16 以「v8」的名字做过一轮实验，2026-09-22 曾被转正为「用户痛点版」，
> **2026-09-28 随"取消文案风格"降为参考**（见 [`README.md`](README.md)）。
> 实验原稿留在 `../../_experiments/2026-09-16_两行广告框架-火山引擎MediaKit/v8-写法.md`（含 v1→v7 踩坑史，只作历史）。
> 成品示例：[两行框架 v8-承接版物料](../../_experiments/2026-09-16_两行广告框架-火山引擎MediaKit/物料/火山引擎MediaKit-hang-两行框架-v8-承接版.html)
> 结构前提：CSDN 页面类广告（CPM），创意固定 **2 行 = 标题 + 描述**，无 CTA 按钮。

## 适用范围（先看这个）

- ✅ **商品 / 产品类广告**：这套写法的抓手是「读者昨天亲手干过的那一刻 → 这个产品怎么做到」，
  要求产品有**可命名的形态**（Skill 包 / 工具 / 助手…）和**可核的机制**。
- ❌ **大赛 / 活动类不合适**（2026-09-22 用户定）：活动没有"产品能力机制"，描述第 2 句的承接句**无处可落**，
  硬写就是空话。活动类什么写法合适**还没结论**，别硬套——2026-09-28 起也没有"默认风格"可退回了。

## 三条之间的关系

- 三条是**并列的实验组**：同一人群、三个不同角度，**没有对照组**（角度之间**痛点不同**，不是卖点不同）。
- AB 分流后同一个人只会看到其中一条，所以三条句式统一不构成问题——不必为了"看起来不一样"强行变换句式。
- 后台三个资源槽位仍叫 `对照 / 实验1 / 实验2`（名字由 `automation/scripts/naming.py` 生成）：那是后台结构，
  不是文案口径——**写法上三条都是角度，谁都不陪跑**。
- **一轮实验只改一样东西**：三条一起换 = 测角度；只换标题句式 = 测句式。别同时改两样。

## 两个阶段

| 阶段 | 产出 | 完成判据 |
|---|---|---|
| **写** | 3 条文案（标题 + 描述 + 钩子说明） | 每条都能指认出「痛点句 → 承接词 → 机制句」三段 |
| **检** | 每条 4 个检验点的结论 + **可选**改法（列成 A / B，等用户点） | 每条 4 点都有结论，且**没有替用户改句子** |

> **「只检不改」是硬口径**（2026-09-18 用户定）：AI 判"怪"的句子，可能正是用户要的灵气或可塑之材。
> 检验环节交付的是**分析**，跟物料 HTML 一起给用户看；改不改、改哪句，由用户拍板。

# 第一部分 · 写

## 1. 格式

```text
标题：想让 X，就 Y
描述：痛点（1 句）+ 怎么做到（1 句）
```

| 位置 | 写什么 | 不写什么 |
|---|---|---|
| 标题前半 X | **读者想要的东西**（愿望、想要的结果） | 不写已完成的事实；不写痛点 |
| 标题后半 Y | **祈使句**：动作 + 产品形态或一条具体能力名 | 不写抽象动词（提升、赋能、助力） |
| 描述第 1 句 | **痛点**：读者昨天亲手干过的那一刻 | 不写抽象需求 |
| 描述第 2 句 | 这个产品**怎么做到**（讲机制），并**接住第 1 句** | 不复述标题已经给过的结果 |

示例（C 桶 · 2026-09-18 定稿）：

```text
想让 AI 直接分析视频，就装个能做剧情故事线分析的包
拿一段视频问模型讲了什么，答得云里雾里。这套能力自带剧情故事线分析、场景切分、智能语义切片，装进 Agent 直接调。
```

## 2. 先定「读者昨天那一刻」，再动笔（这一步一次都别跳）

1. 给这个人群列 **3–4 个具体的"昨天那一刻"**，标准三条，缺一条不合格：
   - 能拍出一个画面（有人在拖进度条、有人在搜参数、有人在注册页填资料）
   - 读者会想「对，就是我」
   - 不是抽象需求（「想提高效率」一律不合格）
2. 选出 **3 个**当三条文案的三个角度——角度之间**痛点不同**，不是卖点不同。
3. 第 1 句写选中的那一刻；第 2 句写机制；**最后**才写标题。

> 早先所有版本的毛病都在这一步：直接开始写句子，写出来的全是从产品视角出发的漂亮话。
> 2026-09-18 那轮又把这条走了一遍：C 桶的"那一刻"从「要做按剧情搜视频」这种功能句，
> 改成了读者真干过的一件事——「拿一段视频问模型讲了什么，答得云里雾里」。

## 3. 标题规则

**规则 1：必须是「想让 X，就 Y」。** 「想…，就…」本身是因果结构，前半给愿望、后半给方案，衔接不用额外铺垫。

**规则 2：前半不能是痛点，也不能是已完成的事实。** 痛点归描述，前半写读者**想要什么**。
自检：前半句如果带「了」，八成是错的（「参数不用自己拼了」→「想让参数自己拼出来」）。

**规则 3：后半必须是祈使句，且要点明产品是什么。** 动词开头：`装个…` / `给…装个…` / `把…换成…` / `用一个…`。
宾语落到**产品形态**（Skill 包 / 技能包 / 助手）或**一条具体能力名**。

> **标题不设字数上限**（2026-09-22 用户定）：**限制太多不好**——把话说清楚比凑字数重要，只按上面三条规则写。

## 4. 描述规则

**第 1 句 = 痛点 = 读者昨天亲手干过的那一刻**（见 §2）。

**第 2 句 = 讲清怎么做到**：交代机制、或者装完之后的实际样子。

| 标题给的结果 | ✓ 描述第 2 句写机制 |
|---|---|
| 想让参数自己拼出来 | 装完这个技能包，你只说想要什么效果，它把参数拼好给你看 |
| 想让 AI 直接分析视频 | 这套能力自带剧情故事线分析、场景切分、智能语义切片，装进 Agent 直接调 |

**描述里不要做的事**：堆数字（连续分数、两数并列）；堆英文专名（一行最多留一个这批人本来就认识的）；
把「我有什么」写成「你能少做什么」。

## 5. 承接：痛点句和机制句之间要下第一颗扣子（2026-09-18 新增，最重要的一条）

**规则：第 2 句开头点名产品形态，动词回指第 1 句的动作——同一件事，换个人做。**

最常见的病：两个句子各自都对，中间没有扣子，读起来像两件事。

| 痛点句（读者自己做的动作） | 承接词（谁来做） | 机制句（同一件事） |
|---|---|---|
| 为一条滤镜链搜了三遍，翻自己的历史命令 | 装完**这个技能包** | 你只说想要什么效果，它把参数拼好给你看 |
| 循环跑了两小时才发现参数写错 | 装上**这个帮手** | 参数由它拼，批量任务还能走闲时批处理 |
| 拿一段视频问模型讲了什么，答得云里雾里 | **这套能力** | 自带剧情故事线分析、场景切分、智能语义切片 |
| 需求散会才发现要接四家供应商 | **这一个包** | 转字幕、擦字幕、画质增强、抠像都在里面 |

**三种接法（择一，别三条都用同一招——一轮实验里三条读起来像同一个模板，测的就不是角度了）**：

1. **时间/动作承接**：`装完这个技能包，…`（前半是读者手上的动作，后半是装完之后的变化）
2. **递话筒（疑问承接）**：`需求散会才发现要接四家供应商？别怕，…`（痛点写成问句，第 2 句直接给答案）
3. **主语回指**：`这套能力自带…` / `这个包一次交一批…`（把悬着的主语补上）

## 6. 硬禁区

- 素材只能取自已核事实清单：**不编数字、不写产品没有的能力**。
- 只讲自家卖点，**不拉踩、不影射同行**。
- 不写抽象动词（提升、赋能、助力、打造）。
- 活动特例（禁用词、口径）**只由用户给**，AI 不自行提炼。

# 第二部分 · 检（只检不改）

写完之后，**逐条**过下面 4 个检验点。每个点只出**结论**，不改句子。

## 7. 四个检验点

| # | 问什么 | 不合格的判据 | 2026-09-18 实例 |
|---|---|---|---|
| **检 1** | 标题前半，读者要不要**想一下**才懂？ | 念给一个同行听，他得反问你一句才明白 | 「想让视频内容能直接搜」→ 读者得先想清"搜哪里、谁搜"；改后是「想让 AI 直接分析视频」 |
| **检 2** | 描述两句连起来念：**第 2 句在回答第 1 句吗？** | 两句各说一件事、中间没有扣子 | 原文「…自己抽字幕再分词，效果勉强。」+「剧情线…都是现成的」——第 2 句没接住第 1 句的动作 |
| **检 3** | 标题 + 描述连起来念：**描述有没有把标题给的结果又说一遍？** | 第 2 句把标题说过的结果重复了一遍 | —— |
| **检 4** | 第 1 句**能不能拍出一个画面**？素材**有没有编数字/编能力**？有没有**拉踩**？一行里英文专名是不是超过一个？ | 任一条踩中 | —— |

## 8. 检验怎么交付（口径）

1. **分析 + 物料 HTML 一起给**，不单独发结论。
2. 改法写成**可选 A / 可选 B**，**不落成新文案**；用户点头了才改物料。
3. 判"怪"之前先自问一句：**是不是我读不出它的灵气？** 用户的判断优先。
4. 完成判据：3 条 × 4 个检验点都有结论，且**一个字都没被 AI 私自改掉**。

# 第三部分 · 提示词模板（两段式）

**第一段（写）**

```text
你写 CSDN 页面类广告文案（CPM），创意结构固定两行：标题 + 描述，没有按钮。

【人群】<人群描述>
【产品】<产品名 + 一句话定位 + 产品形态词（Skill 包 / 工具 / 助手…）>
【已核事实】<只能从这里取材的清单：能力名、规格、支持的平台、可核的机制>

先做这一步，不要直接写文案：
列出这个人群「昨天亲手干过的 3–4 个具体动作」，每个都要具体到能拍出一个画面。
然后选 3 个作为三个角度（角度之间痛点不同，不是卖点不同）。

再按下面格式写 3 条（三条并列，没有对照组）：

标题 =「想让 X，就 Y」
  X：读者在这个角度下想要的东西（愿望、想要的结果）
     硬规则：不能写成已完成的事实（前半带「了」就是错的）；不能是痛点描述
  Y：祈使句，动词开头（装个 / 给…装个 / 把…换成 / 用一个）
     宾语必须点明产品形态或一条具体能力名

描述 = 两句
  第 1 句：痛点——读者昨天干过的那一刻（能拍出画面，不是抽象需求）
  第 2 句：怎么做到（讲机制），并且**接住第 1 句**：
           开头点名产品形态（这个技能包 / 这个帮手 / 这套能力 / 这个包），
           动词回指第 1 句里的动作（同一件事换个人做）。
           三条各用一种接法：装完… / 痛点？+ 答案 / 这套能力…

禁止：编造数字、写产品没有的能力、拉踩影射同行、抽象动词（提升、赋能、助力）、
      成串的英文专名。
```

**第二段（检，只检不改）**

```text
上面那 3 条，逐条做检验，**只给结论、不要改句子**：

检 1 标题前半：念给一个同行听，他会不会要先反问我一句才懂？（会 = 不合格）
检 2 描述两句连念：第 2 句在回答第 1 句吗？中间有没有承接词/主语？
检 3 标题 + 描述连念：描述有没有把标题给的结果又说一遍？两行讲的是不是同一件事？
检 4 第 1 句能不能拍出一个画面？有没有编数字 / 编能力 / 拉踩 / 英文专名成串？

输出：一张 3 条 × 4 点的表，每格只写「像 / 不像 + 一句理由」。
如果你觉得某句不好，把改法写成「可选 A / 可选 B」放在表后，**不要替换原文**——
我自己判断哪句有灵气。分析结果随物料 HTML 一起给我。
```
