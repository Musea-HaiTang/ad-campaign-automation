# 复盘看板优化方案（`web/`）

> 起因（2026-09-28 用户）：看板的主要用途是**看数据 + 复盘**——「达到一定曝光就分析点击」，
> 想看到**每个桶换文案后的点击变化（文案有没有吸引力）**；同时希望**打开网站数据就是最新的**。
>
> 本文是方案，按项目纪律逐阶段确认后实施。上一份（多活动）见 `web/多活动改造方案.md`，已完工。

## 1. 用户口径（2026-09-28 访谈定，实施时不要自行改）

| 问题 | 结论 |
|---|---|

## 2. 现状的三个问题

1. **当前批次可能整批消失**：07 批工单在库里 `workStatus = "0"`（工单已建、任务未生成），
   页面「仅在投」只认 `进行中` → 起投后若状态仍是 `0`，当前批次会被整个藏起来。
   （注：09-28 页面空**主要是火山当天本来就不投**，这条是隐患、不是当天的主因。）
2. **只有资源名和数字，没有文案原文**：判断吸引力必须看到句子本身；文案存在批次 YAML 里
   （`audiences[].resources[].title/summary/highlight`），幸存文案能顺着资源名回历史 YAML 找。
3. **数据新鲜度靠不住**：Codex 项目级定时任务的官方前提是「机器开着 + 桌面 app 运行」
   （OpenAI 官方文档 [Scheduled tasks](https://developers.openai.com/codex/automations)），
   而且它与看板服务**抢同一个浏览器 profile**（一个 profile 同时只能被一个进程用）——
   巡检建了 4 天、0 产出，`待办.md` 从未生成过。

## 6. 关键设计（实现约束）

- **一批 = 一份整活动 YAML**（`配置/…-hang.yaml` 是首批，`调整/…-N批.yaml` 是后续批）。
  名字后缀（`-2`/`-6`）**不是批次身份**——09-17 的 D 桶和 09-18 的 B/C 桶共用 `-2`；
  后缀只用来按 `naming.order_task_name()` 算工单名，再与台账里的 `task_name` 精确匹配。
- **文案索引跨批次合并**：幸存文案带的是**上一批的资源名**（`… · 对照-6` 出现在 -7 的 `abGroups`），
  所以要扫全部批次；同名取最早出现那次（就是它被写出来的那批）。
- **`batch` 口径** = 当前批次的工单（不看 `state`）；页面默认用这个口径。
  没有 `判定门槛.yaml` 的活动（KIRO）：`currentBatch` 回落到最后一批，达标列留空。
- 批次的**判定**仍归 `judge_batch.py`（页面只读库算展示口径，不改判定规则）。

## 9. 页面整改（2026-09-28 用户看页面后提的，已做）

用户反馈三条：①「本批 · 判定」不该单独占一块——判定应该并进**分桶统计**那张表；②「批次之间」太长，
要**能切换**；③**分资源（文案级）的统计弄丢了**（我第 3 期删「三套文案」块时一起删掉的，是回归）。
另让出三个样板选样式：**采纳样板 A（单表展开）**，B（卡片矩阵）/C（双栏详情）弃。

落地（2026-09-28）：

- **分桶统计 = 唯一主表**：`累计读数 / 门槛`（进度条）+ 点击 + 点击率 + 判定 + 建议动作，**点行展开**三条文案
  （原文 + 曝光/点击/CTR + 保留/下）。展开行用 `colspan` 覆盖整行 + 父表 `table-layout:fixed`
  —— 样板 A 里"一点就变形"就是这个没做对。
- **主表左上角加批次下拉**（默认当前批次，刷新后保住所选批次）→ 资源级明细**跟着批次走**，回归的第 3 条解决。
  后端为此新增 `batchJudge`：**每个批次都算一遍判定 + 带上该批三条文案**（以前只算当前批次）。
- **「批次之间」加可视化**：柱 = 各批次点击、虚线 = 点击率（右轴）、柱下小字 = 该批曝光；下面配一张紧凑表；
  桶用按钮切（不再 5 张表堆成长条）。
- **原「本批 · 判定」块删掉**（内容全部并进主表）；原「分桶总计（时间段）」那张**表**也删掉
  —— 它和主表是同一个东西的两种口径，留着就是"同一件事说两遍"；**时间段控件与两张趋势图保留**
  （放在「按时间段看」那一块，工单口径筛选也只作用于它）。

## 10. 待复盘角标 + 弹窗（2026-09-30 起，辅助功能）

**需求（用户 2026-09-30）**：看板上要能一眼看到「**攒够曝光、还没复盘**」的工单，省得自己逐个桶比门槛；
但**不许动现在的布局**——它是辅助功能，只在"有到门槛的"时候出现一个入口。

**做法**：页头按钮组（取数 / 刷新那一排）加一个按钮，带数字角标；点开是弹窗清单（复用 `#modal`）。
弹窗里一行一个工单、跨活动汇总，点行 = 切到那个活动 + 那一批。

### 口径（用户 2026-09-30 定死，实施时不要自行改）

| 项 | 结论 |
|---|---|
| 什么算待办 | **在投** + 该桶累计曝光 ≥ 门槛 + `配置/复盘动作.yaml` **没有**这「批次后缀 × 桶」的记录 |
| 达标没达标 | **都算**（达标要转长期单、没达标要换文案，两种都得动手） |
| 范围 | **所有登记活动**（页面一次只加载一个活动，所以得服务端汇总） |
| 角标数字 | **所有活动**的合计条数；为 0 时按钮隐藏 |
| 点行 | **要**：切到该活动 + 该批次 |
| 不做 | 历史批次（在投才列）、无门槛的活动（KIRO 那种自然为空）、布局改动 |

> ⚠ 已知脏点（用户知情）：`复盘动作.yaml` 是「有调整动作才写」的文件。某桶到门槛后若结论是
> "都不动"，没人补记录，它就会一直挂在清单里 → **复盘时顺手补一条记录**把状态落下去
> （不另做"划掉 / 忽略"机制）。
