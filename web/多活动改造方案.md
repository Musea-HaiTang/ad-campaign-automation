# 看板多活动改造方案（`web/`）

> 起因（2026-09-28 用户）：**两个活动同时在跑**（火山引擎MediaKit、KIRO鬼点子计划），
> 看板网站要能同时看两个活动；并确认数据库能不能撑住多活动。
>
> 本文是**方案**，不是已完成事项。按项目纪律（未确认不实施），逐阶段确认后才动代码。
> 落位依据：流程文档 §11「界面 / 服务层的工程变更写 `web/` 或 `automation/docs/`，不进活动目录」。

---

## 1. 结论速答

**① 数据库能不能多活动？——能，已经做好了，表结构不用改。**

`perf_db.py` 的 schema 从一开始就带活动维度：`activity` 表（主键 = 任务组名）当跨活动锚点，
`task` / `resource_reading` 带 `activity_id`，`daily` 主键 `(task_id, 日期)`——task_id 是后台全局唯一的，
天然不串。所有查询函数（`days` / `order_cells` / `tasks` / `latest_resource_readings`）
第一个参数都是 `activity_id`。文件头当时写的理由就是「跨活动迟早要做」。

**② 网站要改什么？——不是"该更新"，是它现在已经起不来。**

`web/app.py:195 find_config()` 只认「恰好一个能过 YAML 契约的活动」，第二个活动一上线就走
`web/app.py:212` 的 `SystemExit`。实测（只读，没起服务，进程立刻退出）：

```
有多个活动配置，请用 --config 指定其中一个：
  activities/KIRO鬼点子计划/配置/KIRO鬼点子计划-hang.yaml
  activities/火山引擎MediaKit/配置/火山引擎MediaKit-hang.yaml
```

也就是说**双击 `web/start.bat` 现在什么都看不到**。

## 3. 关键设计判断：必须是「一个服务管多个活动」

先排除看起来更省事的做法：**每个活动起一个服务、各自 `--config`**。

这条路走不通：`web/README.md` 已写明「一个登录 profile 同时只能被一个进程用」，
而取数靠的是服务里那只**常驻浏览器**（2026-09-24 用户定）。第二个服务一起来就抢
`.browser-profile`，看板还能看，但**两个服务的「取数 / 刷新」按钮都会废掉**。

所以：

1. **一个 `web/app.py` 进程**，内部维护一张**活动登记表**；
2. 数据库全活动共用一份 `activities/_db/投放数据.db`；
3. 取数**串行**（只有一个浏览器），页面按活动各记一份「今天已取」的配额。

## 4. 改动清单

### 4.1 活动登记：`automation/scripts/campaign.py`（新增一个函数）

`campaign.py` 已经是「整活动 YAML 的唯一入口」，把"扫活动"放这里，web 与测试都能复用，
不新增文件、不反转依赖方向（web → automation）。

```
discover(root="activities", only=None) -> [ {id, label, cfg, cfg_path, activity_dir, data_root} ]
```

- 扫 `activities/*/配置/*.yaml`（**只扫 `配置/`**：`调整/` 下的批次 YAML 不纳管）；
- 用 `campaign.load()` 能不能过契约来筛（`活动定义.yaml`、`*.thresholds.yaml`、`判定门槛.yaml`
  自然被排除，沿用现有做法）；
- **按 `taskGroupName` 去重**：同名两份 → 报错并列出路径（不静默取一个）；
- 结果排序固定，页面切换器的顺序才稳定。

### 4.2 服务层：`web/app.py`（主要工作量）

| 现在 | 改成 |
|---|---|
| `Handler.cfg` / `cfg_path` / `data_root` 各一份 | 注册表 `ACTIVITIES = {任务组名: {...}}`，按请求取 |
| `find_config()` 命中多个就退出 | `--config` 降级为「只登记这一个」（向后兼容）；不给就登记全部 |
| `FETCH` 全局一份 | 每个活动一份；`running` 是全局闸、`todayDone` 按活动算 |
| `JOBS` 里放 `mode` | 放 `(activity_id, mode)`，worker 按活动取 cfg |
| `db_state()` 读 `Handler.cfg` | 按活动算 |

接口契约（`activity` 一律用**任务组名**）：

| 路径 | 现在 | 改成 |
|---|---|---|
| `GET /api/activities` | 无 | **新增**：`[{id, label, dir, db:{days,first,last}}]` |
| `GET /api/perf` | 用 `--config` 那个活动 | `?activity=`；不给 = 默认活动 |
| `GET /api/snapshots` | 当前活动 | `?activity=` |
| `GET /api/fetch/status` | 一份 | `?activity=`（`running` 全局、`todayDone` 按活动） |
| `POST /api/fetch` | 单活动 | `?activity=&today=1&force=1` |
| `/`、`/app.css`、`/app.js` | — | 不变（一个页面服务所有活动） |

- `/api/activities` 以**登记表**为主、`perf_db` 的数据现状为辅，这样
  「后台在跑、库里还没取过数」的活动（KIRO 现在就是）也能出现在切换器里，并标成空库。
- 服务窗口与页面状态行的文案带活动名（`正在取数（KIRO鬼点子计划）…`），否则两个活动分不清。

### 4.3 页面层：`web/static/`（本次范围见 §5）

- `index.html` 页头加**活动切换器**；`app.js` 的 `loadFromServer()` 带上当前活动 id，
  新增 `loadActivities()` 填切换器，`localStorage` 记住上次看的活动。
- **切活动时时间段/口径重置为默认**（不做保留）：两个活动的桶与日期区间都不一样
  （火山 09-14 起、KIRO 09-24 起），硬保留必然出空表。同一活动内「刷新后保住选择」不变。
- `startFetch` / `pollFetch` / `loadFetchState` 带活动 id；空库态复用现成的 503 分支。

## 8. 风险与坑（已知的）

1. **浏览器单例**：多活动取数只能串行；两个活动一起取约 10~30 秒，页面要有进度（现成机制可用）。
2. **KIRO 首次取数要全量回填**（空库 → 从 09-24 起），不是"补昨天"，耗时比日常取数长。
3. **SQLite 单文件多活动**：写入只有一个取数线程，安全；`connect(timeout=5)` 已处理读写相撞。
4. 改 `app.py` / `static/` 后**必须重启服务**（`web/README.md` 已写；之前踩过「页面新、服务旧 → 五个桶静默全 0」）。
5. 火山 **09-28 全天不投**（旧工单已下、-7 批 09-29 起投）——看板上那天是空档，是预期的，别当成漏投或 bug。
6. 页面那条「点击率及格」线（全局 0.10%）与判定门槛（千三）**不是一回事**，见 §5。

## 9. 不做清单（避免过度设计）

- ❌ 不做"每个活动一个端口 / 一个服务"（§3 已论证会互相抢浏览器）。
- ❌ 不给 `activity` 表加 start/end/负责人等元数据（YAML 已是唯一真相，重复存必然飘）。
- ❌ 不做登录 / 多用户 / 权限。
- ❌ 不做混合口径的跨活动折线图（活动周期、门槛、口径都不同，混在一条线上会误导）；
  真要做跨活动视图，只做「每活动一行」的汇总卡。
