> 这块只做**展示**：页面 + 一个本地只读服务。数据由 `automation` 产出，活动数据仍放 `activities/`。
> 用户 2026-09-17 定：可视化走「**前后端分离**」；以后整个流程网站化，也从这块往外长。

## 数据怎么来（三步，各管一段）

| 步 | 谁 | 干什么 | 频率 |
|---|---|---|---|
| ① 取数 | `automation/scripts/fetch_perf.py`（`fetch_mod.run`） | 带登录态调后台只读接口 → **写台账库** `activities/_db/投放数据.db`（「取数」另落一份取数流水 CSV 存档） | 每天 / 随时刷 |
| ② 服务 | `web/app.py` | 读**台账库** → 聚合成 JSON → 交给页面；同时**常驻一只浏览器**给取数用（用户 2026-09-24 定） | 常驻 |
| ③ 展示 | 浏览器（`web/static/`） | `fetch("api/perf")` 拿数据 → 渲染；筛选/切换都在浏览器里算 | 打开即用 |

⚠ **页面的「刷新数据」只重新读台账库，不会去后台取新数**；要新数就点「取数」（或跑 `fetch_perf.py`）。
数据到哪天 = 库里最新那行是哪天；取数**默认增量**（最近有数据那天 ~ 今天），随点随新。

⚠ **浏览器是常驻的**：`web/start.bat` 起服务时就把浏览器开起来（无窗口），「刷新 / 取数」都复用它，
**关掉服务窗口（或 Ctrl+C）时一起关**。
⚠ **但"强杀"会漏**（2026-10-12 实测两次）：`Stop-Process` 掉 8770 的监听进程时，取数线程来不及
`BROWSER.close()`，**那只 Edge 会留在后台占着 `.browser-profile`**；下一次起服务就报
`浏览器：没起来：BrowserType.launch_persistent_context: Target page, context or browser has been closed`
（页面 200、就是取数全失败）。停服务后顺手确认一下、有就清掉：

```powershell
Get-CimInstance Win32_Process -Filter "Name='msedge.exe'" |
  Where-Object { $_.CommandLine -like "*browser-profile*" } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

> 同一根因（`.browser-profile` 上的残留锁）的详细复现与「过期 `lockfile` 也要删」的处置，见
> [`automation/docs/执行层实测耗时.md`](../automation/docs/执行层实测耗时.md) 的
> 「2026-10-12 · 大名单核对"卡住"复现：残留浏览器 + 过期 lockfile」——那边是命令行跑名单，
> 这边是看板服务，症状一样、清法一样。

代价：**一个登录 profile 同时只能被一个进程用**，所以服务开着时别再在命令行跑 `fetch_perf.py`
或 `wait_login.py`（会报"浏览器起不来"，提示里写了怎么办）。

**要让命令行抢浏览器（建批 / 取数）时，按这个顺序**（用户 2026-09-29 授权"需要用的时候直接关，不用问"）：

```powershell
# 1) 停服务：找 8770 的监听进程并结束（关窗口 / Ctrl+C 等价）
(netstat -ano | Select-String "127.0.0.1:8770" | Select-String LISTENING) -replace '.*\s(\d+)$','$1' | ForEach-Object { Stop-Process -Id $_ -Force }
# 1b) 确认没有残留 Edge 占着登录 profile（有就按上面那条清掉，否则第 3 步起来的服务取数全失败）
# 2) 跑命令行脚本（run_ads / run_taskorder / fetch_perf …）
# 3) 起回来：脱离当前会话起，输出落日志（否则进程会继承调用方的会话句柄，**监听得到却回不了 HTTP**）
Start-Process -FilePath "D:\Codex_WorkingSpace\ad_management\.venv\Scripts\python.exe" -ArgumentList "-u","app.py" `
  -WorkingDirectory "D:\Codex_WorkingSpace\ad_management\web" -WindowStyle Hidden `
  -RedirectStandardOutput "$env:TEMP\board_service.log" -RedirectStandardError "$env:TEMP\board_service.err.log"
```

> 2026-09-29 实测：用 `cmd /c "start /B …"` 在本会话里起服务 → 端口 LISTENING 但 TCP 连上后**0 字节**（HTTP 不通）；
> 换成上面 `Start-Process`（隐藏窗口 + 日志）→ 页面 200、自动刷新照跑。排查看 `$env:TEMP\board_service.log`。

### 服务窗口打印什么（2026-09-29 用户要求"规范一下"）

**启动**（一次性，9 行以内）：标题 → 台账路径 → 每个活动一行（标签 / id / 库内几天 / 到今天）→ **跳过几个非整活动 YAML
（合成一行，只列文件名，不再把 6 行绝对路径糊在标题前面）** → 打开地址 + 取数流水位置 → 接口 → 取数/自动刷新 →
一条分隔线（`────（下面只打：取数结果 / 自动刷新 / 出错）`）。

**运行期只打三类**：

| 打什么 | 什么样 | 为什么 |
|---|---|---|
| 取数结论 | `[活动] RESULT: 取数完成（按天 1 行 …；资源级累计 15 行）` / `[活动] ✗ …` | 明细（逐工单 × 日期、逐资源）**只进页面状态和取数流水**，窗口一行就够（以前逐行打，一次取数刷十几行） |
| 自动刷新 | `自动刷新：<活动> 刷新今天（每 30 分钟一次）` | 到点才打，看得出服务在活着 |
| 出错 | 访问日志**只留 4xx / 5xx**（`! "GET /nope HTTP/1.1" 404 -`）+ 浏览器起不来时的提示 | 页面每次拉数据、每个静态资源都会写访问日志，2xx 全打出来会把窗口刷满 |

## 看板相关代码分布（为什么不全在 `web/`）

看板这一域**横跨两层，这是刻意的**（2026-09-23 定）：`web/` 只管"给人看"，"怎么取数、怎么算"留在 `automation/`。
依赖方向**单向**：`web/` → `automation/scripts/`（`app.py` 里 `sys.path.insert(.../automation/scripts)`，取数按钮把 `fetch_perf.py` 当子进程调）。

| 层 | 文件 | 干什么 |
|---|---|---|
| 存储 | `automation/scripts/perf_db.py` | 台账库（SQLite）读写；取数写、看板读、导出读、单测用 |
| 装配 | `automation/scripts/perf_payload.py` | 台账库 + 活动 YAML → 看板 JSON；**口径唯一真源**（合计、有量天数都在这里算） |
| 取数 | `automation/scripts/fetch_perf.py` | 开浏览器带登录态调后台只读接口 → 写台账库（**执行层脚本**，与 `run_*.py` 同族）；`Browser` / `run()` 给看板复用 |
| 服务 | `web/app.py` | 本地 HTTP 服务：读台账库 → JSON；另起一个**取数线程**拿着常驻浏览器，刷新的活投给它 |
| 页面 | `web/static/` | `app.js` / `app.css` / `index.html`，只做渲染与"把所选的天加起来" |
| 导出 | `automation/scripts/visualize_perf.py` | 把 `web/static/` 的页面 + 数据烤成一个单文件 HTML |

改哪层写哪份文档：数据层/取数/导出 → `automation/docs/` 与 `automation/README.md`；服务/页面 → 本文件。
**不建议**把 `perf_db` / `perf_payload` / `fetch_perf` 搬进 `web/`：那会让依赖方向反转（automation 反过来 import web），
也会把"执行层脚本"劈成两处——收益只是目录看起来更整齐（2026-09-23 讨论结论）。

⚠ **改了 `perf_payload.py` / `perf_db.py`（Python 侧）或 `web/static/` 之后，要重启服务**：`app.py` 在启动时
`import perf_payload`，**不会热加载**。2026-09-23 就踩过这条：页面代码是新的、服务里的数据是旧的 → 页面读不到
`bucketCells` 之类的字段，**五个桶静默全显示 0**（看起来像"数据加载不出来"，其实是要重启）。
**改了 `web/app.py` 或 `automation/scripts/fetch_perf.py` 也要重启**（取数走的是常驻浏览器，那只是服务进程里的东西）。

## 一键启动

双击 **`web/start.bat`**：自动打开 `http://127.0.0.1:8770/`，那个黑窗口就是服务（**关窗或 Ctrl+C 即停**，不留后台进程）。

命令行等价写法：

```powershell
.venv\Scripts\python.exe -u web/app.py            # 登记 activities/*/配置/*.yaml 下的全部活动
.venv\Scripts\python.exe -u web/app.py --config activities/火山引擎MediaKit/配置/火山引擎MediaKit-hang.yaml   # 只登记这一个
... --port 8888            # 换端口（默认 8770）
... --host 0.0.0.0         # 允许同局域网其他机器访问（默认只本机）
... --db 别的.db           # 换台账库（默认 activities/_db/投放数据.db）
... --auto 30              # 自动刷新间隔（分钟；默认 30，给 0 关掉）
```

- `--config` 从 2026-09-28 起是**筛选器**（只登记这一个），不再"多个活动就报错让你选"。
- 启动/监听端口需要提权；端口被占用会起不来，换 `--port`。

## 多活动（2026-09-28 起）

一个服务管**所有**活动：启动时用 `campaign.discover()` 扫 `activities/*/配置/*.yaml`，
能过 YAML 契约的登记进表（`活动定义.yaml` / `*.thresholds.yaml` / `判定门槛.yaml` / `调整/` 下的批次
YAML 都不会被登记）；**同一个任务组名出现两份会直接报错**，不静默挑一个。

| 事 | 怎么办 |
|---|---|
| 台账库 | **全活动共用一份** `activities/_db/投放数据.db`（schema 本来就带活动维度，不用改表） |
| 请求带活动 | 接口都接受 `?activity=<任务组名>`；**不给 = 默认活动** |
| 默认活动 | 优先挑**库里有数据的那个**（新活动刚建、还没取过数时，一打开不会是空页面） |
| 取数串行 | 浏览器**只有一只**（一个登录 profile 只能被一个进程用）→ 跨活动也**同时只跑一个**；一批在跑时再点会被挡，并提示队列里还有几个 |
| 一次刷全部（2026-10-09 用户定） | 页面上的「取数」「刷新」= `?all=1`：**登记的活动全跑一遍**（顺序 = 当前看的活动先跑）。理由：浏览器只有一只、取数本来就串行，分开点不会更快；而待复盘角标是跨活动的，只刷一个活动它必然半新半旧。**单活动的 `?activity=` 仍然保留**（自动刷新 / 脚本在用） |
| 「今天已取」配额 | **按活动各算一份**：给 B 取数不吃 A 的额度（看当日取数流水判断）。`full` 模式下 `?all=1` 会**跳过今天已经取过的活动**并在结果里说明；「取数」按钮的禁用看 `todayDoneAll`（所有活动都取过才算今天取过） |
| 取数流水 | 按活动各一份：`activities/{活动名}/数据/{时刻}/` |
| 页面切换器 | 页头那个**下拉**（服务版才有）：选过之后记在浏览器里，下次打开还是它；**切活动会重置时间段/口径**（见「页面控件」） |

## 批次维度（2026-09-28 起）

看板要能按**批次**复盘（"这个桶换了文案之后点击变好没有"），所以 payload 里多了一块：

| 字段 | 是什么 |
|---|---|
| `batches` | 批次表（按起投日排序）：`{id,label,suffix,start,end,yaml,orders,copy}`。**一批 = 一份整活动 YAML**——`配置/…-hang.yaml` 是首批，`调整/2026-09-24-六批.yaml` 是后续批；名字后缀（`-2` / `-6`）**不是批次身份**（09-17 的 D 桶和 09-18 的 B/C 桶共用 `-2`），它只用来算工单名 |
| `currentBatch` | **活动最新一批**的 id（全局回退用；2026-10-08 起不再读 `判定门槛.yaml` 的 `batch`——那个字段已删） |
| `buckets`（2026-10-08 改） | **桶维度，页面主表就吃它**：`[{id, name, color, topic, threshold, currentBatch, refBatch, batches}]`。`currentBatch` = **该桶最后一次建批**（只写 audience 没挂资源的批次不算，规则在 `campaign.bucket_current()`）；`refBatch` = 该桶最近一次有量的批次；`batches` = 该桶参与的每一批（按起投日排序，含 `task/exposure/click/ready/pass/keep/drop/action/groups` 等） |
| `orders[].batch` | 这条工单归哪批（按 `naming.order_task_name()` 算的工单名跟台账里的名字**精确匹配**；对不上 = `null`，页面标"未归类"）。实测火山 29/31 条归上了，未归的是 `测试工单-…` 和 `…A类测试` |
| `copy` | 资源名 → 文案原文（`title` / `summary` / `highlight` / 出处批次），**跨批次合并**——幸存文案带的是**上一批的资源名**（`… · 对照-6` 会出现在 -7 批的 `abGroups` 里） |
| `bucketCells[桶]["batch"]` | 第三个口径：**当前批次的工单**，**不看工单状态** |

⚠ 为什么要单独有 `batch` 口径：新建工单在后台生成任务前 `workStatus` 是 `"0"`（不是"进行中"），
只看「仅在投」会把**当前正在跑的那一批整体漏掉**（2026-09-28 发现）。页面默认口径将改成「当前批次」。

**判定三列（2026-09-28 起）**：payload 还带

| 字段 | 是什么 |
|---|---|
| `thresholds` | `配置/判定门槛.yaml` 原文（当前批次号 + 各桶门槛 + `passCtr` 达标线）；**缺这份文件 = `{}`**，页面据此降级（KIRO 门槛还没定就是这种） |
| `batchJudge` | **每个批次 × 每个桶**一条：`{bucket, task, exposure, click, threshold, needClick, ready, pass, keep, drop, newCopy, state, conclusion, groups}`，`groups` 就是该桶三条文案（`res` / `e` / `c` / `keep` / `title` / `summary` / `highlight`）。页面左上角那个批次下拉就是在这个字典里切。⚠ **资源级与门槛解耦**（2026-09-28）：没定 `判定门槛.yaml` 的活动（KIRO）`threshold` 为 `null`、`state`/`conclusion` 空、`keep` 空，但 **`groups` 照给**——页面照样能展开看三条文案 |
| `batchJudge[].action` | **人定的调整动作**（2026-09-30 加）：读 `activities/{活动}/配置/复盘动作.yaml`，键 = **被判过的那一批**的批次 id（2026-10-08 从"批次后缀"改成批次 id；**2026-10-12 定下"记录挂在你判的那一批"**——建批时写的动作属于上一批，挂到新批名下就会被当成新批的结论顶掉规则结果，KIRO D 桶五批踩过；旧文件仍能读，取不到新键时按后缀兜底一次）→ `{keep, drop, new, note, at, readings, changed}`：`at` = 判定依据的那次取数时间、`readings` = 当时逐槽位的 `[曝光, 点击]`、`changed` = 这些槽位**判定后又变了**（服务端按 `perf_payload.human_action` 比，页面据此打「数据已变」）。**有记录才有这个字段**，并**顶掉规则结果**。页面据此把最后一列分成 **调整动作**（有记录）/ **建议动作**（没记录，走 `judging.py`）两种写法 |
| `batchStats` | 桶 × 批次的**按天累计**（曝光/点击/登录数/有量天数）——「批次之间」那张图与表用的就是它（跟判定的资源读数不是一个口径，页面上都标了） |

⚠ **判定规则本体在 `automation/scripts/judging.py`**（2026-09-28 收口）：命令行 `judge_batch.py`
和看板用的是**同一个函数**，页面上显示的建议动作 = 命令行清单里那套，不许各算一遍。

## 数据新鲜度（2026-09-28 起）

服务**自己定时刷新**（`--auto`，默认 30 分钟；给 0 关掉）：

| 时机 | 干什么 | 为什么 |
|---|---|---|
| 每天**第一次** | 跑一次**取数**（默认区间 = 最近有数据那天 ~ 昨天，落一份取数流水） | 只刷今天的话，**昨天那行会永远停在"半截的今天"**，复盘看到的昨天曝光偏低 |
| 之后每 30 分钟 | 刷**今天**的实时数（不落流水，跟页面上那个刷新图标干的事一样） | 打开网站就是最新的 |
| 每个活动轮着来 | 跨活动串行（浏览器只有一只） | 一个登录 profile 同时只能被一个进程用 |

**收尾的活动不进整批**（2026-10-12 用户定）：活动根下有 `已结束.md` 的活动（首例 `activities/火山引擎MediaKit/已结束.md`）
**整批「刷新 / 取数」一律跳过**（它一旦失败会把整批拖成"0 成功 N 失败"，看不出到底是谁出问题），
跑完那行会把跳过的活动名写出来（`取数完毕！（1 个活动，跳过：火山引擎MediaKit-hang-5类）`），
活动切换器上标「已收尾」，页面照旧能看历史。
**补数窗口 = 收尾日 + 2 天**：标记正文那行 `收尾日：YYYY-MM-DD` 决定窗口（没写 = 按"立即停"处理）——
窗口内看板仍自动补数（后台数据回传有延迟，收尾那天先取到的是半截值，隔天重取才是终值），
过了窗口彻底停、连自动刷新也不再跑；「取数」按钮的禁用判据 `todayDoneAll` 也不把**彻底停掉**的活动
算进来（否则会永远显示"今天还没取"）。
**要看 / 要补某个收尾活动**：切到它再点「刷新 / 取数」——这时**只跑它自己**（不再扩成整批，
`pollFetch` 也改走"只看这个活动"的轮询，免得读到上一批留下的旧进度），服务端单活动入口不做任何拦截。
判定那边同一份标记也让定时巡检跳过它（`automation/docs/巡检与自动复盘.md` §1）。

取数失败那行提示只在**真像登录态问题**（跳登录页 / 未授权 / 401 / 403）时才带
"登录态过期就去跑 `wait_login.py`"（2026-10-12 修）——原先无条件套这句，把"日期区间算错""DNS 都解析不出来"
也一起指去重登，纯误导。

页头第二行会写：`数据区间 09-14 ~ 09-28（15 天）｜ 最近取数 09-28 09:50 ｜ 自动刷新 每 30 分钟（上次 14:03）`；
自动刷新失败会写「上次 14:03 失败」（详细原因在服务窗口里，多半是登录态过期）。页面每 60 秒问一次状态，
自动刷新跑完会**自动更新页面**（并保留你选的时间段与口径）——2026-10-09 起**顺带重问一次待复盘清单**，
角标也跟着变（以前只换表格、角标会停住）。`--auto 0` 关掉自动刷新 —— 那就只能手点「取数」。

## 接口（全部只读）

## 每天取的是哪些数据

| 文件 | 粒度 | 字段 |
|---|---|---|
| 台账 `daily` | **工单 × 日期**（按天） | 曝光 / 点击 / **登录曝光** / **登录点击** / 取数时刻 |
| 台账 `resource_reading` | **工单 × 3 组资源 × 取数时刻**（累计读数） | 组别（对照·实验1·实验2）/ 资源名称 / 累计曝光 / 累计点击 |

拿不到的：消耗 / 金额 / 预算、圈选人数、日均曝光(预估)（那在后台圈选列表里）、文章级与用户级明细。

**取数默认取「库里最近有数据那天 ~ 昨天」**；**今天那行只有点「刷新」才会写/更新**（它是半截的，看板上按一天参与 日均曝光）。两条路都写同一张 daily 表，所以先刷新后取数也不会互相覆盖。

## 页面怎么改

- **改样子 / 改交互**：只动 `static/` 三个文件，改完刷新浏览器即可（服务不用重启）。
- **加数据字段**：在 `automation/scripts/perf_payload.py` 的 `build_payload()` 里加，页面用 `DATA.xxx` 取。
- **加新页面 / 新接口**：在 `app.py` 的 `do_GET` 里加路由，静态文件放 `static/`。

## 跟"单文件版"的关系

`automation/scripts/visualize_perf.py` 会把 `static/` 三件套 + **台账库数据**烤成一个 HTML（发人 / 归档用，双击即开、断网可看）。
两边用的是同一个 `perf_payload.build_payload()`，数字必然一致——不会出现"页面和文件对不上"。

## 常见问题

- **页面整片显示「Failed to fetch」**（2026-10-12 真踩到）：这不是"库里没数据"，是 `/api/perf` **抛异常**了——
  服务把连接掐掉，浏览器只会给这一句。看 `$env:TEMP\board_service.err.log`（服务是隐藏窗口起的，日志落这两个文件）。
  那次的原因：批次索引新加的一个字段写成了 `set`，而 `build_payload` 会把**整份** `campaign.load_batches()` 放进 payload
  （`batches` 那一栏），`json.dumps` 直接 `TypeError: Object of type set is not JSON serializable`。
  ⛔ **规矩**：凡是会进 payload 的数据（含 `load_batches()` 的输出）**必须是 JSON 可序列化的**——
  测试 `automation/tests/test_campaign.py::BatchIndexTest::test_批次索引必须能过json` 现在会拦住这类。
  （⚠ 顺带一条：**8770 别开两个服务**——Windows 允许同端口多实例共存，请求会随机落到其中一个，
  表现就是时好时坏；`netstat -ano | findstr 8770` 看 LISTENING 有几行。）
- 页面显示「数据加载失败」：服务没起或端口不对 → 起服务后点右上角「刷新数据」。
- 数字是旧的：先跑 `fetch_perf.py` 出新快照，再点「刷新数据」（服务不缓存，`Cache-Control: no-store`）。
- **页面只显示最近几天**：2026-09-20 之前是"最新一份快照即真相"造成的（窄区间取数会把可见区间缩窄）。
  现在数据源是台账库，页面区间 = **库里有的全部日期**，这个坑已经不存在。
  真遇到只有几天，先看页头「库内数据 X ~ Y」——那就是库里只有这么几天，点「取数」补，或用
  `fetch_perf.py --from 投放开始日` 把历史全量拉一遍。
- 台账库还空着时 `/api/perf` 返回 503，页面上点「取数」即可。
