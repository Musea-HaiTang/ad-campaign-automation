# CSDN 创建任务工单 · 数据驱动自动化（执行层第 4 步）

> 与 `run_taskgroup.py`（建任务组）/ `run_ads.py`（建资源）/ `run_audience.py`（圈选用户）平级，
> 属于执行层第 4 步「**建任务工单**」。消费同一份整活动 YAML（`activities/{活动名}/配置/{品牌}{负责人}.yaml`）
> 里新增的 `taskOrder:` 段，**按 `audiences[]` 逐桶（7 个工单）**跑：任务名/主题按桶派生，其余字段（任务组/渠道/AB 组/日期/名单/曝光）各桶共用。dry-run 默认只填+校验+截图，绝不点「创建」。

## 定位与依赖
- 任务工单 = 1 个人群桶（`audiences[]` 1:1），把「任务组 / 渠道 / AB 三组资源 / 投放类型 / 计费价格 /
  投放日期 / 分发方式(用户名单) / 曝光上限」串成一条投放工单，审核通过后自动生成任务开始投放。
- **依赖链顺序**：`任务组(可能自动创建) → 资源 → 客群(圈选用户) → 任务名单(一键创建分发名单) → 任务工单`。
  本步骤要等**任务名单**（用户名单）生成后，`分发方式 = 分发名单 → 选某个用户名单` 才选得到；
  用户名单名与圈选任务名保持一致。
- **执行层门控**：开工前先确认「任务组名 / 子业务线 / 是否新建任务组 + 名字 / **投放日期 + 时间段**」，未给齐不进执行层。

> ⚠ **提交成功 ≠ 开始投放**（2026-09-24 实测）：提交后工单状态是**「未审核」**，
> 要**广告运营审核通过**才"自动生成任务、开始投放"。在那之前：**任务工单列表（界面）能看到它，
> 但取数接口 `taskPageList` 里没有它**（任务还没生成）——所以别拿取数接口当"建没建成"的依据（会得假阴性）。
> 2026-09-24 就因此虚惊一场：5 条 -6 工单提交成功、界面在位、状态未审核，取数接口查不到。
>
> 📍 **建完正确的核对位置**（用户 2026-09-24 明确）：后台 **分发管理 → 4.创建任务工单**
> （`/distribute/distApplyOrder/list`），按「任务名称」搜活动前缀 → 看那几行的「状态」列。
> 该列表每行右侧就是 `查看资源 / 审核 / 操作`——**审核通过才会生成任务、才开始有曝光**；
> 在这一步之前，任务工单列表是唯一能核的地方。
>
> ⚠ **回读核对只认完整任务名**（2026-09-24 修假通过）：老实现只搜**桶名**（如 `…A类`），
> 而老工单名字里本来就含这个串 → 新工单没建成也会打 ✓。现在要**完整任务名**命中，
> 名字被表格截断时退一步认「任务名末 6 个字符」（如 `工具-6`），两个都找不到才算失败。

## 数据来源（`taskOrder:` 段，新增于活动 yaml）
| 字段 | 说明 |
| --- | --- |
| `businessLine` | 业务线（事业部），显式选，如 `企业服务事业部` |
| `taskGroup` | 任务组：**选已有的**（不给就搜不到），如 `华为云码道-博客T0` |
| `taskName` | *(可选，脚本按 `audiences[]` 逐桶派生)* 工单任务名 = `{audiences[].taskName} · {topic}`，如 `{品牌}{负责人}-A类 · 模型部署 / GPU 基础设施` |
| `channel` | 渠道（穿梭框），如 `PC-博客-详情页-相关推荐T0` |
| `channelSizeId` | 该渠道的 尺寸/ID，如 `58`（正常点击渠道即可，58 自带） |
| `abGroups` | AB 测试三组：`对照组`(34) / `实验组1`(33) / `实验组2`(33)，合计 100。**逐桶优先**：`audiences[].abGroups` 有就用本桶的，没有才用 `taskOrder.abGroups` 兜底（全活动共用一组） |
| `price` | 计费价格（CPM）。**必填、由用户当期给**（2026-09-22 起不再固定数值，历史 20 / 30 都不套用） |
| `deliveryDate` | 投放日期=设置时间：`{mode: set_time, start, end, timeStart, timeEnd}`，如 `2026-09-09`~`2026-09-11`、时段 `8~23`（**起止日 + 时间段需用户提供**） |
| `distributionList` | *(可不填)* 用户名单名。优先级：`audiences[].distributionList` → `taskOrder.distributionList` → **本桶客群名**（正式跑走这条）。彩排拿后台现成测试名单验流程靠这个。填真名，别带后台显示的「… 用户名」后缀 |
| `exposureCaps` | 每日/每周/总曝光上限，默认 `100000 / 500000 / 500000` |

`subBusinessLine` 沿用 `audiences[0].subBusinessLine`；签呈号选填不填；渠道类型/资源平台/尺寸/产品页面/形式、
价格上限、频次控制、门槛频次控制、展示概率、用户排除等**默认不填**。

## 怎么跑
```powershell
# dry-run：填+校验+截图，点「取消」，不创建（默认）
.venv\Scripts\python.exe -u automation/scripts/run_taskorder.py --config activities/{活动名}/配置/{品牌}{负责人}.yaml

# 想看点窗口
--headed
# 真正创建（默认关闭，创建即入后台，谨慎）
--submit

# 只建指定桶（逐桶推进，如先只建 A 桶那一个工单）：加 --only
.venv\Scripts\python.exe -u automation/scripts/run_taskorder.py --config activities/{活动名}/配置/{品牌}{负责人}.yaml --only A --submit

# 断点账本不想要了，从头全跑
--reset-progress
```

**提交后回读核对（2026-09-14 加）**：`--submit` 点完『创建』不再直接记 `submitted`——
会**回读工单列表**按桶名（如 `火山引擎MediaKit-hang-A类`）查找，找得到才记 `submitted`，
查不到记 `warn`（下次重跑这一桶）。原因同 `run_audience.py`：老实现只看「弹窗关闭 + `.el-message`」，
后台没落库也算成功（圈选步骤已踩过两次假成功）。

**`--only A`（或 `--only A,C`）**：只建指定桶的工单，逐桶推进用（先建一个看效果再批量）。
截图落 `activities/{活动名}/日志/taskorder_shots/`：**每桶 1 张** = `taskorder_{id}.png`（视口图），7 桶共 7 张。**仅 dry-run（测试）截图；正式 `--submit` 不截图**。前置：python 3.12 装 `playwright`/`pyyaml`；
浏览器 `D:\playwright-browsers`；登录 profile `\.browser-profile`（cookie 过期需重登）。启动浏览器需提权。

**断点与止损**（与其他三个执行器同一套规矩，见 `../README.md`「设计原则」）：逐桶跑，每桶记一笔到
`../activities/{活动名}/日志/taskorder_progress.json`——**已创建的桶跳过**，只是彩排校验过的桶在正式跑时会重跑；
**彩排里步骤没全过的桶记 `warn`**（下次会重跑），只有 15 个步骤全 ok 才记 `done`；
某桶失败会关掉残留弹窗，**首桶失败 / 连续 3 桶失败即中止**（不再像以前那样 7 桶全挂也跑完 7 遍）；
结尾 `RESULT: OK / HAS_WARN / HAS_FAILURES`（只有 `OK` 返回 0）。

**新一轮重投前先归档 + 清账本（2026-09-21 踩到）**：账本键是 **`{任务组}|{桶id}`**，**不含 `nameSuffix`**——
同一个活动第二次起投时，上一轮那几条 `submitted` 会把整桶 **直接 `SKIP`**（本轮五桶重投第一遍彩排，
B/C/D 三个桶就被 9-14/9-18/9-20 的旧记录挡住了，只有 A/E 跑起来）。做法：
先 `Copy-Item 日志/taskorder_progress.json 日志/taskorder_progress.backup-<日期>.json` 归档，
再带 `--reset-progress` 重跑（先彩排、确认后再 `--submit`）。

## 已知坑
- **多选下拉（分发名单）选完不会自动收**（2026-09-22 优化）：`csdn_ui.close_dropdown()` 现在会**点弹窗正文
  左上角空白**把它收起（实测有效）。别点标题栏——被浮层盖住会超时；也别按 Tab——会把下拉又打开。
- **用户名单 / 资源下拉必须按「真名 + 分隔符」命中，不能按前缀**（2026-09-22 五桶对比批彩排踩到）：
  首屏拿到的是**还没被关键词过滤的全量选项**，纯前缀匹配会把同前缀的另一项抢走 ——
  选 `…A类 · AI 编程 / Agent 工具` 时命中了排在它前面的 `…A类 · AI 编程 / Agent 工具-4`，
  **工单静默挂错名单，日志里看不出来**（日志打的是配置里的意图值）。`csdn_ui._pick_option` 已改成
  只认「完全相等」或「真名 + 分隔符（空格 / 括号 / 制表符）+ 类型标签」，等不到就抛错
  （消息里带看到的选项）——**宁可报错也不选错**。改完真机复验：老名单回读命中、不再误选 `-4`。
- **提交按钮叫「提交」，不是「创建」**（2026-09-14 真机踩到）：按钮名写错 → 16 项字段全 ok、
  界面也没报错，**实际什么都没建还返回成功**。修法三条：按钮名改对 + **找不到按钮记 warn 不再当成功** +
  提交后按**桶名回读列表**核对（`verify_created`）。顺带给了 `--only` 逐桶推进。
  （这条原记在活动细则，2026-09-20 按归位原则挪进本文件。）
- 业务线/子业务线/任务组都是 **el-select，选项异步加载**，须等选项出现再点（`csdn_ui._pick_option` 轮询 6s；找不到会把「看到的选项」列进报错）。
- 任务组/用户名单选项极多（任务组 337 项），**先搜再选**（`csdn_ui.search_select`）。
- AB 资源/用户名单搜索框 `readonly`：点外层容器打开，用 `page.keyboard.insert_text` 输入（CJK 也能输），再点下拉项。
- **2 资源桶：权重必须 50/50**（2026-10-08 火山九批 D 桶踩到）：生成时按 3 资源的 `34/33/33` 填了
  `34/33`，点提交被后台拒：**`资源流量占比累计为67%，请将流量占比总量调整为100%`**。
  修法：按**本桶资源条数**算权重（2 条 = 50/50）。生成后先跑 `check_batch_plan.py` 能提前挡掉。
- **2 资源桶：AB 第二个位置必须是"实验组1"**（同上，KIRO 四批 B 桶踩到）：后台三行行名固定
  `对照组 → 实验组1 → 实验组2`，只能顺序填满；把第二条标成"实验组2"会报 **`实验组1资源ID不能为空`**。
  修法：2 资源桶一律 `对照组 + 实验组1`；如果这条文案是从"实验2"谱系延续的，**按槽位改名**（`…B类 · 实验1-4`），
  并在台账记 lineage（`实验2-2 → 实验1-4`）。⚠ 已经建出来的旧名字资源会变成孤儿（没绑任何工单），要么留着不管、要么在后台手动删。

## 性能（2026-09-22 实测）

一条工单（A 桶）彩排 **24.6 s → ~12 s**；5 桶全量彩排 **110~117 s → ~58 s（约 -50%）**。
改的全是"等待"，判断逻辑与回读校验一点没动：

| 改动 | 位置 | 效果 |
|---|---|---|
| 多选下拉（分发名单）选完**点弹窗正文空白**收起 | `csdn_ui.close_dropdown()`（`search_select()` 末尾调用） | 那次 `_wait_dropdown_closed` 原来把 6 s 超时等满（实测 6.01 s）→ 现在 0.32 s |
| 「分发方式 → 用户名单」由死等 600 ms 改成**等输入框可见**（150 ms 轮询、最多 8 s） | `run_taskorder.set_distribution()` | 该步骤 11.1 s → 3.5 s |
| 穿梭框填完搜索词后的 500 ms 去掉（后面本来就有 `expect(复选框).to_be_visible`） | `csdn_ui.transfer()` | 渠道步骤 0.8 s → 0.2 s |
| `_open_dropdown()` 首次点击超时 **2000 → 300 ms**（readonly 输入框被 `.el-select__tags` 盖住，必然点不中） | `csdn_ui._open_dropdown()` | 5 桶合计 11.5 s → 3.0 s |
| 投放日期注入后的 **1200 ms 死等 → 轮询 `td.active` 格子数 = 期望值**（100 ms 步长、上限 4 s） | `run_taskorder.set_delivery_date_by_inject()` | 该步骤 1.7 s → 0.5 s（回读 `选中格=352` 不变） |
| AB 资源弹窗「点完组卡片后」的 500 → **150 ms**（紧随其后有 `expect(资源框可见)` 兜） | `run_taskorder.pick_ab_resource()` | AB 三组 6.8 s → 4.0 s |
| `search_select()` 的两个垫等（250 ms 就绪 + 400 ms 等过滤）→ **条件**：① 等检索框就绪（上限 0.8 s + 150 ms 兜底）② 直接**轮询目标项**（步长 300 → **100 ms**） | `csdn_ui.wait_input_ready()` / `_pick_option(interval=…)` | `search_select` 平均 5.5 s → 1.8 s |
| **换序**：曝光上限 ×3 提到「分发方式 / 用户名单」**之前**，用户名单**放最后一格**（2026-09-22 用户建议） | `run_taskorder.run_bucket()`；`set_distribution()` 用 `search_select(..., close=False)` | 少付一次"收下拉"（每桶 ~0.5 s）；名单下拉只盖住曝光那几格，不再影响后续字段。**几何实测**：下拉浮层 y 1054~1331、提交按钮 y 1395 → **不重叠**；万一将来挡了，点提交/关窗那一下会先 `close_dropdown()` 再重试 |

⚠ **两条试过但回退**：
1. 把「下拉打开后 / 填完值后」的 settle 等待**直接删掉** —— 实测反而更慢（24.6 s → 30.6 s）：这些垫等在等
   **后台的远程过滤结果**，删掉就会以 300 ms 步长空轮询。**要换就换成"等目标选项出现"的条件轮询**（已按此实现）。
2. AB 资源弹窗「**填完资源名后**」的 500 ms 降到 150 ms —— 实测出现一次 **5.73 s** 的轮询空转（赶在远程查询返回前冲进去了）。
   该处**保留 500 ms**：它是在等后台，不是冗余。
3. AB 资源选择的轮询步长 300 → 100 ms —— **没收益**：多读 27 次选项快照（每次 ~20 ms），平均反而 0.19 → 0.34 s，
   还撞上一次 4.38 s 的波动。回退到默认 0.3 s。
4. `ui.select()` 里"等下拉收起"的 `_wait_dropdown_closed` 去掉（每次省 ~0.3 s）—— **不安全**：5 桶里出现一次
   「子业务线」点击被上一个下拉的残留浮层挡住、直接超时 8 s。**这 0.3 s 是安全垫，不是浪费**，已加回。

### 还能再快（未做，按收益排序）

1. AB 资源选择仍用 300 ms 轮询步长（`pick_option()` 默认值）——可降到 100 ms，看后台是否稳定（收益 ~1 s/单）。
2. `ui.select()` 每次 ~0.77 s（业务线/子业务线/分发方式各一次）：`_wait_dropdown_closed` 的地板是 ~0.31 s（`expect` 轮询），

3. AB 资源弹窗「填完资源名后」的 500 ms：想再压需要先确认后台过滤的 P95 延迟（现在保留是踩过坑）。

### ✅ 提交前闸门（2026-09-22 修）

原来 `--submit` 路径**不看"步骤是否失败"**：16 步的成败只写进 `steps`，彩排分支会据此记 `warn`，
正式分支却直接往下点「提交」——某一步失败（如那次「子业务线」点击超时）就会建出一条**缺字段的工单**，
而 `verify_created()` 只查"工单名在不在列表里"，查不出字段缺失。

现在 `run_bucket()` 在正式提交前加了一道闸：**有任一 fail 步骤 → 关弹窗、`return WARN`、不提交**
（账本记 `warn`，下次重跑这一桶）。真机安全验证（`_tmp/probe_submit_guard.py`：故意让「计费价格」失败 +
拦截提交按钮点击）：日志打出 `!! 有步骤未通过（计费价格、投放日期、分发方式）→ 不提交`，
`run_bucket` 返回 `warn`，**提交点击次数 0**。

> 顺带暴露：**一步失败会触发 `ui.dismiss_dialogs()` 把整个表单关掉**，导致后面所有步骤连环 fail
> （本次就出现「计费价格 fail → 投放日期 / 分发方式 跟着 fail」）。这是既有行为，不是本次改动引入；
> 有闸门兜住之后最坏结果只是"这桶不建、等重跑"，不会再漏建半成品。

## 投放日期 + 时间段：**传参优先，点击兜底**（2026-09-14 定，用户认可）

老实现是**逐格点击**：29 个日期行 × 16 小时 = 464 次点击（约 26 秒/桶），而且只按"日号"点，
跨月区间会点错（曾把 `09-14~10-12` 点成 `09-12~09-14`）。

现在默认走**传参（注入表单数据）**：

- **字段格式**（来自后台详情接口 `tTaskInfo/detailPage`，可用列表「查看」录到）：
  `dateLimits = [{timespan: ["开始日","结束日"]}]`、
  `hourLimits = [{putDate: "2026-09-14", times: [8..23]}, …每天一条]`（`times` 是**数字**数组）；
- **做法**：在页面的 Vue 组件树里找到持有 `dateLimits`/`hourLimits` 的表单组件，`$set` 这两个字段 → 界面自动渲染；
- **提交前自检**：回读日期输入框 + 数 `td.active` 格数，对不上就抛错（**绝不带着错日期提交**）；
- **兜底**：注入抛错时，先把 `dateLimits`/`hourLimits` 清空（避免注入一半的状态把回退点击"点反"），
  再走原来的点击实现 `set_delivery_date_by_click()`；入口函数 `set_delivery_date()` 负责这个切换，日志里会打 `[传参]` 或 `回退点击方式`。

实测：传参 **1.3 秒** vs 点击 **26 秒**；单桶整体 **27 秒** vs 45~50 秒。
代价：注入依赖页面 Vue 内部结构（后台改版可能失效）——**失效也只是回退到点击，不会中断**。
