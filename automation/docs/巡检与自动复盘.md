# 巡检与自动复盘（定时任务怎么配、怎么触发）

> **管什么**：Codex 定时巡检这个**定时任务本身**——怎么配、什么条件下触发复盘对话、对话里必须怎么回、排查踩过的坑。
> **不管什么**：判定规则与门槛在流程文档 §9.3 / 各活动 `配置/判定门槛.yaml`；取数与看板在 [`fetch_perf.md`](fetch_perf.md) / `web/README.md`。
> **谁什么时候读**：要改巡检频率 / 通知策略 / 触发条件，或巡检"看起来没动静"时。
>
> 2026-10-09 从流程文档 §9.1 搬来（用户定：流程文档只留"现在该怎么做"的规则，运维配置归执行层文档）。

## 1. 这个任务是什么

- **Codex 定时任务「广告数据巡检」**：**heartbeat 类型、每小时整点、时段 10:00–18:00**（`FREQ=HOURLY;INTERVAL=1;BYHOUR=10,11,…,18;BYMINUTE=0`），挂在 ad_management 的**专用对话**上。
- **它只读台账库、不自己取数**（2026-09-28 改——取数归看板服务，见 §6）：对每个有 `配置/判定门槛.yaml` 的活动跑 `judge_batch.py --write --todo`（清单追加、待办覆盖），结尾原样抄脚本那行 `STATUS: 巡检 …`。
- **通知策略：每次都通知**（2026-10-09 用户定，原来只在失败时通知）——只在上班时间用，每小时一条不算吵，而门槛触发要靠它提醒。**时段同理只排 10:00–18:00**（用户 9:30 上班、18:30 下班）。

## 2. rrule 的两个坑（实测）

- `BYHOUR` **只认逗号列表，不认 `10-18` 区间**——写了会被判"没有未来运行"。
- **不加 `BYMINUTE=0` 就不是整点**：分钟会继承这条任务自己的锚点（当时存成 11:58，于是一路 12:58 / 13:58）。
- **改完必须读回 `automation.toml` 核对**。

## 3. 到门槛自动起复盘对话

**触发条件只有一个：某桶累计曝光 ≥ 门槛**（= `STATUS` 行「可判：」后面出现了那个桶）。**不看点击**——点击是复盘对话里才看的事，不参与触发判断。

**去重**：同一活动 + 同一桶，**当天最多起一次**（巡检自己在 `数据/判定/已触发复盘.md` 里记一行）；当天已起过但该桶还没出**新文案**、或该桶又攒了更久的数，**不重复起对话**（用户口径"一天最多一次 + 要尽快处理"：曝光是累计值，放久了数会偏，所以复盘产物开头要记触发时刻的快照）。

**一轮一条，不按桶拆**（2026-10-09 用户定）：巡检先把本轮所有活动里「到门槛 + 今天没触发过 + 数据新鲜」的桶**汇总成一张清单**（逐桶对着「可判」核一遍，别再漏——13:56 那轮漏过一个 KIRO C），然后**只起一条对话**装下全部，title 形如 `复盘 · 2026-10-09 14:00 · 火山 C/E桶 + KIRO B桶`；清单为空就不起。一个桶里的报告文件仍然是每个桶一份（`复盘-{日期}-{桶}桶.md` 不动），合并的只是**对话**。

**这条对话同时是这批桶的执行落点**（2026-10-09 用户定：「我后续需要在那个对话里面直接执行任务」）：用户看完文案确认后，会**直接在那条对话里**下指令走下一步（定稿 → 整活动 YAML → 建资源 / 工单 → 新批上线后下线旧批）。所以复盘回复**开头先列清「本轮触发桶清单 + 每个桶的报告文件路径」**，后面用户说「建批 / 建工单 / 下线」时要认得出是哪个桶、用哪份配置，**不要另开对话**接着做。

**起之前先判数据新不新**：读 `GET http://127.0.0.1:8770/api/fetch/status?activity=<活动id>`（只读 HTTP，不碰浏览器）。读不到（看板服务没开）或上次取数距今 > 40 分钟 → **不起对话**，只在通知里写「看板服务没在跑」/「数据待刷新」。

**起的那个对话干什么**：按写死的 prompt，读判定清单 + 台账经验 → 写 `物料/复盘/复盘-{日期}-{桶}.md` → 出下一轮文案草案 → **停在文案这一步等人确认**（不建 issue、不推代码、不碰后台）。将来要全自动化，只需摘掉这道"停在文案"的闸门。

### 落点对话必须是"自己新建的普通对话"（2026-10-09 实测，已修）

派生出来的线程（预置内容里带 `<codex_delegation>`）**没有 app 那套工具**——12:58 那轮到门槛（火山 C/E、KIRO C）却起不了对话就是这个原因。换成普通新建的对话 **「广告数据巡检 · 落点」**（`01a11f2c-032c-7ad1-b21a-278655da1b21`）后当场验通。

**那个落点会话里有的工具**：`create_thread` **有**；`list_projects` / `wait_threads` **没有**——所以 prompt 里 ad_management 的 `projectId` **写死**（`edeebda7-79f1-4aea-b38d-f52abf7d8deb`），建完**不要**等它跑完。

## 4. 通知格式（只留三块）

2026-10-09 用户定"看不清重点，重写成这个样子"：

1. **【要你动手】**：一个桶一行，`活动名 + 桶号：留 … ｜ 下 … ｜ 补 N 条`，**不写曝光/点击数字**；上一轮已报过还没处理的桶**不重述动作**，只写一行「同上（11:40 已报，仍未处理）」。
2. **【提醒】**：没有就整块不出现（数据待刷新 / 看板没在跑 / 起复盘对话失败 / 已起复盘对话 / 今天已触发还没出结果）。
3. **【状态】**：每个活动一行，**必须把活动名补在最前面**——脚本那行 `STATUS:` 里**不含活动名**，两个活动的内容长得一模一样，这是上次"看不清楚"的主因；`可判：` 后面那串括号解释删掉，只留桶号。

## 5. 复盘对话的回复格式（2026-10-09 用户定死）

> 用户原话：「我需要看到很清晰的信息…修改前和修改后的文案我需要看到，这是最重要的」。

- **① 【达标】**一行（曝光/点击/门槛；未达门槛的只用一行带过）
- **② 一个桶一段**，段首 `### <活动> · <桶> 桶（<曝光> 曝光 / <点击> 击 · 门槛 <门槛>）`，紧接一行 `改什么：<资源> 留 ｜ <资源> 下 → 下一轮 = N 条幸存 + M 条新文案`
- **③ 每条文案一块，①②③ 连号排下去**（跨桶连着数）：`序号 动作 · 槽位（CTR，备注）` → `改前`（标题 / 摘要 / 飘红，**逐字抄原文，不许概括**）→ `改后`（标题 / 摘要 / 飘红，标题没动写「（不动）」）→ `卡点：<为什么这么改，一行>`（文案正文用反引号包、飘红用 `**加粗**`；「本桶最高」只写在 CTR 最高的那条上）
- **④ 【问你】**分点 → **【产物】**文件名
- 过程叙述（读过什么、几点快照、历史曝光怎么变）**一律留在报告文件里**，不写进对话；存疑账最多一行；边界说明最多一行。报告文件本身照旧写全（判定快照 / 全史 / 存疑 / 草案 / 待办）。

## 6. 跟看板服务的关系

- **看板服务自带自动刷新**（2026-09-28 起，数据新鲜度不靠 Codex）：`web/app.py` 每 **30 分钟**（`--auto`，给 0 关掉）自动刷「今天」的实时数；**每天第一次先跑一次「取数」**把昨天的终值固定下来。**不配开机自启**（放假不需要，上班自己开）。
- ⚠ **巡检不能与看板服务同时取数**（一个登录 profile 只能被一个进程用）——所以取数交给看板服务，巡检只做"读库出建议"。
- ⚠ **命令行脚本（建批 / 取数 / 体检 / 重新登录）也和看板服务抢 profile**：要用浏览器时 **AI 自己先停看板服务**（关窗口 / Ctrl+C），跑完提示用户重开（用户 2026-09-29 授权"需要用的时候直接关，不用问"）。
- **巡检只在 Codex 开着时才会跑**：Codex 没启动（放假没开电脑）就没有产出，`数据/判定/待办.md` 停在上一次的时间——**这本身是正常的**。判断它活着没：看 `数据/判定/待办.md` 的时间戳，或看绑定那条对话里每次都会有一行 `STATUS: 巡检 …`。
