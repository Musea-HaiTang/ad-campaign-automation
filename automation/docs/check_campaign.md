# 活动体检 · `check_campaign.py`（只读）

> 给一份**整活动 YAML**，核对后台这 5 类对象是否都在、**名字是否一字不差**：
> 任务组 1 ｜ 资源 N×3 ｜ 客群 N ｜ 分发名单 N ｜ 任务工单 N。
> 查客群时**顺带做「达标体检」**（读「日均曝光(预估)」判达标），见下面「客群达标体检」一节。

## 为什么有它

2026-09-14 火山引擎MediaKit 那轮真实创建里，连续踩到"脚本报成功、后台其实没有"：
圈选 A/E 假通过、工单提交按钮名写错（16 项全填对却没提交）、投放日期跨月点错、
分发名单被"圈选用户中"挡住……本质都是**"我以为建成了"**。

这个命令就是那句"我确认一下"：**交付前、复盘中、怀疑时**，一条命令看后台现状。

## 怎么跑

```powershell
# 全查（任务组/资源/客群/名单/工单）
.venv\Scripts\python.exe -u automation/scripts/check_campaign.py --config activities/{活动名}/配置/{品牌}{负责人}.yaml

# 只查某几类：taskgroup,ads,audience,list,order
... check_campaign.py --config <yaml> --only ads,order

# 只做客群达标体检（默认口径：目标 2 万 / 底线 1 万，可改）
... check_campaign.py --config <yaml> --only audience
... check_campaign.py --config <yaml> --only audience --min-exposure 10000 --target-exposure 20000

# 想看浏览器窗口
... check_campaign.py --config <yaml> --headed
```

- **退出码**：全部找到 = 0；有缺失 = 1（可以串进别的流程当门禁）。
- **只读**：只填筛选框 + 点「查询」，**绝不点** 新建/创建/确定。
- 名字一律问 `naming.py`（唯一实现），不手写——后台按精确字符串匹配，差一个字符就是没有。

## 客群已删、分发名单还在 → 不算缺失（2026-09-23 用户口径）

口径原话（用户 2026-09-18）：**"这个没关系呀，只要分发名单还在就行"**。

重投 / 换词之后经常把**圈选任务删掉、只留分发名单**（2026-09-23 火山引擎MediaKit D 桶就是这样）。
工单认的是**分发名单**，投放不受影响；但体检原来会报 `✗ 缺失 [客群] …`、退出码拉成 1——
一直红着的门禁等于没有门禁。

现在的判定：

| 客群 | 分发名单 | 结论 |
|---|---|---|
| 在 | 在 | `✓` |
| **不在** | **在** | `ⓘ 客群已删、分发名单在，不算缺失`（只在报告里提一句；**不影响退出码**） |
| 不在 | 不在 | `✗ 缺失`（真缺失） |

- 客群缺失时会**补查一次**「分发名单」页签来核这一条（`--only audience` 也会补查）；这次已经查过分发名单就直接用，不重复开页。
- 提示里带一句"下次改词重圈时按新任务走"——客群没了就不能拿旧客群当输入，重圈要按新任务来。
- 实现是一处纯函数 `check_campaign.split_deleted_audiences()`，单测 `tests/test_check_campaign.py::DeletedAudienceTest`。

## 客群达标体检（2026-09-21 加）

查客群时顺带读「圈选用户 → **博文圈选任务**」列表的四列，逐桶判达标：

```
实际圈选博客ID数 | 日均点击(预估) | 日均曝光(预估) | 日均pv(预估)
```

判定（口径默认**目标 20000 / 底线 10000**，由用户当期给；`--target-exposure` / `--min-exposure` 可改）：

| 日均曝光(预估) | 判定 | 动作 |
|---|---|---|
| ≥ 20000 | 达标 | 继续 |
| 10000 ~ 20000 | 过线未达标 | 记一笔，下轮加词 |
| < 10000 | 不达标 | **改词重投**（客群重名建不了，重投带后缀） |
| 读不到（`—`） | 待后台 | 后台还在「圈选用户中…」，等算完再跑一次 |

- ⚠ 这几项**建完、等后台算完才刷出来**——**创建弹窗里没有**，所以体检只能在创建之后做。
- ⚠ **`预估圈选总数` 不是曝光**：它数的是博文ID个数，不区分有没有流量。经验比例
  `日均曝光(预估) ≈ 实际圈选博客ID数 × 0.33~0.63`（曝光≥1 时）。
- 达标只**报数**，**不影响退出码**（退出码仍只表示"对象在不在"）；不达标不会让命令失败。

## 提速（2026-09-22）

- **开页改成条件等待**：原来每类对象都是三段固定死等（`goto` 后 1500ms + 点菜单后 1800ms + 切页签后 1800ms），
  现在统一等"下一步真要用的东西"——侧边菜单 / 页签 / **筛选框**出现（各 10~12 秒上限）。
  **实测（2026-09-22，五类全查，墙钟含浏览器启动）：32.0 秒 → 25.7 秒（省 6.3 秒）**。
  比原先估的 15 秒少：换掉死等之后，每页剩下的 3~4 秒是**页面真的在渲染**的时间，省不掉。
- **点「查询」交给共用层 `csdn_ui.click_query()`**：**只在这次查询真的转圈过**（`.el-loading-mask` 出现 → 消失）时
  提前返回；没看到遮罩仍按原来的固定底（2200 / 2500 / 1600ms）收尾——**宁可慢一点，也不能读上一次查询的旧数据去判达标**
  （2026-09-21 踩过）。所以"查询"这步的耗时**不一定**变短（看后台有没有加载遮罩），但**不会变慢**。
  - **2026-09-23 修**：原来数的是"DOM 里有没有遮罩元素"，而**加载完遮罩元素留在 DOM 里、只是 `display:none`**
    （真机实测：圈选页 0.5 秒就答完、工单页要 2.5 秒）→ 永远判成"还在转圈"：每个查询白等 3 秒、
    误报"这次数可能是旧的"，而且那个 3 秒兜底几乎贴着工单页的真实耗时（真慢一点就会读到旧数）。
    现在只认**看得见的**遮罩（`.el-loading-mask:visible`）；遮罩**一直看得见**才等到 `timeout`，并说明数可能是旧的。
    复验（同一条命令）：墙钟 14.7 → 10.5 秒（含浏览器启动）、遮罩警告 0 条、四个数字与改前**逐行一致**。
- 客群/名单页的读数轮询（`audience_metrics.wait_ready`，间隔 10 秒、上限按 `--verify-timeout`）**没动**。

## 页面层归属（2026-09-23 架构体检 01）

「翻开列表页 → 填筛选 → 点查询 → 按名字取行」这套原先在本脚本里自写一遍（`_fill_visible` / `_query` /
`read_page`），与圈选、分发名单、任务组三处各写一遍、判据还不一致（2026-09-22 因此把 5 个已建名单报成未找到）。
现在四条列表页 + 资源页的筛选/查询全走 `scripts/list_page.py`：

- `read_page()` 只负责「`ui.goto` 目标地址 → `list_page.open_list(...)` → 填筛选 → `lp.query()`」，返回**页面把手**；
- 客群那一页的筛选字段（日期窗 + 名称 + 创建人）仍归 `audience_metrics.apply_filters(lp, ...)`；
- 体检仍然**只读**：`list_page` 里没有新建/提交/确定这类动作。

## 每类怎么查（真机勘察 2026-09-14）

| 类别 | 列表页 | 用什么筛 |
|---|---|---|
| 任务组 | `#/distribute/taskteam/team` | 输入框 `请输入任务组名称` ← `campaign.taskGroupName` |
| 资源 | `#/distribute/resource/list?channelType=page` | **下拉 `请选择任务组`** 选本活动任务组 → 一次列全 |
| 客群 | `#/distribute/distUser`（侧边菜单「圈选用户」→ 页签 `博文圈选任务`） | 输入框 `请输入圈选任务名称` ← 活动前缀 |
| 分发名单 | 同上 → 页签 `分发名单` | 输入框 `分发名单模糊查询` ← 活动前缀 |
| 任务工单 | `#/distribute/distApplyOrder/list` | 输入框 `请输入任务名称模糊查询` ← 活动前缀 |

## 坑（都已固化进脚本）

1. **资源列表的模糊查询必须给具体名字**：用共同前缀（如 `火山引擎MediaKit-hang`）查会返回 **0 行**，
   给完整名或 `A类 · 对照` 都能命中。所以资源首选**任务组下拉**筛（一次列全，15 条约 8.6 秒），
   下拉不可用时自动回退"逐条精确查"（约 35 秒）。
2. **输入框有隐藏副本**（element-ui 固定列/克隆）：必须挑**可见且宽度>0** 的那一份，否则填了个假框。
3. **进「圈选用户」要先点侧边菜单**再点页签，直接 `goto` 页签不生效。
4. **一条记录被拆成三份 DOM 行**（Element UI 冻列）：主表放「日期 + 四个数 + 关键词 + 创建人」、
   左冻列放「圈选任务ID + 名称」、右冻列放按钮。按**行号**把三份合并成一行再解析（`_merge_cells` → `_row_metrics`，
   单测见 `../tests/test_check_campaign.py`）；单看任何一份都认不出这行。
5. **客群列表默认只筛最近 4 天**（真机 2026-09-21：`开始日期=09-18 / 结束日期=09-21`）——
   老客群会被挡在列表外，体检误报「客群缺失」。查客群前脚本自动把开始日期拉到 `2020-01-01`（`widen_dates=True`），
   日志会打一行 `[日期窗] 2020-01-01 ~ 今天 ✓`。
   > 9/18 记的「重投轮次的客群在列表里查不到」，真因多半就是这个默认窄窗，不是后台没建。
6. ⚠ **资源列表也有默认创建时间窄窗**（真机 2026-09-22：`09-19 ~ 09-22`，共 9 条）——9-14/9-17/9-18
   建的老资源被挡在列表外，体检误报「资源缺失」（当天连报两次×15 条）。放宽开始日期后翻完 2 页
   （该任务组共 33 条）**15/15 精确命中**。**脚本目前还没放宽资源页的日期窗——查资源前请手工放宽或按本条预期读结果。**
7. ⚠ **名字检查目前是子串匹配**（`name in 页面正文`）：`…A类 · 对照` 会被 `…A类 · 对照-4` 命中
   （2026-09-22 踩到）→ 既可能**假阳性**（老对象已不在也报「在位」），也可能漏掉真缺失。
   查具体名字时请以**逐条精确查**为准（见第 1 条）。

## 名字来源（2026-09-18 修）

- **客群名 / 分发名单名**：优先取 `audiences[].distributionList`（`run_taskorder.py` 选名单就是按它选的），
  **没写才回落** `naming.order_task_name()`（`{桶名} · {topic}` + `nameSuffix`）。
  起因：B/C 桶 2026-09-18 重投**复用了旧名单**（名字不带 `-2`），按命名规则算会在后台找一个不存在的
  `…-2` 名字 → 误报「分发名单缺失」。
- **资源名 / 工单名**：永远按命名规则（`naming.py`，含 `nameSuffix`）——重投建的就是新对象，
  复用旧名单 ≠ 复用旧工单。
- 单测：`../tests/test_check_campaign.py`（纯函数，毫秒级；覆盖「复用旧名单 / 没写 distributionList / 普通轮次 / 工单名不受影响」）。
- ⚠ **2026-09-18 记的「重投轮次客群查不到」已解释**：2026-09-21 复核是同一天实测——客群一条没少
  （5 条全在，含 `…-D类 · 短视频 / 内容生产-2`），此前查不到是**列表默认只筛最近 4 天**（见「坑」第 5 条）。
  脚本已自动放宽日期窗，正常轮次不必再退化成 `--only ads,list,order`。
