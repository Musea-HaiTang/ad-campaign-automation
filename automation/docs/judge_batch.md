# 判定清单（`judge_batch.py`）· 新判定机制的执行层

> 机制出处：[`../../ad_output/流程文档/CSDN广告投放自动化流程.md`](../../ad_output/流程文档/CSDN广告投放自动化流程.md) §9.3（用户 2026-09-24 定）。
> 门槛配置（**业务口径，唯一真源**）：`activities/{活动名}/配置/判定门槛.yaml`。
> **这个脚本只读台账库，不碰后台、不创建不删除**——下线只有用户本人（或运营）能做。
> **规则本体在 `../scripts/judging.py`**（2026-09-28 收口）：命令行清单和**看板**（`perf_payload` 的
> `judge` 字段，页面上「本批 · 判定」那三列）用的是**同一份**判定函数，不许各写一遍。

## 它回答一个问题

**这一轮跑到现在，该留谁、该下谁、下一轮要补几条新文案？**

## 用法

```powershell
# 只打印
.venv\Scripts\python.exe -u automation/scripts/judge_batch.py --config "activities/{活动}/配置/{活动}-hang.yaml"
# 同时追加到 activities/{活动}/数据/判定/{日期}_{批次}.md
.venv\Scripts\python.exe -u automation/scripts/judge_batch.py --config "activities/{活动}/配置/{活动}-hang.yaml" --write
# 覆盖写 activities/{活动}/数据/判定/待办.md（一眼扫的那份；定时巡检用）
.venv\Scripts\python.exe -u automation/scripts/judge_batch.py --config "activities/{活动}/配置/{活动}-hang.yaml" --todo
```

- `--config` 传**活动的基础 YAML**（`配置/{活动}-hang.yaml`）就行：脚本靠它定位活动目录 →
  读 `配置/判定门槛.yaml`、写 `数据/判定/`，并自己扫 `配置/` + `调整/` 推批次。
  ⚠ **判哪个批次由脚本自己算**（2026-10-08 桶独立）：**每个桶判它自己最后一次建批**那一批，
  规则在 `campaign.bucket_current()`（只写了 audience、没挂资源的批次不算），看板用的是同一份；
  `判定门槛.yaml` 里原来的 `batch` / `batchConfig` 两个字段**已删**。
- 不开浏览器、不联网：读的是台账库（`activities/_db/投放数据.db`）里**该批次任务的资源读数**。
- **结尾永远打印一行 `STATUS: …`**（如 `巡检 17:12 ｜ 各桶独立 ｜ A 0/0 · … ｜ 可判：无`）——
  定时巡检**原样抄这一行**当结尾状态，别再让模型自己编（2026-09-28）。
- 纯逻辑（`judge()` / `todo_text()` / `status_line()` / `next_batch()`）有单测：
  `automation/tests/test_judge_batch.py`（手写读数，不开库、不开浏览器）。

## 判定口径（与流程文档 §9.3 一致）

| 工单累计曝光 | 点击 | 结论 | 动作 |
| -- | -- | -- | -- |
| < 门槛 | — | 未到门槛 | 继续观察 |
| ≥ 门槛 | **实际点击率 ≥ 千三**（点击 ÷ 曝光 ≥ 0.3%） | 达标 | 该桶停测试：**留有点击的前 N 条**（3 资源桶 2 条 / 2 资源桶 1 条，看点击实际情况）作长期单，**不补新文案** |
| ≥ 门槛 | 有点击但未达标 | 未达标 | 有击的留下（3 资源桶最多 2 条、2 资源桶 1 条，**按点击多的优先；点击并列时比点击率**，2026-10-09 用户定），零点击的下线，幸存 + 新文案凑满下一轮 |
| ≥ 门槛 | 0 | 全不合格 | 整批换新文案 |

门槛写在各活动的 `配置/判定门槛.yaml`（**唯一真源**，按活动各一份；默认档）：A **3,000** ｜ B·C·E 1,500 ｜ D 1,000（D 是 2 资源，50/50）。
达标线算的是**实际点击率**（用户 2026-09-30 定）：`need_click = 当次实际曝光 × 0.3%`（向上取整），
**不是"门槛 × 千三"那个固定击数**——曝光跑过门槛之后两者会脱钩；曝光**正好压在门槛**时的参照值：A 9 ｜ B·C·E 5 ｜ D 3。

> **下一轮批次号 = 当前批次号 +1**（`-6` → `-7`）。名字里的数字是"第几批"，**越大越新**——
> 不是整数加一（那会算出 `-5`，指向已经下线的老批次）。

## 数据从哪来、什么时候准

- 读的是**该批次任务的最新资源读数**（资源级接口给的是**累计值**，所以最新一条 = 本轮整段累计）。
- 要它有意义，得先跑过 `fetch_perf.py`（定时巡检每 2 小时跑一次，见 `fetch_perf.md`）。
- ⚠ **工单「未审核」时读不到**：后台要运营**审核通过**才生成任务、才开始有曝光；在那之前这个脚本会显示
  「无在跑工单」（不是 bug，也不是失败）——正确核对位置是后台「分发管理 → 4.创建任务工单」的列表。
- ⚠ **别拿 `taskPageList` 接口判断"工单建没建成"**：它滞后（新工单要生效后才进列表），会得假阴性。

## 输出的两份文件

| 文件 | 性质 |
| -- | -- |
| `数据/判定/{日期}_{批次}.md` | `--write` **追加**：每次巡检的完整判定表 + 逐条动作 |
| `数据/判定/待办.md` | `--todo` **覆盖**：永远只显示当前待办，给人一眼扫（2026-09-28 起**由脚本生成**，不再由提示词手写） |

## 交接给下一步

1. 先把结论补进 `ad_output/memory/数据台账.md`（该轮每条文案的曝光/点击/结论）；
2. 有值得总结的规律 → 写 `ad_output/memory/数据经验.md`（**只写经验**，带数据依据）；
3. 需要动手的：下线老工单（**用户手动**）+ 写下一轮新文案（批次号 +1，见流程文档 §9.3 两条纪律）。

## 门槛里没有的桶 → 当场报错（2026-10-12 加）

**症状**：多产品活动加了一个新产品，新建的桶**不进判定清单，也不报错**——既不判、也不会触发自动复盘，
悄没声地卡住（看板同样拿不到门槛，那一行是降级的）。

**根因**：本脚本只遍历 `配置/判定门槛.yaml` 里 `buckets` **列出来的**桶；桶没写进去就查不到。

**现在的行为**：`load_thresholds()` 会拿这份门槛跟 YAML 里的 `audiences[]` 对一遍，**缺了就 `SystemExit`**，
并在报错里直接给出该补的那一行：

```
判定门槛.yaml 缺这些桶：TokenHub
  → 给每个桶补一行（起手值 3,000 = 每条约 1,000 曝光…）：
      TokenHub: {threshold: 3000, resources: 3}
```

> 这是**故意的强烈失败**：宁可当场炸，也不要"看着正常、其实这个桶永远不判"。
> 配套动作写在流程文档 §1.3「加新产品时的两个额外动作」。
