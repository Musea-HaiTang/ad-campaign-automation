# 执行层全流程（把整活动 YAML 变成后台对象）

> **管什么**：执行层**每一步做什么、用哪个脚本、读哪份文档、在哪停下**。
> **不管什么**：YAML 字段规范在 [`../campaigns/README.md`](../campaigns/README.md)；所有脚本共用的命令、恢复、日志和结果口径在 [`脚本通用约定.md`](脚本通用约定.md)；脚本内部实现与踩过的坑在各 `run_*.md`；投放后的取数 / 判定 / 复盘在流程文档 §9。
> **谁什么时候读**：拿到用户确认的整活动 YAML 之后，**每一次建批**（新活动首投或复盘重投）都从这一页开始。
>
> 上游：流程文档 §8（生成整活动 YAML + 执行层前置门控）。执行层总览与设计原则见 [`../README.md`](../README.md)。

## 0. 一句话 + 三条安全口径

一份**整活动 YAML**（`activities/{活动名}/配置/{品牌}{负责人}.yaml`）→ 用 `--config` 指过去 → 按依赖顺序跑脚本 → 后台依次出现 **任务组 / 资源 / 客群（或分发名单）/ 任务工单**。

- **默认彩排**：不带 `--submit` 就是 dry-run——只填、只回读、只截图，**不点提交**；**加 `--submit` 才真建**。
- **提交前门控**：任一步没通过就**不提交**（关弹窗、记 `warn`、下次重跑）。
- **模式二恢复**：正常新建不预读后台；填写前先落 `submitting`。只有上次中断/未确认的项，下一次才做定点对账：`FOUND` 复用、`ABSENT` 重做、`UNKNOWN` 记 `needs_reconcile` 并停止。
- **提交后回读**：点了提交 ≠ 成功，一律回后台列表按**完整名称精确行**核对落库。

（三条是每个 `run_*.py` 共用的，实现见 [`../README.md`](../README.md)「设计原则」。）

## 1. 依赖顺序（工单前必须齐）

```
① 任务组 run_taskgroup.py
      ├─→ ② 资源 run_ads.py
      │
      └─→ ③ 圈选 / 名单
             A：run_audience.py → run_distribution.py
             B：run_selection.py → run_distribution_ids.py
                         ↓
④ 任务工单 run_taskorder.py
      ↓
体检 check_campaign.py（只读核对）
```

> **资源与圈选/名单互不依赖，可以互换先后；二者都齐了才能建工单。** 新加产品的真实流程通常在活动准备阶段先圈选、建名单，建批时只补资源，所以不能把旧表里的展示顺序当成硬依赖。

## 2. 两条圈选路径 —— 开工前先定走哪条

> 用户 2026-09-21 定：**用哪条先问用户，AI 不自行选**。区别不在"圈得准不准"，在于**圈选结果落在哪、工单挂什么**。

| | **A 路径 · 后台圈选用户** | **B 路径 · 数据平台圈选博文** |
|---|---|---|
| 在哪圈 | 广告后台「3.圈选用户」→「关键词博客ID圈选任务」 | `data.csdn.net`（BI 数据平台）→ 导出 CSV |
| 圈选脚本 | [`run_audience.py`](run_audience.md) | [`run_selection.py`](run_selection.md)（**只导 CSV，不建任何后台对象**） |
| 建名单脚本 | [`run_distribution.py`](run_distribution.md)（在圈选列表点「一键创建分发名单」） | [`run_distribution_ids.py`](run_distribution_ids.md)（拿 CSV 的 `article_id` 建**普通名单**） |
| 两脚本之间 | 可以连着跑 | **必须停下人工看数量**，满意才建名单（数量不满意就不该往下走） |
| 圈选时点 | **固定下午**——后台数据集每天上午还在写入、一般中午才写完，早圈出来的数偏小 | **随时可导**（不受这条约束） |
| 工单挂什么 | **客群** | **分发名单**（工单不再挂客群） |
| 后台有"一键创建"吗 | 有（列表里就有） | **没有**——只有 CSV，所以只能拿 id 手工建普通名单 |

> ⚠ **两条路径不能混着用**：B 路径圈完，后台的圈选列表里没有可点的「一键创建分发名单」，必须走 `run_distribution_ids.py`。
> 后台「圈选用户」还有一套**搜索词 / Landing 词 / 相似任务**的通路口径——**本流程不走**，存档在 [`run_audience.md`](run_audience.md) 末尾。

## 3. 每一步做什么（逐步表）

> **`--config` 统一指整活动 YAML**；`--only <桶>` 只跑指定桶；`--headed` 显示浏览器；`--reset-progress` 清断点账本。详细开关见各脚本自己的说明书。

| # | 这一步做什么 | 脚本 | 详细文档 | 产出 / 落在哪 | 停下确认 |
|---|---|---|---|---|---|
| 0 | **执行前门控**（AI 自己判，不是脚本） | — | [`../AGENTS.md`](../AGENTS.md)、流程文档 §8 | 三样必给：负责人标识→`taskGroupName` / 子业务线 / 是否新建任务组+名（+ 投放日期与时间段）；缺了**不启动** | 是 |
| 0′ | **批次计划离线自检** | [`check_batch_plan.py`](check_batch_plan.md) | 同左 | 秒级、离线：权重按资源数 / AB 位次不能跳 / 名字↔槽位 | 不过就别往下跑 |
| 0″ | 等登录态（只在过期时用） | [`wait_login.py`](wait_login.md) | 同左 | `--site admin`（广告后台，默认）/ `--site databi`（数据平台） | — |
| 1 | 建**任务组** | [`run_taskgroup.py`](run_taskgroup.md) | 同左 | 后台任务组（新建时名 = `taskGroupName`） | 首投才有这一步 |
| 2 | 建**资源**（每桶 2~3 条文案） | [`run_ads.py`](run_ads.md) | 同左 | 后台资源；名字 `{前缀}-{X}类 · {角色}-{N}` | 是 |
| 3A | **圈选用户**（A 路径） | [`run_audience.py`](run_audience.md) | 同左 | 后台**客群**；下午跑；建后按日均曝光验收 | 是 |
| 3B | **圈选博文**（B 路径） | [`run_selection.py`](run_selection.md) | 同左 | 中间 CSV 落在 `activities/{活动}/数据/圈选/`；统计写入数据库 `selection_run` | 看数量 |
| 3.5A | 建**分发名单**（A 路径） | [`run_distribution.py`](run_distribution.md) | 同左 | 后台分发名单（圈选列表「一键创建」） | 是 |
| 3.5B | 建**分发名单**（B 路径） | [`run_distribution_ids.py`](run_distribution_ids.md) | 同左 | 后台**普通名单**（类型 博客ID）；日志打印名单ID | 是 |
| 4 | 建**任务工单**（每桶 1 条） | [`run_taskorder.py`](run_taskorder.md) | 同左 | 后台工单；挂本桶资源 + 本桶客群/名单 | 是 |
| 5 | **体检**（只读核对） | [`check_campaign.py`](check_campaign.md) | 同左 | `--only taskgroup,ads,audience,list,order`；5 类对象在不在、名字一字不差 | — |
| 6 | **等平台审核 → 上线 → 下线老工单** | — | 流程文档 §8 | 工单建好即已提交，状态「未审核」→ **平台会审，不需要我们（也不需要用户）操作**（用户 2026-10-12：「审核不归我管，你只要提交任务了，过一会就有人审核」）；**审核通过才开始投放**；新批跑起来后再下线老批（**先上后下，别断流**）<br>⛔ **建批收尾就把「待下线老工单清单」（桶 + 任务 ID）列给用户**（用户 2026-10-13 定：「把要下的任务 id 给我，这个列入流程中吧，不要我每次说」）——ID 从数据库 `activities/_db/投放数据.db` 的 `bucket_batch` 表按**老工单完整名**查（`select task_id, task_name from bucket_batch where task_name like '%{桶名}%' order by id desc`）；**新单是新建的，ID 要等下一次取数才进库**，所以这一轮给的是"老工单" | 后台审核，无需人操作 |

### 复盘重投和首投不一样

| | 首投（新活动第一次） | 复盘重投 |
|---|---|---|
| 任务组 | 建（或沿用已有） | **不建**，按名字沿用 |
| 客群 / 分发名单 | 建 | **一般复用**（只有判定写着"换大名单"才重建） |
| 资源 | 建全部（2~3 条/桶） | 只建**这次要动的桶**那几条（同一批只装要动的桶） |
| 工单 | 全部桶 | 只建这次进批的桶 |
| 物料 HTML | **出**（流程文档 §7） | **不出** |
| 当前执行输入 | 当前整活动 YAML（`配置/` 或沿用 `批次/`） | 更新当前执行 YAML；历史批次、指标和复盘只进数据库 |

> ✅ **任务工单断点键 = 本批完整工单名**，不同批次天然不同；不再需要重投前手工归档或 `--reset-progress`。旧格式 `任务组|桶id` 不再读取。账本在 `activities/{活动}/日志/`。

## 4. 建批收尾（固定三段）

**① 复盘结果写入数据库**：AI 判定完成后更新 `review` 与 `review_resource`；看板只读取数据库。

**② 提示"下一步"**（用户 2026-10-15：「**执行完任务之后就提示我往下走，继续做补任务这一步**」）：每次建批 / 复盘收尾固定写三样——
① **待下线老工单**（桶 + 任务 ID）② **池子状态**（哪个桶缺几条新文案）③ **下一步动作**（例：`下一步：补 X 桶 N 条文案 → 到时我再问你要不要建批`）。

**③ 待下线老工单的给法**（用户 2026-10-15：「**这个给一次就好了，就是建完任务之后给我就行，不过给的格式要那种可以直接复制的**」）：**只在"建完批"这一次给**，格式必须是可直接复制的**纯文本块**——先一行一行 `ID  活动·桶`，再单独给一行逗号串（`1112741,1112811,…`）；⛔ **不要塞进表格或带别的字**（一行里夹说明就不好复制）。后面再提"下线"时**不重复整块**，只写一句。

> ⛔ 池子缺口是硬信息：**哪个桶池子里没货，下一轮它就要卡住**，收尾时必须点名，不等用户问。

## 5. 每步一停（纪律）

- **建批类动作一律分步走**：一步跑完 → 给用户看后台效果 → 确认后才下一步。**不要一口气跑完**。
- **建批一律直接 `--submit`，不再单跑一遍彩排**（用户 2026-10-15：「**我们的执行层是有校验的呀，为什么还要彩排**」）：`--submit` 路径本身就是「填完 → 逐字段回读 → 全过才点确定」，正式跑不截图，彩排只是把同一件事做第二遍。**首投 / 新桶 / 改过脚本也一样直接提交。** 彩排（不带 `--submit`）只剩一个用途：脚本刚改完、或只想验「配置填得对不对」而**不想动后台**时的干跑。
- **建批链一次只跑一条写命令**：每一步先确认结果，再跑下一步；不要同时启动两个 `--submit`，全局写锁会拦下第二个。只读命令可以另开标签页，明确支持并发的脚本除外。
- **失败自动重试一次，不用人重跑**（2026-10-15 加）：后台的下拉 / 穿梭框选项是异步拉的，当天第一次开浏览器（profile 冷启）常遇到「业务线 0 选项 / 渠道穿梭框不可见」——`bucket_runner` 对**没点过提交**的失败自动**清场 + 重开列表页 + 重试一次**（`retry=1`；点过「确定 / 提交」的失败一律不重试，防重复创建）。如果是 `Page.goto` / 页面服务无响应，先做页面级健康探针，必要时重启公共浏览器再重试。人只需要看最后的 RESULT。
- **命令行脚本和看板服务不再互斥**（2026-10-16 起）：浏览器只有一只，但它是独立于所有程序的**公共浏览器**（[`../scripts/browser_broker.py`](../scripts/browser_broker.py)，首选 CDP 9222，冲突时读取实际端口）——看板取数、建任务脚本、`wait_login.py` 同时挂上去、各开各的标签页，**不用再停看板服务**。⚠ 唯一要避开的：两个脚本**同时真办事**（都带 `--submit`）——写锁会直接拦下第二个。
- **耗时**只记在 [`执行层实测耗时.md`](执行层实测耗时.md)，**不写进流程文档和各说明书正文**。
- **每次会话自动落运行日志**：`activities/{活动}/日志/runs/{时间}-{脚本}-{PID}.log`；页面失活、恢复、重试和 RESULT 都在同一份日志里。
