# 投放看板 · `visualize_perf.py`（只读）

> 给一份**整活动 YAML**，把**台账库**（`activities/_db/投放数据.db`）渲染成一张**单文件 HTML 看板**。
> 区间 = 库里有的**全部日期**（不再有"最新快照"这个概念，所以取数取多窄都不会把看板缩窄）。
> **只做两块**（用户 2026-09-17 定的范围）：**分桶总计** ＋ **三套文案**；
> 之前做过的总览 KPI / 每日趋势 / 每天×桶明细 / 快照对比 都已按用户要求删掉。

## 为什么有它

复盘闭环第一条是「**每天监控数据**」。`fetch_perf.py` 只落 CSV——CSV 看不出哪个桶在起量、
哪个桶点击率不行。这个脚本把最新快照渲染成能直接看的页面：每个桶一行横条比高低，
桶内三套文案横着比。

## 怎么跑

```powershell
# A. 日常看（推荐）：起一次服务，之后页面自己拿数据（页面本体在 web/static/）
.venv\Scripts\python.exe -u web/app.py
#    → 浏览器打开 http://127.0.0.1:8770/，或直接双击 web/start.bat（详见 web/README.md）

# B. 出一份数据内嵌的单文件（发人 / 归档用）
# 先取数（只读快照，见 fetch_perf.md）
.venv\Scripts\python.exe -u automation/scripts/fetch_perf.py     --config activities/{活动名}/配置/{品牌}{负责人}.yaml

# 再出看板（读台账库）
.venv\Scripts\python.exe -u automation/scripts/visualize_perf.py --config activities/{活动名}/配置/{品牌}{负责人}.yaml

# 指定输出位置 / 换台账库
... --out 某处.html
... --db 别的.db
```

- **只读**：只读台账库和整活动 YAML，**不连后台**（取数那步仍归 `fetch_perf.py`）。
- 产出默认落 `activities/{活动名}/数据/看板/{生成时刻}.html`，可反复重新渲染。
- 退出码：成功 0；库里没有这个活动的数据 → 非 0。

> **页面本体在 `web/static/`**（index.html + app.css + app.js），服务在 `web/app.py`。
> 这个脚本只负责**把页面和当次数据烤成一个文件**（发人 / 归档）。
> 两边用的是同一份聚合代码 `automation/scripts/perf_payload.py` 的 `build_payload()`，数字必然一致；
> 区别只在"数据是现拿还是烤进文件"。网站那块怎么起、怎么改，见 `web/README.md`。

## 两块分别是什么

| 块 | 内容 | 自带控件 | 回答什么 |
|---|---|---|---|
| **分桶总计** | ① 一张表：桶 ｜ **曝光占比条** ｜ 曝光 ｜ 点击 ｜ 点击率 ｜ 登录曝光 ｜ 登录点击 ｜ 日均曝光 ｜ 判定；点「工单」展开该桶的工单（状态 / 首个有数据日 / 最后有数据日 / 在投天数 / 曝光 / 点击，**后四列都按所选时间段算**）。② 表下面**并排两张图**：左＝**柱状图**（每个桶两根柱：**彩柱＝曝光**左轴 / **橙柱＝点击**右轴，柱顶标实际值，扁而细）；右＝**累计折线图**（每个桶一条线，画的是**区间内逐日累加**的量——不是每天单独的量，最后一点＝区间合计；**顶部按钮切「曝光 / 点击」，不同时画**） | **时间段**：`今天` / 最近 7 天（默认）/ 全部 / 一个日期按钮点开自绘日历（**先点开始日、再点结束日**）；**工单口径**：仅在投（默认）/ 全部。两者都同时作用于表与两张图 | 哪个桶有量、哪个桶点击率不行；谁在涨谁在掉；哪个工单停了、哪个新来了 |
| **三套文案** | **按桶切换**（一次只看一个桶，不同桶点上方按钮切）：该桶每个工单一张小表，三组资源各一行 —— 曝光（量）条 ｜ 点击 ｜ 点击率 ｜ 标记（点击最高 / 0 点击）；已下线或最后有数据日早于数据末日的工单，标题后标 **「已结束」** | **桶**：A~E 单选 | 这一桶里哪套文案更抓人、曝光量够不够判 |

**日期选择器是自绘的**（2026-09-17 定，2026-09-20 合成一个按钮）：点日期按钮弹出月历，弹层跟页面同一套字体与配色；
只有**后台有数据的日期**可选（其余置灰）；**点一天定开始日、再点一天定结束日**，第二步之前弹层不关，选完即重算。
不用浏览器原生 `input[type=date]`——它的弹层字体/外观浏览器画死、改不了，用户明确嫌丑。

**页头只留必要信息**（2026-09-20 用户要求删）：「生成时间 / 数据源 / 末尾一天没走完」这些字**不显示**；
「刷新数据」是一个**图标按钮**（悬停出 tooltip），点一下图标转圈 + 状态行闪一行「已刷新 时:分:秒」。

**页面上不放说明文字**（用户 2026-09-17 要求删掉："样本不足 30"标记、各块下面的 legend / 图注、footer 口径），
口径只写在本文件里；图下只留颜色对照（哪条线/哪根柱是哪个桶）。

控件放在**各自块的标题行右侧**（用户 2026-09-17 的要求：切换要挨着它影响的图，不放在顶部当全局工具栏）。

## 样式与画图规则（用户 2026-09-17 定）

- **样式照旧**：两块沿用用户认可的那版样式——分桶总计是**表格 + 行内占比条**，三套文案是**卡片块 + 小表**；
  不要另加图表、不要换视觉风格（用户 2026-09-17：「我刚才说的那两个别动样式」）。
- **不许堆叠**：早先那版把各桶叠在一根柱子上（「一点美观度和清晰度都没有」），已废弃；
  现在只在表格里用**行内细条**表示相对大小，一根条只表示一个数。

## 口径（和 `fetch_perf.md` 一致）

- **口径归属（2026-09-23）**：一个桶「当天的量」与「哪些天算有量」（＝日均曝光的分母）由
  `perf_payload` 算好下发（`bucketCells` / `bucketDays` / `orderDays`），**页面只做加减**——
  把所选的天加起来、数落在区间里的有量天。原先这套口径写在 `app.js` 里（**没有测试护着**），
  命令行摘要的 `totals()` 又是另一份实现、还只能算全区间。现在 `totals(payload, 桶, 口径, days=…)`
  一处实现：不传 `days`＝库里全部天，传了＝页面所选区间。
- 两块都用 `投放数据.csv` 的**按天**数据汇总（一天一行、**已是终值**，过去任意一天可重查）；
  三套文案那块的曝光/点击来自 `资源级累计.csv`（**整段累计**、含当天已发生的部分）。
- 现在数据源是**台账库**：按天事实来自 `daily` 表，三套文案来自 `resource_reading` 表的**最新读数**。
- **工单口径**：「仅在投」＝状态为「进行中」的工单；「全部」＝把同桶已下线工单的历史也算进来。
  同一个桶常有多条工单（重投 / 测试各一条），**默认只算在投**，免得把两个实验混成一个数。
  口径同时作用于分桶表、两张图、工单明细和三套文案卡片（卡片的「已结束」标记不变）。
- **「日均曝光」＝ 曝光 ÷ 该桶实际投放的天数**（2026-09-20 用户定，方案 A）：分母数的是**当天有量的日子**（曝光/点击任一非零），**多条工单并行时同一天只算一天**；工单明细里也各有一列「日均」＝该工单曝光 ÷ 它自己的投放天数。起因：原来拿区间日历天数当分母，把工单**还没起投 / 已下线**的日子也算进去——B 桶 -2 是 9/18 才起投、9/14~9/17 根本没跑却照样进分母，显示 58/天、实际 116/天。⚠ 活动细则 §9.4 的达标线「日均曝光(预估) ≥ 5,000」是**后台按客群池子给的预估**，跟这里的实际日均不是一回事。
**末尾那天（今天）算一天**：今天的按天数据是半截的，但工单确实在跑，所以分子分母都按一天算、口径一致（页面上不写提示）。
- **登录曝光 / 登录点击**＝只统计已登录用户（后台接口自带，后台导出 excel 里没有这两列）。
- 点击率及格线 `0.10%` 取自活动细则 §6 的博客详情页底部基线（**尚未由本活动验证**）；
  「每工单 ≥30 点击再判优劣」同理——样本没到只标「样本不足」，不下结论。
- **工单变更**：后台只给「某天某工单有没有数据」，没有停投时间字段，所以**停投以最后有数据那天为准**。
- **一个桶多条工单**：桶是聚合单位，工单才是分析单位——同一个桶下有几条工单，
  表里就有几行、下面「三套文案」就有几张卡片（各自按**任务名称**分组，如 `…-2` / `…-3`）。
  ⚠ 重投 / 测试工单常常**沿用上一批资源**（如 2026-09-20 B 桶的 `…-3` 直接挂 `…-2` 的
  `对照-2 / 实验1-2 / 实验2-2`），这时两份工单在 `资源级累计.csv` 里**资源名称一模一样**，
  只能靠任务名称（卡片标题的 `-2` / `-3` 后缀）区分——聚合一改按资源名称就会把两份合并，
  所以 `automation/tests/test_perf_payload.py` 把这条钉住了。
  另外桶级数字（曝光占比条、柱状图、折线图）是**同桶所有工单相加**，含已下线工单的历史数据。
