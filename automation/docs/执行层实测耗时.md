# 执行层实测耗时（人看的记录）

> 这份**只记实测数据**：哪条命令、什么条件、跑了多久。**不是流程规则**，也不进 AI 的分阶段阅读清单
> （流程规则只在 `ad_output/流程文档/CSDN广告投放自动化流程.md`）。
> 规矩：**每次彩排/真跑觉得值得记，就往下加一行**，别改历史行；数据要能对得上当时的命令与模式。

## 测量口径（读表前先看）

- **脚本自报** = 脚本自己打的 `⏱ 总用时 X 秒`（**不含**浏览器启动与页面首屏加载）。
- **墙钟** = 跑整条命令的时间（**含**浏览器启动 ~3~4 秒）；没有自报数的命令只能用它。
- 两种口径**不要混着比**。同一次对比里，两版用同一种口径。

## 2026-09-24 · 看板「刷新」提速（省掉冗余请求 + 只刷在投 + 前端轮询调快）

条件：火山引擎MediaKit 真实配置、**只读**刷今天的实时数（`--from 今天 --to 今天 --no-archive`，
＝看板右上角那个「刷新」按钮），同一天、同一台机、同一份登录态。
请求段用**同一只浏览器**对拍（起/关浏览器那 ≈1.7 s 两边一样，不算进请求段）。

**整条命令墙钟**（＝点一下「刷新」，含起/关浏览器）：

| 版本 | 样本 | 中位 |
|---|---|---|
| 改前（原样） | 5.73 s / 5.24 s | ≈5.5 s |
| 改后第一版（按"在投 + 有量"筛 → 16 个工单） | 3.58 / 4.01 / 4.01 / 4.02 s | ≈4.0 s |
| **改后定版（只刷在投 → 5 个工单）** | 2.72 / 4.20 / 3.12 s | **≈3.1 s** |

（另有几次"新开一个 shell 的首跑"6.84 / 7.81 s，冷启动噪声，未计入。
看板上的**感知**时间还受前端轮询影响：`web/static/app.js` 的轮询 1.2 s → 0.4 s，最多再少等 0.8 s。）

**请求段对拍**（同一只浏览器交替跑改前 / 改后）——后台快慢在不同时段不一样，所以按时间窗分开列，
**同窗内的两列才可比**：

| 时间窗 | 改前（任务组 + 按天 + 资源级 26 个） | 改后（按天 + 资源级 5 个） |
|---|---|---|
| 16:4x（后台较快） | 0.90 + 0.61 + 1.37 = **2.88 s** | 0.43 + 0.83 = **1.26 s** |
| 16:5x（后台较慢） | 1.15 + 1.03 + 2.16 = **4.34 s** | 0.82 + 0.31 = **1.13 s** |

净效果：**命令行整条从 ≈5.5 秒降到 ≈3 秒**。

## 2026-09-24 · 常驻浏览器（看板服务持有）

用户 2026-09-24 定：`web/start.bat` 起服务时就把浏览器开起来（无窗口），刷新 / 取数都复用它，
**关窗口（或 Ctrl+C）时一起关**。取数逻辑仍在 `automation/scripts/fetch_perf.py`（`Browser` + `run()`），
`web/app.py` 起一个取数线程拿着它、任务从队列里来（playwright 同步接口不能跨线程）。

| 场景 | 改前（每次起一只浏览器） | 常驻后 |
|---|---|---|
| 看板「刷新」（点一下，含前端轮询） | 3.1 ~ 4.2 s（当天早些时候 5.2 ~ 5.7 s） | **首次 1.80 s，之后 0.88 / 1.09 / 0.88 s** |
| 看板「取数」（补到昨天，落流水） | — | **1.1 s**（那天只补 1 天） |

实测口径：8771 测试实例、同一份登录态，`POST /api/fetch?today=1` 连点 4 次（服务端时间戳与客户端墙钟一致）。
另外验了两条边界：① **强杀服务进程**（＝直接关窗口）之后，指向 `.browser-profile` 的 msedge / node
残留进程 **0 个**；② 服务开着时在命令行跑 `fetch_perf.py` → 报一句人话
（"浏览器起不来…多半是看板正开着…"），不再甩一大坨 playwright 日志。

复现：同一条命令连跑几次取中位；请求段对拍＝同一只浏览器里交替跑"改前/改后"两种请求顺序（临时探针，未入库）。

## 还没量到的（下次补）

> 2026-09-28 补：`run_distribution_ids.py --submit` 这条路径**已量**（上面那行"下次补"已兑现），结论是
> **慢在服务端落库、不在脚本**——100 条含提交 7.1 秒；11.3 万条彩排 6.4 秒；五份大名单每份 3~4.7 分钟
> 且**与数据量无关**（固定成本）。数据、排除项与两个候选方案见 `run_distribution_ids.md`
> 「提交路径耗时实测（2026-09-28）」。
>
> **同日下午修正**：初版"服务端落库慢"是错的。实测曲线（100 / 1k / 10k / 113k 四档真提交）显示
> **提交回执** 0.3 / 0.3 / 0.8 / **5.0 秒**（不慢），慢的是**提交之后在本会话里继续操作页面**——
> 回读那一段 **~190 秒**（换新标签页 186.6 秒，一样慢；会话结束后只读访问只要 6 秒）。
> 修法：`READBACK_MAX_IDS=20000` 以上跳过会话内回读、以回执为准、回读交事后只读体检。
> **效果：同一份 113,285 条，201.7 秒 → 8.5 秒。** 详见 `run_distribution_ids.md`。
>
> **同日再修正**：核对**不能在同一进程里补**——实测同一份 11.3 万条：同进程第二会话 **~5 分钟**、
> 从活着的父进程 spawn 子进程 **~2.8 分钟**、**父进程退出后另起命令 6.3 秒**。
> 规律：只要上一个浏览器还活着，新浏览器就被拖住。最终形态 = **两步走**：
> 建名单（~10 秒，只认回执）→ 独立命令核对（`--verify-only --name …`，实测 **4.4 秒**）。

| 项 | 为什么没量 | 怎么补 |
|---|---|---|
| `--submit` 路径的闸门 + 回读 | dry-run 根本走不到那段 | 下次真实起投时记 `⏱ 总用时`；预计整批回读 +10 s 以内（按任务组下拉筛一次约 8.6 s） |
| `run_selection.py`（B 路径第 1 步）全程 | 这轮没跑 | 下次导出 CSV 时记一行；已知 09-21 五桶的落盘时间戳间隔：35 s ~ 2 min/桶 |
