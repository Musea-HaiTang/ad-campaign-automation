## 测量口径（读表前先看）

- **脚本自报** = 脚本自己打的 `⏱ 总用时 X 秒`（**不含**浏览器启动与页面首屏加载）。
- **墙钟** = 跑整条命令的时间（**含**浏览器启动 ~3~4 秒）；没有自报数的命令只能用它。
- 两种口径**不要混着比**。同一次对比里，两版用同一种口径。

## 2026-09-28 · 建分发名单 `run_distribution_ids.py` 提交提速（201.7 s → 8.5 s）

> 来源：2026-09-28 从 `run_distribution_ids.md` 搬来（2026-10-09 整理：说明书只留"现在该怎么做"，
> 实测过程归这里）。起因 = 本活动 5 份名单（11.3 万 ~ 46.2 万条 id）每份端到端要 **3~4.7 分钟**，
> 用户问"为什么这么久"。

**第一轮：三组数据**

| 场景 | 数据量 | 结果 |
|---|---|---|
| 100 条 id，**含提交与回读**（临时名单 `测速-临时-20260928`，名单ID 206875） | 100 | **全程 7.1 秒**：灌入 0.0 / 计数 0.0 / **点提交 0.1** / **等回执 0.3（拿到"保存成功"）** / 就地回读 3.1 |
| 彩排（只填+校验后取消） | **113,285** | **全程 6.4 秒**：翻开页 2.0 / 填名与类型 1.1 / **灌入 0.4** / **后台计数 0.5** |
| 五份正式名单（2026-09-24 18:32~18:46） | 113,285 / 115,567 / 145,042 / 372,198 / 462,239 | 每份 **3~4.7 分钟**；**名单创建时间间隔恒定 3~4 分钟**，与 id 数**不成正比**（最大的 46.2 万不比最小的 11.3 万慢） |

**第一轮排除掉的方向**：✗ 不是脚本慢（灌 11.3 万条 0.4 秒、后台计数 0.5 秒）；✗ 不是"连续开浏览器"；
✗ 不是数据量线性放大；✗ 不是回读导航慢。当时**误判**成"服务端落库那一下要 3~4 分钟"。

**第二轮：递增 id 数 + 分段计时**（每档都真提交、都核对过落库条数）——这一轮推翻了第一轮结论：

| 档 | id 数 | 灌 id + 后台计数 | **点提交** | **等回执「保存成功」** | 回读那一段 | 脚本全程 |
|---|---|---|---|---|---|---|
| 1 | 100 | 0.0 s | 0.1 s | **0.3 s** | 3.1 s | **7.1 s** |
| 2 | 1,000 | 0.0 s | 0.0 s | **0.3 s** | 2.7 s | **6.6 s** |
| 3 | 10,000 | 0.1 s | 0.0 s | **0.8 s** | 2.0 s | **6.6 s** |
| 4 | 113,285 | 0.4 s | 0.1 s | **5.0 s** | **192.8 s** | **201.7 s** |
| 4′ | 113,285（**换新标签页**回读） | 0.4 s | 0.1 s | 4.8 s | **186.6 s**（一样慢） | 195.3 s |
| 4″ | 113,285（提交后**另起进程 / 新会话**，0 秒延迟就核） | — | — | — | **5.9 s**（立刻就能读） | — |
| 4‴ | 113,285（提交后在本进程里**再开一个会话**核对） | — | — | — | **~5 分钟**（不行） | — |
| 4⁗ | 113,285（活着的父进程 **spawn 子进程**核对） | — | — | — | **~2.8 分钟**（也不行） | — |
| 4⁵ | 113,285（**父进程退出后**另起命令核对） | — | — | — | **6.3 s**（可以） | — |

**第二轮结论**：

- 提交本身和回执**不慢**：11.3 万条的回执只要 **5.0 秒**，内容就是「保存成功」。
- 慢的是**做提交的那个浏览器会话**：提交之后在这个会话里继续操作页面，回读那一段要 **~190 秒**——
  而它由「重新打开页面 / 翻开页签 / 筛选 / 点查询 / 取行」组成，**各步超时上限加起来才 16 秒**，
  说明每次页面交互都被拖住；**同一浏览器里换新标签页也一样慢**（同站标签共用渲染进程）。
- **只要"上一个浏览器还活着"，新的浏览器实例就会被拖住**：本进程里再开会话 ~5 分钟、spawn 子进程 ~2.8 分钟；
  **等本进程退出后**另起命令 6.3 秒 ⇒ 瓶颈是**浏览器重载期**，不在服务端（服务端数据立刻就绪）。
- 所以"id 多了就卡"的真相是：**大 payload 提交后，本次会话的页面在 ~3 分钟里不可用**——
  **在原会话里怎么等都是白等**。

**据此落地的修法**（2026-09-28）：以回执为准（`ACK_TIMEOUT_S=300`，每 15 秒打进度）；
`READBACK_MAX_IDS = 20000`，超过就在会话内**跳过**回读、打印一条立刻可跑的独立核对命令；
提交路径保留全程埋点（`⏱ 阶段: 本段 X 秒 · 累计 Y 秒`）。
**为什么不自动补**（用户当时同意自动化，实测后否掉）：自动化只能在同一个进程里做，
而"上一个浏览器还活着"时新浏览器会被拖住（同进程第二会话 ~5 分钟、spawn 子进程 ~2.8 分钟），
都远不如"退出后另起一条命令"的 6 秒。所以这一步保持**两步走**。

**效果**（同一份 113,285 条 CSV，真提交）：**201.7 秒 → 8.5 秒**（整进程 10.7 秒）；
事后只读探针核对：名单 `测速-113k-c-20260928`（ID 206880）**用户个数 = 113285**，与 CSV 一致。
5 份正式名单（ID 206870~206874）条数事后也核过：113285 / 115567 / 145042 / 372198 / 462239，**全部精确**。

**更早的两次数据点**：

- **2026-09-22 死等改条件等待**：`run_distribution_ids.py --csv … --name …` 墙钟 **7.2 s → 5.8 s**

## 2026-10-12 · 大名单核对"卡住"复现：残留浏览器 + 过期 lockfile

**背景**：腾讯云产品活动第二批，两份大名单（113,389 / 76,083 条 id）建完，独立命令 `--verify-only` 却分别跑了
**~190 s**、**~190 s**，第三次 **357.5 s** 还报「列表里没找到」；而 09-28 记的同一条命令是 **4.4~6.3 s**。
用户当时的记忆是"重开浏览器跑只读会话就好了"，查下来记录是对的，只是这次多踩了两个新症状：

| 现象 | 证据（2026-10-12） |
|---|---|
| 上一次跑完的浏览器**没退干净** | 查进程：`msedge.exe --user-data-dir=…\ad_management\.browser-profile` 还有两组（16:43、16:59 启动）活着，而它们的父进程早就退出了 |
| 有旧浏览器活着 → 新会话被拖住（09-28 已记过的结论） | 三次核对 = 190 s / 190 s / 357 s（还读不到名字）；**把残留全清掉后，同一条命令 71.5 s 跑完并读到名单 207067** |
| **新症状**：残留锁让新会话**起不来** | 残留浏览器在 `.browser-profile\lockfile` 上留了锁 → `BrowserType.launch_persistent_context: Target page, context or browser has been closed`；删掉 lockfile、清干净进程后立刻恢复 |

**做法（本轮实测有效）**：跑大名单的核对前先确认没有残留——

```powershell
Get-CimInstance Win32_Process -Filter "Name='msedge.exe'" |
  Where-Object { $_.CommandLine -like '*ad_management\.browser-profile*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
# 确认一个残留都不剩，再删这把过期的锁：
Remove-Item .browser-profile\lockfile -Force -ErrorAction SilentlyContinue
```

⚠ 判据是 `.browser-profile` 这个 **user-data-dir**，**别按进程名 `msedge` 一刀切**——用户自己的 Edge 也在同一台机器上跑。

```powershell
#   旧代码 = $base\old\automation\scripts\…（git archive HEAD 取出来的）
#   新代码 = 仓库里的 automation/scripts/…
#   日志   = $base\log_{new,old}_*.txt
```
