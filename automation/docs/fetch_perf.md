# 取数 · `fetch_perf.py`（只读接口 → 台账库，默认补到昨天）

> 给一份**整活动 YAML**，把后台的投放数据写进 **SQLite 台账**（`activities/_db/投放数据.db`）：
> 工单 × 日期（按天，终值可覆盖）+ 资源读数（每次取数追加一条）。
> 同时往 `数据/{时刻}[_标签]/` 落一份**取数流水**（原始 CSV，可 diff），但看板不读它。
>
> 2026-09-20 起改成"**台账库 = 唯一真相**"：以前"最新一份快照即真相"，窄区间取数会把看板缩窄
> （真踩过），而且同一桶多条工单、今天反复刷新都表达不了。详见流程文档 §9.5 与 `perf_db.py`。

## 为什么有它

投放跑起来之后要看数据：哪个桶在起量、哪套文案更划算。后台的数据只能按日期区间查，
过去任意一天都能重新查，所以**不需要一个天天活着的采集服务**——你要看的时候喊一声即可。

## 怎么跑

```powershell
# 默认（＝看板上的「取数」）：从"库里最近有数据那天"取到**昨天**——把昨天的数固定下来
#   昨天一天取一次就够（它不会再变）；空库从投放开始日全量回填；
#   活动**开投第一天**（起始日 = 今天，昨天还不存在）只取当天那一格（2026-10-12 修：
#   原来这种区间是反的，会直接报"日期填反了"）；起始日还在未来则报"还没开始投放"，不写库
.venv\Scripts\python.exe -u automation/scripts/fetch_perf.py --config activities/{活动名}/配置/{品牌}{负责人}.yaml

# 只取今天 = 看板上那个「刷新」干的事（今天的实时数，随时可点；2026-09-24 实测整条命令 ≈4 秒，
#   其中约 1.7 秒是"起浏览器 + 关浏览器"的固定开销——要再快只能上常驻浏览器，见下「代价」）
... --from 2026-09-20 --to 2026-09-20 --no-archive   # 只取今天 = 看板上那个「刷新」干的事（不落流水）

# 显式区间：补历史 / 修后台改过的数（幂等，随时可重拉）
... --from 2026-09-14 --to 2026-09-15

# 标注这次取数对应哪次调整（只进流水文件夹名）
... --label 调整前

# 想看浏览器窗口（默认无头 + 最大化）
... --headed

# 换台账库（默认 activities/_db/投放数据.db）
... --db 别的.db
```

- **只读**：只调「查任务列表 / 查任务资源明细」两个查询接口，绝不创建、修改、暂停后台任何对象。
- **失败不落盘**：登录态失效、查不到任务组、区间内一天数据都没有 → 退出码 1，**库和流水都不写**。
- 退出码：成功 0 / 失败 1。
- **随时可以跑**：今天那行在库里是被覆盖的（不是新增），所以页面上点几次「取数」都只刷新今天，不会脏。

## 落盘长什么样

```
activities/_db/投放数据.db             # ★ 台账库（SQLite，不进 git）：唯一真相，看板只读它
activities/{活动名}/数据/
  README.md                           # 口径说明
  2026-09-20_1405/                    # 取数流水：一次取数一个文件夹（文件名 = 时刻[_标签]）
    投放数据.csv                      # 这次**实际取回来**的那几天：工单 × 日期
   资源级累计.csv                    # 这次取数那一刻的资源读数（累计值）
```

日志里那行 `本次取回 N 天（起 ~ 止）合计：曝光 X | 点击 Y` 说的是**这次取回的那几天**——
跟看板的合计（库里全部天）不是一个口径，别拿来互相对（2026-09-23 标明的，起因：「合计」这个词
原先在三个地方各算一遍、覆盖范围还不一样，对不上时没人说得清谁错了）。

**真相在库里的两张表**（见 `perf_db.py`）：

| 表 | 主键 | 语义 |
|---|---|---|
| `daily` | (工单, 日期) | 一天一行；**历史是终值，今天反复覆盖**（所以窄区间补数不会顶掉别的天） |
| `resource_reading` | (工单, 资源, 取数时刻) | 每次取数追加一条读数；两条相减 = 区间增量 |

流水文件夹**只是原始存档**：要查"后台哪天改过数"，才需要翻它做 diff。
一天取几次就有几个文件夹，不用担心"哪份才是最新"——这个问题在库上已经不存在了。
*「刷新今天」不落流水*（`--no-archive`，数据只进台账库）——所以一天最多一份流水 = 当天的「取数」。

## 后台接口契约（真机勘察 2026-09-15 ~ 16）

接口域名是 **`https://csdn-distadmin.csdn.net/admin/`**——不是页面的 `mp-admin.csdn.net`，
这是第一次录制「一条接口都没抓到」的原因。

| 步骤 | 接口 | 要点 |
|---|---|---|
| 工单 × 日期 | `POST /tTaskInfo/taskPageList` | 带 `businessHappenStartDate/EndDate`，**一次一天**（区间会聚合成合计）；**返回的行里就带工单名/状态/taskGroupId，所以"工单清单"直接用它，不再单独查一次任务组**（2026-09-24 起） |
| 任务组全量 | `POST /tTaskInfo/taskPageList` | 只填 `taskGroupName`。**现在只在兜底时查**：按天返回的工单比库里已知的少（例如补历史那天还没建的工单）才补这一次 |
| 资源级 | `GET /tTaskInfo/creativeDataByTaskId?taskId=…` | 一个任务一次，返回 `resourceId / resourceName / experimentName / exposure / click`；**只查在投的工单**（状态＝进行中） |

必带 `Accept: application/json`：不带会返回 XML（`<ResultVO>…`），且编码变成 GBK
（带 Accept 是 UTF-8）。脚本两种都兜。

## 资源级（对照 / 实验1 / 实验2）

后台点任务名弹出的「数据统计」弹窗走的就是 `creativeDataByTaskId`，我们直接调它，不爬弹窗。

**它是累计值，不能按天**——真机试过四种日期参数（`startDate/endDate`、`businessHappenStartDate/EndDate`、
`startTime/endTime`、只取单日），返回的数字**一模一样**。所以：

- `daily` 表（按天终值）和 `resource_reading` 表（累计读数）**口径不同，别混着算**。
- 资源级含当天已发生的部分；看板「三套文案」那块展示的是**最新一次读数**（＝整段累计）。
- 想看"某段时间里三套文案各涨了多少"，**拿两条读数做差**（读数按取数时刻存在库里，随时可对）。
- **只查在投的工单**（2026-09-24 起，用户定"就改成进行中，不要别的"）：资源级**只认状态＝进行中**，
  **不看"今天有没有量"**。理由是多轮上线下线之后，会有一堆"下线了但还残留数据"的工单
  （实测 A 类-4 今天跑了 2591 曝光才下线），按"有量"筛等于把它们又全捞回来，省不下来。
  本活动 26 个工单里只有 5 个在投 → 资源级从 26 次降到 5 次。
  代价（明说）：**下线工单的累计读数定格**在最后一次读到它的那一刻（看板「三套文案」那张卡停在下线时的数）；
  **按天的数不受影响**——按天查询本来就是全量、每个工单都取，图表/表格里的曝光点击照常更新，
  判定脚本读的也是这张读数表，但它只对**在跑的那批**（`-6`）有用，在跑期间每次都刷。

## 为什么不用后台的「按天导出」excel（2026-09-16 弃用）

导出那条路一开始是能用的，踩够了才换掉，四条都是真机教训：

1. **导出模块会整块失效**：2026-09-16 那天 `/admin/export/*` 全部返回 `code=400600 无权限`，
   连只读的 `export/tasks/meta`、`export/tasks/list` 也一样，页面自己提示「无权访问，请重新登录」；
   而任务列表接口始终正常。重新登录才恢复。
2. **后端按参数复用旧导出（最坑，数据会静默偏小）**：同样的 `9/14~9/15` 区间，9/16 提交会拿回
   **9/15 10:14 生成**的那份文件——那时 9/15 才刚开始。快照里 9/15 合计 267，实际 1951，**差 7 倍**，
   而且返回值上看不出新旧（`submit` 直接给一份 SUCCESS + URL）。当时的应急修法是每次带唯一
   `cacheBust` 字段 + 提交后回读生成时间；换掉导出后这两个补丁一起删了。
3. **导出是异步任务**：`status=QUEUED`、`downloadUrl` 为空，要轮询等。
4. **有提交频率限制**：连提几次报 `code=400000 提交过于频繁，请稍后再试`。

换掉之后还白捡两列导出没有的指标：**登录曝光 / 登录点击**。

## 代价（明说）

按天数据要**一天查一次**。增量模式下每天只要 1~2 次按天请求（昨天复看终值 + 今天刷新）
+ 每个**在投**的工单 1 次资源读数请求（本活动 26 个工单里只有 5 个在投 → 只查 5 个），
比原来的"每天重拉全区间"省得多；真要全量回填 / 补 30 天，才是 30 次按天请求。
任务列表接口如果哪天加了频率限制，这里会是第一个受影响的地方。

**整条命令的时间去哪了**（2026-09-24 实测，刷新＝只取今天；后台快慢会变，括号里是同一时刻的对拍）：
起浏览器 + 关浏览器 ≈1.7 秒（固定，和后台无关）、按天查一次 0.4~1.0 秒、资源级 5 次 ≈0.3 秒、
落库收尾 ≈0.2 秒，合计**中位 ≈3 秒**（改前同一时刻 ≈5.5 秒）。

**看板上的「刷新 / 取数」更快**（2026-09-24 起）：`web/app.py` 起服务时就把浏览器**常驻**（见文件头的
`Browser`），刷新/取数都复用它，省掉"起浏览器 + 关浏览器"那 ≈1.7 秒，**实测首次刷新 ≈1.8 秒、
之后 0.9~1.1 秒**。代价：**一个 profile 同时只能一个进程用**——看板开着时别在命令行跑这个脚本，
也别跑 `wait_login.py`（起不来时会直接告诉你"看板正开着，先关掉"）。

- **看板上取的是"当前选中的活动"**（2026-09-28 起，看板改成"一个服务管多个活动"）：页面每个请求都带
  `?activity=<任务组名>`，选的是哪个活动就取哪个；**跨活动也是串行**（浏览器仍然只有一只），
  但**"今天已取"的配额按活动各算一份**——给 B 取数不吃 A 的额度；取数流水同样按活动各落一份。
  命令行仍然是一次一个活动（`--config` 指定），多个活动就多跑几次。

## 数据本身的边界

- **A 组 = 正版 A 类 + 测试工单-A 类**：正版时间设错了，`测试工单-…` 是它的替补工单，
  分析 A 组时要把两条**相加**（9/15：7 + 1084）。
- 数据里会有 `测试工单-…` 这种命名的工单，脚本按后台原样存，不做过滤。
- **取数是「任务组 × 全量」，不看整活动 YAML 的桶清单**：`taskGroupName` 底下有几条工单就取几条。
  所以同一桶起了重投 / 测试工单（如 2026-09-20 B 桶的 `…-3`），**一建出来就会自动进下一份快照**，
  不用改配置；反过来，想少取某条也只能去后台下线它。
- 没有消耗 / 金额 / 预算（后台这些查询接口不给）。
- 任务列表接口里还有 `userCount`、`totalExposure`、`abTestConfig` 等字段，脚本目前只取
  曝光 / 点击 / 登录曝光 / 登录点击 + 状态，需要别的再加。
