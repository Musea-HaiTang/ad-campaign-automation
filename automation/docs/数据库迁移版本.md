# 数据库迁移版本与回滚

> **管什么**：数据库 v2 每个 `schema_version` 的结构变化、升级前置备份和回滚步骤。
> **不管什么**：表的业务职责见 [`数据库v2说明.md`](数据库v2说明.md)；备份与恢复命令细节也以该文档为准。
> **谁什么时候读**：提升 `SCHEMA_VERSION`、升级正式库、恢复旧库或排查版本不兼容时。

## 版本表

| 版本 | 历史状态 | 主要变化 | 数据处理 |
|---|---|---|---|
| v1 | 早期导入库，无 `schema_version` | `activity`、`daily`、`daily_change`、`fetch_log`、`resource_reading`、`task` | 非空遗留 `daily` / `task` 不会被静默转换；迁移会停止，需先人工核对 |
| v2 | `schema_version=2` | 规范化为 `activity`、`bucket`、`bucket_batch`、`creative`、`daily_metric`、`fetch_run`、`resource_reading`、`review`、`review_resource` | 建立活动 → 桶 → 批次 → 文案/指标/复盘的正式关系 |
| v3 | `schema_version=3` | 删除遗留 `daily`、`task` 表 | 仅允许删除空表；仍有数据时迁移失败 |
| v4 | `schema_version=4` | 新增 `selection_run` | 保存 B 路径圈选导出时刻、词数、博文数和总点击 |
| v5 | 当前版本 | 当前批改为 `batch_no` 最大的未中止批次；重建 `v_bucket_current`；修复旧导入首批编号和起投日 | 迁移会按后台 `task_id` 顺序重排异常批次，不改 `status` / `task_state` 语义 |

## 升级前置要求

- 提升 `SCHEMA_VERSION` 前，必须在本文件增加对应版本行，写清结构变化、数据处理和回滚方式。
- `workspace_repo.connect()` 检测到旧 schema 时，会自动生成 `pre-v{旧版本}` 快照。
- 快照必须通过 `PRAGMA integrity_check`；备份失败时迁移不会开始。
- 升级前确认看板和取数任务已停止，并保留最近一份手动备份。
- 迁移无法唯一映射数据时直接失败，不能猜关系或静默删表。

手动备份：

```powershell
.venv\Scripts\python.exe automation/scripts/db_backup.py
```

## 回滚步骤

1. 停止看板、取数和所有写库脚本。
2. 找到升级时生成的 `pre-v{旧版本}` 快照，先做只读校验。
3. 执行恢复；恢复命令会再保存一份当前库的 `pre-restore` 快照。
4. 切换回理解旧 schema 的代码版本。
5. 重新运行 `scripts/doctor.py` 和测试，再启动看板。

```powershell
.venv\Scripts\python.exe automation/scripts/db_restore.py check "<pre-vN 快照>"
.venv\Scripts\python.exe automation/scripts/db_restore.py restore "<pre-vN 快照>" --confirm
```

数据库回滚不会撤销 CSDN 后台已经创建的工单、资源、客群或名单。恢复旧库后，必须重新对账后台对象，不能假设远端一起回滚。
