# 数据库 v2 说明

> **管什么**：当前正式数据库的位置、领域关系、核心约束、读写边界和备份规则。
> **不管什么**：投放业务规则 → `../../ad_output/流程文档/`；表字段的完整 DDL 以 `../scripts/workspace_repo.py` 为准；单个脚本操作 → `run_*.md` / `fetch_perf.md` / `judge_batch.md`。
> **谁什么时候读**：修改数据库、脚本读写、看板取数、自动复盘或做迁移备份时。

## 当前事实

- 正式库：`activities/_db/投放数据.db`
- 当前 schema：v5
- 备份目录：`activities/_db/backups/`
- 数据库是活动、桶、批次、指标、复盘和圈选统计的长期唯一真相。
- YAML 只是当前输入或一次性执行载荷，不保存历史运行状态。
- DDL、迁移函数和仓库接口的唯一实现是 `automation/scripts/workspace_repo.py`；本文件只解释职责，不复制每个字段。

## 领域关系

```text
activity
  └─ bucket
      └─ bucket_batch
          ├─ creative
          ├─ daily_metric
          ├─ resource_reading
          └─ review
               └─ review_resource

activity
  ├─ fetch_run
  └─ bucket ─ selection_run
```

核心口径：

- 批次属于桶，`batch_no` 只在同一个桶内递增。
- 当前批 = 该桶 `batch_no` 最大且未 `aborted` 的批次。
- 一个桶批次最多对应一个后台任务工单。
- 同一份 YAML 可以描述多个桶的变更，但文件本身不是数据库中的共同批次。
- 复用旧资源时，新批次仍创建新的 `creative` 快照。
- 是否需要复盘只由 `review.status` 表示，不混入批次状态。

## 表的职责

| 表 | 保存什么 |
|---|---|
| `schema_version` | 当前数据库结构和迁移版本 |
| `activity` | 活动主数据、后台任务组名、活动起止状态 |
| `bucket` | 活动下的人群桶、当前关键词和默认曝光门槛 |
| `bucket_batch` | 每个桶自己的批次、后台工单身份和任务状态 |
| `creative` | 某批次实际使用的资源与文案快照 |
| `daily_metric` | 按批次和业务日期的曝光、点击等日指标 |
| `resource_reading` | 每次取数得到的资源级累计读数 |
| `fetch_run` | 一次取数的范围、状态、错误和汇总 |
| `review` | 达到门槛后的复盘状态、结论、对话和报告 |
| `review_resource` | 复盘时每条资源的指标快照与留、下、补验决定 |
| `selection_run` | 圈选导出时刻、词数、博文数和总点击 |

状态分工：

- `bucket_batch.status` 表示项目内批次生命周期。
- `bucket_batch.task_state` 表示 CSDN 后台工单状态。
- 后台工单下线只更新 `task_state`，不回写 `status`。
- 当前批 `task_state=下线` 的桶保留历史展示，但不再进入当前批门槛和待复盘项。
- 今天实时刷新时，后台查询直接限定 `workStatus=1`（只取进行中工单）；没有在投工单就跳过本次取数。
- 历史补数仍查询全部工单状态，避免漏掉旧任务曾经产生的真实历史数据；落库时仍只写入当前进行中任务。
- 未到曝光门槛时不创建 `review`，没有 `not_due` 状态。

## YAML 边界

以下长期状态只进数据库：

- 活动、桶和批次身份；
- 历史工单与批次关系；
- 文案资源快照；
- 按天指标和资源读数；
- 圈选统计；
- 复盘判断和结论。

以下一次性执行参数可留在本批 YAML：

- 价格、投放日期、时间段；
- AB 权重和曝光上限；
- 分发名单和用户名单名；
- 物料路径和本批资源计划。

登录态、浏览器 profile、原始截图和运行日志不写入数据库。

## 读写规则

- 业务读写统一经过 `workspace_repo.py`，不要在脚本里散写重复 SQL。
- 每次连接启用外键约束；正式库使用 WAL 和 `busy_timeout`。
- 活动、桶、批次和文案的整批同步放在同一事务内；中途失败整批回滚。
- YAML 导入只负责生成或更新当前批次，不从 YAML 反推历史数据。
- 取数根据后台 task ID 或完整工单名归桶；无法唯一匹配时整次失败，不猜桶。
- 看板和自动巡检只读数据库，不从旧 YAML 或 Markdown 待办文件恢复状态。

## 迁移、备份与恢复

- 数据库升级必须通过 `schema_version` 和迁移函数，不能在启动时静默删库重建。
- `workspace_repo.connect()` 检测到旧 schema 时，先自动生成 `pre-v{旧版本}` 备份；备份或完整性校验失败则中止迁移。
- 每个历史版本的变化和回滚步骤见 [`数据库迁移版本.md`](数据库迁移版本.md)。
- 迁移无法唯一映射时停止并输出异常，不猜测历史关系。
- 回滚时恢复数据库快照；已产生的后台对象不回滚，仍按远端事实处理。
- 日常检查至少确认 `PRAGMA foreign_keys=ON`、`PRAGMA integrity_check` 和最近一次 `fetch_run.status='ok'`。

手动备份：

```powershell
.venv\Scripts\python.exe automation/scripts/db_backup.py
```

- 默认数据库：`activities/_db/投放数据.db`
- 默认备份目录：`activities/_db/backups/`
- 默认保留：最近 7 份由本工具生成的快照；旧的人工备份不会被自动删除
- 快照使用 SQLite backup API，包含 WAL 中已提交的数据，并在落盘前执行 `PRAGMA integrity_check`

需要指定数据库或目录时：

```powershell
.venv\Scripts\python.exe automation/scripts/db_backup.py `
  --db "<数据库路径>" `
  --backup-dir "<备份目录>" `
  --keep 7
```

只读校验快照：

```powershell
.venv\Scripts\python.exe automation/scripts/db_restore.py check "<快照路径>"
```

恢复前先停止看板和取数任务，再显式确认恢复：

```powershell
.venv\Scripts\python.exe automation/scripts/db_restore.py restore "<快照路径>" --confirm
```

- `check` 只读打开快照，检查 `schema_version`、`integrity_check` 和外键。
- `restore` 先再次只读校验，再自动备份当前正式库为 `pre-restore` 快照。
- 恢复会生成并校验临时库，最后原子替换正式库；正式库被占用时中止。
- 恢复成功后应重新运行 `scripts/doctor.py`，确认数据库和登录态后再启动看板。
- 恢复低版本快照后，首次由项目打开数据库时仍会先备份再迁移。
