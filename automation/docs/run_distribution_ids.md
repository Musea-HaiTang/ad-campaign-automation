# 用博文 id 建分发名单（B 路径）· `run_distribution_ids.py`（执行层第 3.5B 步）

> **管什么**：怎么拿圈选 CSV 的博文 id 在后台建一条**普通**名单、为什么必须分两条命令走。
> **不管什么**：上游导出 CSV → [`run_selection.md`](run_selection.md)；A 路径（后台「一键创建分发名单」）→ [`run_distribution.md`](run_distribution.md)；两条路的区别 → [`执行层全流程.md`](执行层全流程.md) §2。
> **谁什么时候读**：走 B 路径、且圈选数量已核对满意之后。

## 开工前

- B 路径后台**没有**「一键创建分发名单」按钮，只有 CSV，所以只能拿 `article_id` 手工建**普通**名单（类型 = 博客ID）；下游是第 4 步工单挂这条名单（[`run_taskorder.md`](run_taskorder.md)）。
- ⚠ **圈选 CSV 是中间产物**：名单确认落库后，核对那一步会把这份 CSV 删掉（`--verify-only --name X --csv <路径>` 通过即删，`--keep-csv` 可保留）。统计已写入数据库 `selection_run`，要复现重导一次即可——别把 CSV 当账。

## 怎么跑

```powershell
# 彩排（默认）：填完名字/类型/博文 id，读回后台计数后点取消，不创建
.venv\Scripts\python.exe -u automation/scripts/run_distribution_ids.py ^
  --csv activities/火山引擎MediaKit/数据/圈选/2026-09-21_D桶96词_圈选博文_20260921.csv ^
  --config "<当前执行 YAML>" ^
  --only D --suffix -3 --headed

# 真建：加 --submit（建完以回执为准，核对照下面「两步走」）
... 同上 + --submit

# 名字不想按命名规则推，直接写
... --name "测试名单-火山引擎MediaKit-hang-D类"

# 独立核对（只读）——建完之后**另起一条命令**跑，别在同一个进程里补
... --verify-only --name "测试名单-火山引擎MediaKit-hang-D类"
```

- 名单名来源：`--name` 优先；否则 `naming.audience_task_name(campaign, audience)`；`--suffix`（如 `-3`）**覆盖**（不是追加）YAML 里的 `audiences[].nameSuffix`。重投第 N 次就换 `-N`，名字必须跟第 4 步工单的 `distributionList` 一字不差。
- 截图落 `日志/distribution_ids_shots/`。

## 两步走（重要）

后台建名单**提交之后，这个浏览器会话的页面在约 3 分钟里不可用**（大 payload 提交后的浏览器重载期，跟服务端无关）。所以固定这么走：

1. **建**（~10 秒）：正常新建不预读名单；提交前先落 `submitting`。正式提交必须等到回执明确为「保存成功」，失败或未知不能报 `OK`。只有上次中断/未确认的同名名单，下一次才按完整名单名定点对账并校验成员数。
2. **核对**（~5 秒）：**退出这个进程之后**另起一条命令跑 `--verify-only --name …`，或整批核 `check_campaign.py --only list`。**在同进程里补核对会等 2.8~5 分钟**，反而更慢。

数据量 ≤ 2 万条时脚本会在会话内顺手回读（`READBACK_MAX_IDS`）；超过就自动跳过并打印可用的核对命令。

**筛选结果刷新（2026-10-20 修）**：核对时填完名单名并点查询后，脚本先等**表格文字签名真正变化**，再读取目标行。此前 `wait_ms=0` 会立即扫描尚未重绘的旧表：实测页面有 60 条主行 + 120 条冻列副本，单次核对会卡 20 秒以上；改成条件等待后同一核对约 2.9 秒。⛔ 不使用固定 200 秒冷却。

**大名单后自动重开浏览器（2026-10-20 加）**：超过 `READBACK_MAX_IDS`（2 万条）的名单提交成功后，当前命令会主动关闭公共浏览器；下一条建名单或核对命令由 broker 自动启动一只新的。这样不复用刚灌过大 payload 的页面，也不用人工等待固定分钟数。

## 真机流程

| 步 | 动作 |
|---|---|
| 1 | 广告后台 → 分发管理 → **3.圈选用户** → 页签 **分发名单** |
| 2 | 点 `新增` → 弹窗「新增分发名单」 |
| 3 | 填 `分发名单` 名字；`名单列表类型` 选 **博客ID**；`分组个数` 默认 1 |
| 4 | 把 CSV 的 `article_id` 用逗号连起来灌进文本域，读回「提示: 已输入 N 个有效数据」 |
| 5 | 彩排点 `取消`；正式点 `提交`，等到「保存成功」→ **另起命令**核对（见上） |

## 安全阀

- **计数校验**：后台计数 ≠ CSV 行数 → 直接取消并报错，绝不提交（防文本域被截断 / 后台没解析完）。
- **回读核对**：点了提交不算成功——按完整名单名精确查到才算；查不到记 `HAS_WARN`、退出码 1。大名单回执未知时同样退出 1，并保留独立 `--verify-only` 核对命令。
- **id 里有空白字符** → 启动就报错（后台会把带空格的当无效数据）。

## 已知坑

1. **列表是 element-ui 固定列**：「名单ID / 分发名单」两列渲染在另一张固定列表格里，逐行 `inner_text()` 只读得到 用户个数/类型/创建人/日期 → 回读要读**整页正文**（名字上面一行就是名单ID）。
2. 列表按创建时间排、**分页**，刚建的名单不一定在第 1 页 → 用「分发名单模糊查询」筛，或直接读整页正文。
3. **这张表是异步加载的**，而且**隐藏页签里的表也有行** → 读正文前先等**当前页签**的表格出行，不限定页签作用域会被误满足。
4. **大名单核对单独起命令**：不要在同一次提交进程里继续读列表；当前脚本超过 2 万条会主动退出这次浏览器会话，下一条命令由公共浏览器重新启动。
