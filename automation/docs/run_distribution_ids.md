# 用博文 id 建分发名单（`run_distribution_ids.py`）

> 位置：执行层**第 3.5 步（建分发名单）的另一条走法**。原来那条 `run_distribution.py` 是在
> 「博文圈选任务」列表里点该行的「一键创建分发名单」；这条路是**拿圈选出来的 CSV，建一条普通名单**。
>
> 跟 `run_selection.py` **分开跑**：先导出 CSV、看数量满意，再跑本脚本建名单。

## 怎么跑

```powershell
# 彩排（默认）：填完名字/类型/博文 id，读回后台计数后点取消，不创建
.venv\Scripts\python.exe -u automation/scripts/run_distribution_ids.py ^
  --csv activities/火山引擎MediaKit/数据/圈选/2026-09-21_D桶96词_圈选博文_20260921.csv ^
  --config activities/火山引擎MediaKit/调整/2026-09-17-D桶换词重投.yaml ^
  --only D --suffix -3 --headed

# 真建：加 --submit；建完回读核对，日志里打印名单ID
... 同上 + --submit

# 名字不想按命名规则推，直接写
... --name "测试名单-火山引擎MediaKit-hang-D类"
```

名单名来源：`--name` 优先；否则 `naming.audience_task_name(campaign, audience)`，
`--suffix`（如 `-3`）**覆盖**（不是追加）YAML 里的 `audiences[].nameSuffix`。
重投第 N 次就换 `-N`，名字必须跟将来第 4 步工单的 `distributionList` 一字不差。

截图落 `activities/{活动名}/日志/distribution_ids_shots/`。

## 真机流程

| 步 | 动作 |
|---|---|
| 1 | 广告后台 → 分发管理 → **3.圈选用户** → 页签 **分发名单** |
| 2 | 点 `新增` → 弹窗「新增分发名单」 |
| 3 | 填 `分发名单` 名字；`名单列表类型` 选 **博客ID**；`分组个数` 默认 1 |
| 4 | 把 CSV 的 `article_id` 用逗号连起来灌进文本域，读回「提示: 已输入 N 个有效数据」 |
| 5 | 彩排：点 `取消`；正式：点 `提交`，然后**回读核对**（重开列表读整页正文，打印名单ID） |

## 安全阀

- **计数校验**：后台计数 ≠ CSV 行数 → 直接取消并报错，绝不提交（防文本域被截断/后台没解析完）。
- **回读核对**：点了提交不算成功——重开列表查名字，查不到记 `HAS_WARN` 并返回退出码 1。
- **id 里有空白字符** → 启动就报错（后台会把带空格的当无效数据）。

## 提速（2026-09-22）

固定死等改成「等下一步真要用的东西出现」（快就少等、慢就多等，最长各 5~10 秒）：

| 位置 | 原来 | 现在 |
|---|---|---|
| `open_list_page()` 切完页签 | 死等 1500ms | 等「新增」按钮出现（上限 10 秒） |
| 等后台「已输入 N 个有效数据」 | 每 **2000ms** 读一次 | 每 **500ms** 读一次（180 秒上限不变，算完立刻走） |
| 提交后读提示 | 死等 2000ms | 等提示出现（上限仍是 2 秒——没提示时与原行为一致） |
| 彩排点「取消」后 | 死等 800ms | 等弹窗关闭（上限 5 秒） |
| 回读名单 | 死等 1000ms | 等名单名出现在列表里（上限 8 秒，后台慢也不会误判成没建成） |

**实测（2026-09-22 彩排，42,366 个 id 的 dry-run，墙钟含浏览器启动）**：**7.2 秒 → 5.8 秒**。
这次后台计数是秒回的（灌进去就显示「已输入 42366 个有效数据」），所以"轮询步长 2000 → 500ms"没机会发挥；
省下的是开页与取消后那两段死等。后台计数慢的时候，步长变小才会体现出来。

⚠ 读正文前会先等**当前页签**的表格出数据（`.el-tab-pane:visible` 里的行数 > 0）——
这张表是异步加载的，且隐藏页签里的表也有行，不限定作用域会被误满足（2026-09-22 踩到）。

## 提交路径耗时实测（2026-09-28 · 复盘「建名单为什么慢」）

> ⚠️ **同日追加实测推翻了本节下面的初版结论**（初版以为是"服务端落库慢"）。真正的慢点是
> **提交之后、在这个浏览器会话里继续做页面操作**——跟回读方式无关，见文末「追加实测 + 修法」。

**背景**：本活动的 5 份名单（11.3 万 ~ 46.2 万条 id）每份端到端要 **3~4.7 分钟**，用户问"为什么这么久"。

**实测三组数据**：

| 场景 | 数据量 | 结果 |
|---|---|---|
| 100 条 id，**含提交与回读**（临时名单 `测速-临时-20260928`，名单ID 206875） | 100 | **全程 7.1 秒**：灌入 0.0 / 计数 0.0 / **点提交 0.1** / **等回执 0.3（拿到"保存成功"）** / 就地回读 3.1 |
| 彩排（只填+校验后取消） | **113,285** | **全程 6.4 秒**：翻开页 2.0 / 填名与类型 1.1 / **灌入 0.4** / **后台计数 0.5** |
| 五份正式名单（2026-09-24 18:32~18:46） | 113,285 / 115,567 / 145,042 / 372,198 / 462,239 | 每份 **3~4.7 分钟**；**名单创建时间间隔恒定 3~4 分钟**，与 id 数**不成正比**（最大的 46.2 万不比最小的 11.3 万慢） |

**结论（已排除的方向 + 真正的瓶颈）**

- ✗ **不是脚本慢**：灌 11.3 万条 0.4 秒、后台计数 0.5 秒；100 条那趟**含提交+回读**才 7.1 秒。
- ✗ **不是"连续开浏览器"**：只读体检验证——连跑两次 4.5 秒 / 4.5 秒（原以为是上一个会话没退出、下一个在等）。
- ✗ **不是数据量线性放大**：五份名单耗时与 id 数不成比例，创建时间间隔**恒定**。
- ✗ **不是回读导航慢**：同样的"翻列表→筛选→取行"在 `check_campaign` 里查 5 类对象总共 25.7 秒。
- ✓ **瓶颈在服务端落库那一下**：后台要先校验/入库 10~46 万条 id 才回「保存成功」，**每份固定 3~4 分钟**。
  旁证：100 条时回执 0.3 秒就到；大样本时 2 秒内没有任何回执（旧实现跑完打印的是 `提交提示:[]`）。
- ✅ **数据没丢**（只读探针 `_tmp/_probe_distribution_list.py` 读列表）：五份名单的**用户个数 = 113285 / 115567 / 145042 / 372198 / 462239**，与 CSV 行数逐一相等，**没有被截断**。

**据此做的改动（2026-09-28）**

1. **提交后等服务端回执**（`_wait_submit_ack`，上限 `ACK_TIMEOUT_S=300`，每 15 秒打一行进度）——
   原来只等 2 秒就跳页走人，**等于把"保存成功/失败"的回执丢掉**，只能靠回读猜；现在有明确信号。
2. **回读改成就地筛选**（不再重新 `goto` + 翻开页签，省一次导航和一次服务端往返）；
   就地读不到时**自动回退**成旧路径（重新打开页面再筛一次），行为有兜底。
3. 提交路径每步打 `⏱ <阶段>: 本段 X 秒 · 累计 Y 秒`（本次复盘的依据，长期留着）。

**后续可选（现在不需要）**：初版曾提「改走 A 路径」或「并发提交」两条绕行方案；上面的修法已验证
单份 **~10 秒**（11.3 万条实测 10.7 秒整进程），**不再需要为此改圈选路径或上并发**。
真要继续压时间，只剩"服务端回执 5 秒 + 开页 2 秒"这点底噪可省。

> 临时测速名单：`测速-临时-20260928`（ID 206875，100 条 id）——列表行里有「删除」，测完可在后台删掉。

### 追加实测 + 修法（2026-09-28 下午，同一份 CSV 反复真提交）

用「递增 id 数 + 分段计时」把曲线打了出来（每档都真提交、都核对过落库条数）：

| 档 | id 数 | 灌 id + 后台计数 | **点提交** | **等回执「保存成功」** | 回读那一段 | 脚本全程 |
|---|---|---|---|---|---|---|
| 1 | 100 | 0.0 s | 0.1 s | **0.3 s** | 3.1 s | **7.1 s** |
| 2 | 1,000 | 0.0 s | 0.0 s | **0.3 s** | 2.7 s | **6.6 s** |
| 3 | 10,000 | 0.1 s | 0.0 s | **0.8 s** | 2.0 s | **6.6 s** |
| 4 | 113,285 | 0.4 s | 0.1 s | **5.0 s** | **192.8 s** ← | **201.7 s** |
| 4′ | 113,285（**换新标签页**回读） | 0.4 s | 0.1 s | 4.8 s | **186.6 s** ← 一样慢 | 195.3 s |
| 4″ | 113,285（提交后**另起一个进程/新会话**，0 秒延迟就核） | — | — | — | **5.9 s** ← 立刻就能读 | — |
| 4‴ | 113,285（提交后在本进程里**再开一个会话**核对） | — | — | — | **~5 分钟** ← 不行 | — |
| 4⁗ | 113,285（活着的父进程**spawn 子进程**核对） | — | — | — | **~2.8 分钟** ← 也不行 | — |
| 4⁵ | 113,285（**父进程退出后**另起命令核对） | — | — | — | **6.3 s** ← 可以 | — |

**结论**：

- 提交本身和回执**不慢**：11.3 万条的回执只要 **5.0 秒**，且回执内容就是「保存成功」。
- 慢的是**做提交的那个浏览器会话**：提交之后在这个会话里继续操作页面，回读那一段要 **~190 秒**——
  而它由「重新打开页面 / 翻开页签 / 筛选 / 点查询 / 取行」组成，**各步超时上限加起来才 16 秒**，
  说明每次页面交互都被拖住；**同一浏览器里换新标签页也一样慢**（同站标签共用渲染进程）。
- **但只要"上一个浏览器还活着"，新的浏览器实例就会被拖住**：本进程里再开会话 **~5 分钟**、
  从活着的父进程 spawn 子进程 **~2.8 分钟**；**等本进程退出后**另起命令 **6.3 秒**（第 4″/4⁵ 档，
  条数 113285 精确）⇒ 瓶颈是**浏览器重载期**，不在服务端（服务端数据立刻就绪，不用等那 3 分钟）。
- 所以"id 多了就卡"的真相是：**大 payload 提交后，本次会话的页面在 ~3 分钟里不可用**，
  跟"服务端落库多久""用哪种回读姿势"都无关——**在原会话里怎么等都是白等**。

**修法（已落地）**：

1. **以回执为准**：等到「保存成功」即为提交成功信号（`ACK_TIMEOUT_S=300`，每 15 秒打进度）。
2. **不在"被污染的会话"里回读，也不在同一进程里补**：会话内回读只对小样本做
   （`READBACK_MAX_IDS = 20000`，≤2 万条实测 2 秒内）；超过 2 万条就**跳过**，日志打印一条
   **立刻可跑**的独立核对命令——`run_distribution_ids.py --verify-only --name "<名单名>"`（实测 **4.4 秒**），
   或整批核 `check_campaign.py --only list` / `_tmp/_probe_distribution_list.py`（6 秒）。

   **为什么不自动补**（用户当时是同意自动化的，实测后否掉）：自动化只能在同一个进程里做，
   而"上一个浏览器还活着"时新浏览器会被拖住——同进程第二会话 ~5 分钟、spawn 子进程 ~2.8 分钟，
   都远不如"退出后另起一条命令"的 6 秒。所以这一步保持**两步走**：建（~10 秒）→ 核对（~5 秒，独立命令）。
3. 提交路径保留全程埋点（`⏱ 阶段: 本段 X 秒 · 累计 Y 秒`）。

**效果（同一份 113,285 条 CSV，真提交）**：**201.7 秒 → 8.5 秒**（整进程 10.7 秒）；
事后只读探针核对：名单 `测速-113k-c-20260928`（ID 206880）**用户个数 = 113285**，与 CSV 一致。

> 5 份正式名单（ID 206870~206874）的条数也在事后核过：113285 / 115567 / 145042 / 372198 / 462239，**全部精确**。
>
> 另：`--verify-only` 是这次新加的**只读**模式（`--verify-only --name "<名单名>"`），
> 专门给"建完之后的独立核对"用。

## 踩过的坑

1. **分发名单列表是 element-ui 固定列**：「名单ID / 分发名单」两列渲染在另一张固定列表格里，
   逐行 `inner_text()` 只读得到 用户个数/类型/创建人/日期 → 回读核对要读**整页正文**，名字上面一行就是名单ID。
2. 列表默认按创建时间排是**分页**的，刚建的名单不一定在第一页 → 用「分发名单模糊查询」筛，或直接读整页正文。
