# 用博文 id 建分发名单（`run_distribution_ids.py`）

> **第几步**：执行层 **3.5B**（B 路径 · 建分发名单）
> **一句话**：拿 BI 导出 CSV 里的博文 id，在后台建一条**普通**分发名单。
> **上游 → 下游**：`run_selection.py`（导出 CSV）→ **本脚本** → `run_taskorder.py`（工单挂这条名单）。
> **什么时候用它**：走 **B 路径**、且圈选数量已核对满意之后。
> **和 A 路径的区别**：A 路径的 `run_distribution.py` 是在后台「博文圈选任务」列表里点「一键创建分发名单」；
> B 路径只有 CSV、后台没有那个按钮，所以只能拿 id 手工建普通名单。总览见 [`执行层全流程.md`](执行层全流程.md) §2。

## 怎么跑

```powershell
# 彩排（默认）：填完名字/类型/博文 id，读回后台计数后点取消，不创建
.venv\Scripts\python.exe -u automation/scripts/run_distribution_ids.py ^
  --csv activities/火山引擎MediaKit/数据/圈选/2026-09-21_D桶96词_圈选博文_20260921.csv ^
  --config activities/火山引擎MediaKit/调整/2026-09-17-D桶换词重投.yaml ^
  --only D --suffix -3 --headed

# 真建：加 --submit；建完以回执为准，核对照下面的「两步走」
... 同上 + --submit

# 名字不想按命名规则推，直接写
... --name "测试名单-火山引擎MediaKit-hang-D类"

# 独立核对（只读）——建完之后**另起一条命令**跑，别在同一个进程里补
... --verify-only --name "测试名单-火山引擎MediaKit-hang-D类"
```

名单名来源：`--name` 优先；否则 `naming.audience_task_name(campaign, audience)`，
`--suffix`（如 `-3`）**覆盖**（不是追加）YAML 里的 `audiences[].nameSuffix`。
重投第 N 次就换 `-N`，名字必须跟将来第 4 步工单的 `distributionList` 一字不差。

截图落 `activities/{活动名}/日志/distribution_ids_shots/`。

## 两步走（重要）

后台建名单**提交之后，这个浏览器会话的页面在约 3 分钟里不可用**（大 payload 提交后的浏览器重载期，
跟服务端无关）。所以固定这么走：

1. **建**（~10 秒）：等到回执「保存成功」即为成功信号，**不要**在原地回读。
2. **核对**（~5 秒）：**退出这个进程之后**另起一条命令跑 `--verify-only --name …`，
   或整批核 `check_campaign.py --only list`。**在同进程里补核对会等 2.8~5 分钟**，反而更慢。

数据量 ≤ 2 万条时脚本会在会话内顺手回读（`READBACK_MAX_IDS`）；超过就自动跳过并打印可用的核对命令。
完整实测曲线（100 / 1k / 10k / 113k 四档）见 [`执行层实测耗时.md`](执行层实测耗时.md)
「2026-09-28 · 建分发名单 `run_distribution_ids.py` 提交提速」。

## 真机流程

| 步 | 动作 |
|---|---|
| 1 | 广告后台 → 分发管理 → **3.圈选用户** → 页签 **分发名单** |
| 2 | 点 `新增` → 弹窗「新增分发名单」 |
| 3 | 填 `分发名单` 名字；`名单列表类型` 选 **博客ID**；`分组个数` 默认 1 |
| 4 | 把 CSV 的 `article_id` 用逗号连起来灌进文本域，读回「提示: 已输入 N 个有效数据」 |
| 5 | 彩排：点 `取消`；正式：点 `提交`，等到「保存成功」回执 → **另起命令**核对（见上） |

## 安全阀

- **计数校验**：后台计数 ≠ CSV 行数 → 直接取消并报错，绝不提交（防文本域被截断 / 后台没解析完）。
- **回读核对**：点了提交不算成功——按名字查到才算，查不到记 `HAS_WARN` 并返回退出码 1。
- **id 里有空白字符** → 启动就报错（后台会把带空格的当无效数据）。

## 已知坑

1. **分发名单列表是 element-ui 固定列**：「名单ID / 分发名单」两列渲染在另一张固定列表格里，
   逐行 `inner_text()` 只读得到 用户个数/类型/创建人/日期 → 回读核对要读**整页正文**，名字上面一行就是名单ID。
2. 列表默认按创建时间排是**分页**的，刚建的名单不一定在第一页 → 用「分发名单模糊查询」筛，或直接读整页正文。
3. **这张表是异步加载的**，而且**隐藏页签里的表也有行** → 读正文前要先等**当前页签**的表格出行，
   不限定页签作用域会被误满足（2026-09-22 踩到）。
4. **大名单核对前先看有没有残留浏览器**（2026-10-12 复现）：上一次会话没退干净时，`--verify-only` 会被拖到
   ~190 秒（极端 357 秒，还会误报"列表里没找到"）；残留浏览器留在 `.browser-profile\lockfile` 上的锁还会让新会话
   直接起不来（`Target page, context or browser has been closed`）。清理命令与证据见
   [`执行层实测耗时.md`](执行层实测耗时.md)「2026-10-12 · 大名单核对"卡住"复现」。
